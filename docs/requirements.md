# Requirements

Source of truth: [Epic #88](https://github.com/fukuda-yuki/gh-projects-boards/issues/88) and its child Issues. [Epic #76](https://github.com/fukuda-yuki/gh-projects-boards/issues/76) defines the implemented planning-editor foundation. This is a navigation outline, not a replacement for Issue acceptance criteria.

## Product goal

A Windows planning editor for GitHub Projects. It replaces the planning work previously done with TFS 2017 + MS Project + the Excel add-in. The PMO takes in Issues already registered on GitHub and their weekly updates, then maintains effort in person-hours, assignments and predecessors while seeing the whole schedule. Start and end dates follow automatically, and adopted changes are published to GitHub in one step. Creating Issues in the app is occasional. GitHub's table and roadmap remain the place for general Issue work.

One PMO maintains one version, named 第YYYY.MM版 by its shipping date, in one Project. Normal scale is about 40 要求事項, each with 25 tasks across SA, UI, SS, PS, PG, PT, IT, ST and OT, numbered within each phase (for example SA-001), and about 20 people. The phase split is an evaluation placeholder until a real template is available. Versions are developed waterfall-style, not agile, between a project start and end date; some run six months to a year. The PMO reads their status by phase. Initial planning is followed by a weekly refresh, plan correction and publish cycle. Assignment and overload resolution remain human decisions; the app never levels resources automatically.

## Agreed boundaries

- Launch from a Windows executable; no browser extension or Excel dependency. Ship a Japanese manual and app-generated screenshots that let a new internal user complete the weekly cycle; Help/F1 opens an offline HTML rendering of the shipped Markdown ([#172](https://github.com/fukuda-yuki/gh-projects-boards/issues/172)).
- Register Projects explicitly and switch between them. Each scoped Project is one workspace. Only Issues are planned; draft items and pull requests are not.
- Edit locally and publish explicitly, as with MS Project and the TFS Office integration. No request is sent per edit. The PMO can reset the plan to GitHub's current state, overwriting every local value with GitHub's data after a confirmation; afterwards the plan shows GitHub's values, dates included, and nothing is unpublished ([#123](https://github.com/fukuda-yuki/gh-projects-boards/issues/123)).
- The published plan is reproducible from GitHub plus the exported settings file: Issue title and assignees, blocked-by predecessors, sub-issue hierarchy, Estimate (見積), Actual (実績) and Remaining (残) number fields, a 工程 single-select field and Start/Target date fields. Calendar, rates and allowances are local settings.
- Columns use standard Japanese headers that cannot be renamed, with the GitHub Issue type as the standard 種類 column, and name the mapped GitHub field in their tooltip (#109 replaced showing the raw GitHub field name). In settings the PMO chooses the visible columns, including other Project fields and the Issue's labels, milestone and repository; only a GitHub Project field carries a display name, as GitHub Projects allows, and only Settings › 列 sets these choices ([#319](https://github.com/fukuda-yuki/gh-projects-boards/issues/319)). The chosen fields are edited and published like the planning fields, and #125 settles which field types are editable ([#125](https://github.com/fukuda-yuki/gh-projects-boards/issues/125)).
- Rates and allowances cover the people assigned in the Project. Opening a Project reads no repository-wide assignable-user list; a login typed for an assignment is verified on demand for that login ([#253](https://github.com/fukuda-yuki/gh-projects-boards/issues/253)).
- Delegate authentication and API access to GitHub CLI (`gh api`); do not require manually issued PATs or a custom GitHub App.
- Start with local development and the designated sandbox. Company GHEC + EMU behavior remains unverified until tested there.

AI assist is optional and off by default. It uses GitHub Copilot through the connected gh login or a BYOK provider. It answers from the open local plan and proposes edits that the PMO applies locally as one Undo step; it never publishes. Planning and the weekly job never depend on it ([#208](https://github.com/fukuda-yuki/gh-projects-boards/issues/208)).

The PMO can read the selected Issue's body and recent comments beside the plan in 詳細, opened by a click next to the selected task ([#211](https://github.com/fukuda-yuki/gh-projects-boards/issues/211)). The PMO can also edit that one Issue's body there and publish it with its own button, after a check that nobody changed it on GitHub meanwhile. This per-Issue body publish is the one GitHub write outside 発行; it is not part of the plan's local edits, Undo or unpublished changes, and there is no bulk body publish. Titles and comments are edited on GitHub ([#216](https://github.com/fukuda-yuki/gh-projects-boards/issues/216)).

## Planning rules

- Effort is entered and shown in person-hours (h). One working day is eight hours: weekdays 09:00–13:00 and 14:00–18:00, excluding Japanese public holidays and explicit company days off. An effort cell also accepts the displayed unit (`8h`), `d` for whole days, and full-width digits typed with the Japanese IME ([#239](https://github.com/fukuda-yuki/gh-projects-boards/issues/239)). Personal days off are not maintained: versions run for months and the PMO cannot keep them current ([#128](https://github.com/fukuda-yuki/gh-projects-boards/issues/128)).
- Effort follows the fields of a TFS task, which MS Project shares ([#131](https://github.com/fukuda-yuki/gh-projects-boards/issues/131)). Estimate (見積) is the original estimate (TFS Original Estimate, Project baseline work). Actual (実績) is the cumulative work done (Completed Work) and counts for the task's current assignee. Remaining (残) is the current estimate of the work left (Remaining Work) and drives scheduling. The forecast effort, 見込工数, is Actual + Remaining; the forecast finish, 見込終了, comes from the scheduler.
- A task is complete when its Issue is closed. Its actual start (着手日) and actual finish (完了日) are records read only from the Issue's Status-change, close and reopen history, shown read-only and never written by the app; closing no longer changes the task's plan 開始日 or 終了日, and the close day still decides successors and the summary's 完了見込 ([#308](https://github.com/fukuda-yuki/gh-projects-boards/issues/308)).
- Planning commands act on the plan: the PMO can delete a row that was never published, close a task as completed or not planned, reopen it, and take it out of the version by archiving it ([#231](https://github.com/fukuda-yuki/gh-projects-boards/issues/231)). None of these moves another task's dates.
- Scheduling is a bounded subset of MS Project auto-scheduling: finish-to-start predecessors, effort, the assignee's rate for the Project, the calendar and typed dates: a typed start is the floor of the schedule. No lag, other link or constraint types, critical path, leveling or cost.
- Start and end are plan values. They change only when the PMO edits that task, or when a refresh adopts a date changed on GitHub; tasks without effort keep their GitHub dates. An edit of 開始日, 終了日, 見積, 実績, 残 or 先行 reschedules that task, its transitive successors and the roll-ups as one Undo step, never from the 基準日. A changed date is an unpublished change. The [plan sheet Issue](https://github.com/fukuda-yuki/gh-projects-boards/issues/78) lists the exact rules; [#236](https://github.com/fukuda-yuki/gh-projects-boards/issues/236) (owner 2026-10-18) replaced the derived-date rule.
- The schedule is shown by day. The forecast is derived and is never stored or published; minute endpoints are not stored.
- One status date (基準日) anchors actual and remaining entry and the forecast. It is the day of the latest GitHub read (the first take-in, 最新の情報に更新 or a reset to GitHub) unless the PMO picks another date, which holds until the next read; opening the app or a new day does not move it, and a 基準日 change moves no task's dates. After the first take-in and after a reset the plan shows GitHub's dates as they are ([#130](https://github.com/fukuda-yuki/gh-projects-boards/issues/130)).
- A summary view shows the version against its start and end dates: elapsed and remaining working days, progress, forecast finish and remaining work against remaining capacity, by phase (a 工程 single-select Project field) and by person × phase, with remaining capacity capped by each person's optional allowance, forecast (Actual + Remaining) and monthly/daily load ([#127](https://github.com/fukuda-yuki/gh-projects-boards/issues/127)). Phase is editable in the plan; settings own the period, rates and allowances. Overloads are shown, never levelled automatically.
- GitHub milestones appear on the Gantt and in the summary at their due dates, so the forecast finish can be checked against them. Their due dates are kept on GitHub ([#133](https://github.com/fukuda-yuki/gh-projects-boards/issues/133)).

## Explicit exclusions

Generic Issue administration other than what the plan itself offers — closing a task as completed or not planned, reopening it, and taking it out of the version by archiving it ([#231](https://github.com/fukuda-yuki/gh-projects-boards/issues/231)); labels, comments, transfer and Issue deletion stay on GitHub — Kanban, Gantt drag editing, critical path, MS Project import, task creation by pasting from Excel, automatic resource leveling, personal days off, minute-precision schedules, realtime synchronization, cross-Project publish and organization-wide load. Mass creation and agreed-plan comparison are unscheduled conveniences. CSV import remains available but is not required for the ordinary planning job; its template and accepted columns follow the column settings ([#324](https://github.com/fukuda-yuki/gh-projects-boards/issues/324)). CSV export is optional whole-Project analysis output for Excel, including current local values and unpublished markers, without an Excel dependency or GitHub writes ([#173](https://github.com/fukuda-yuki/gh-projects-boards/issues/173)). Project-wide totals belong to the summary view; weekly reports, additional backup and logging are not planned unless version-scale use demonstrates a need. GHEC + EMU uses the appropriate gh authentication; it is not a separate product track.

GitHub milestones provide read-only target dates on the Gantt and summary. The PMO compares forecasts with targets, drills into late member Issues, and optionally maps phases to milestone targets without changing scheduling. First open initializes the period and unambiguous phase milestone mappings from GitHub; subsequent reads preserve explicit settings and clears ([#195](https://github.com/fukuda-yuki/gh-projects-boards/issues/195)).
