# Specification

The [requirements](requirements.md) and [decisions](decisions.md) define the planning editor. The ordinary window exposes the workspace, Project settings, an editable native plan sheet with a row-aligned Gantt, a read-only summary view for phase status and load, and explicit refresh and publish review.

## Pending-input invariant (all editing views)

The plan sheet and settings obey the same invariant: **pending input is never hidden or dropped**. A row or cell containing uncommitted, composing or invalid input remains in the visible, focusable presentation until committed or explicitly discarded. Filters, recalculation, drill-down membership, period/zoom changes and redraws cannot remove it. Pending rows remain alongside the normal filtered/period results; they stop being retained when their last pending cell resolves. This retention changes presentation only, never the schedule, totals or assignment.

There is always a way out. Escape in an editor discards only that cell's pending input and restores its current committed display value, clears its validation error and creates no Undo entry. IME conversion Escape belongs to the IME first. Invalid input has an error callout anchored next to its cell. Commands requiring resolved input (navigation, Undo/Redo, Project switching and close) either proceed after resolution or refuse and focus/scroll to the problem cell; they cannot leave the only correction path outside the view. Focus-loss validation may report an error without stealing focus from another edit. Leaving an unchanged, already rejected settings value does not restart focus recovery or dismiss the Project picker. Choosing a navigation command still refuses the transition and returns to that invalid input.

Validation feedback follows task identity and field, not a recycled control instance. The cell callout is announced to assistive technology and overlays the view without inserting a line above the sheet or moving its rows. When scrolling moves its cell outside the sheet viewport, unloads or rebinds its row, the callout closes or moves to a visible editor for that same problem. An offscreen cached editor is not a callout target. Scrolling back or a refused command makes the retained error reachable again; another task must never inherit its message.

After a refused or failed operation, toggles, pickers and selectors are synchronized with the current document (or accepted presentation setting), including an in-memory change accepted before a persistence failure. Restoring a control is not another edit. Each view owns its controls and pending inputs; this invariant does not introduce a second document or shared editing framework.

## CSV import of new tasks (#82)

**CSV から追加…** in the sheet toolbar opens the native `.csv` picker. Import adds new local tasks to the selected Project only; it never updates existing tasks or writes to GitHub. File selection, validation and duplicate confirmation precede one atomic `InsertPlanRows` operation with kind `CsvImport`. Its rows and any newly resolved people are one Undo step. A successful import clears the title filter and selects the first imported task so the result is reachable. Imported Estimate leaves Remaining and Actual empty; Remaining is displayed and scheduled from its calculated default. The existing scheduler calculates dates and parent roll-ups, retaining unknown dates for unassigned or incomplete work. Only **発行** creates Issues and publishes their relationships.

The template is [templates/new-tasks.csv](../templates/new-tasks.csv), copied to `templates/new-tasks.csv` in the app output. It is UTF-8 with BOM for Excel. Input accepts strict UTF-8 with or without BOM, then strict Windows-932 (Shift-JIS) if UTF-8 decoding fails, using the framework code-page provider. Files are at most 5 MiB and 10,000 data records. Quoted commas, doubled quotes and quoted line breaks are supported. Error line numbers are physical file lines, including the header; a multiline record is identified by its first line.

| Header | Value |
| --- | --- |
| キー | Required unique, case-sensitive file-local key; no `#`, semicolon or control characters. Numeric keys are allowed. |
| タイトル | Required nonblank task title. |
| 見積 | Required column; empty means unknown, otherwise a nonnegative decimal number of person-hours using `.` as the decimal separator. |
| 担当者 | Optional; GitHub login, or semicolon-separated logins; empty is unassigned. |
| 先行タスク | Optional; semicolon-separated file keys or existing Issue references. |
| 親 | Optional; one file key or existing Issue reference. |
| 開始日指定 | Optional; `yyyy-MM-dd` or `yyyy/M/d`, empty for none. |
| リポジトリ | Optional `owner/repository`; empty uses the current default repository. |

Imported rows use stable parent-first order, preserving sibling CSV order and accepting forward parent references without renumbering keys. Subtrees attached to existing plan parents go after their last current descendant; other imported subtrees append at the end.

Columns may be reordered. Unknown or duplicate headers and missing required columns are errors. File keys resolve first; `#123` (or a bare number without a matching key) refers to Issue 123 in that row's repository. `owner/repository#123` disambiguates repositories. Existing references must identify an Issue already loaded in this Project. Keys are not sent to GitHub or stored as task identity; each import creates fresh local identities.

Core checks all records before accepting any rows: syntax, duplicate keys, missing titles, invalid numbers/dates, unresolved keys/Issues, repositories and assignable logins, and hierarchy/dependency cycles including existing tasks and inherited summary dependencies. Repository existence and Issue-creation capability and required assignable-user identities are read through the active scoped connection; incomplete reads cannot authorize an import. New people start at 100% rate with no allowance; existing resource settings are preserved. Validation uses the same scheduling rules as ordinary editing. Errors appear in a bounded list of **line number + short reason**, with **CSVを選び直す** as the next action. Cancellation changes nothing.

Duplicate detection uses SHA-256 of the original file bytes, retained as local provenance on each imported row. If any current row has that hash, the UI requires **重複して追加** confirmation before adding another copy. It survives save/reopen, identity promotion on publish and refresh; Undo removes it with the imported rows. Changed bytes, including a changed encoding, are a different file; this is an exact-repeat warning, not semantic deduplication. Provenance is excluded from GitHub fields and unpublished markers.

CSV preparation belongs to the workspace operation queue. Pending edits are resolved before the picker opens; closing cancels its owned repository reads and dismisses validation/duplicate dialogs without adding rows.

Publication resolves each new row's repository separately. Every destination must pass preflight before the first dispatch; creation and uncertain-creation reconciliation use that same repository, while batch sizes, pacing and #79 stage order remain unchanged.

The [sandbox evaluation file](evaluation/sandbox-plan.csv) contains a small plan for Project 3, uses only `fukuda-yuki` or no assignee, and targets `fukuda-yuki/codex-sandbox`. Importing it is local preparation; publishing it remains an explicit ordinary-app action.

## CSV export (#173)

**CSV に書き出し…** (`PlanSheetCsvExport`) sits beside **CSV から追加…** in the plan sheet overflow. With a Project open, it resolves pending cell input through the ordinary command gate before opening a native save picker; invalid or composing input prevents export. The suggested name is `<Project title>.csv`, with a `.csv` file type. Cancellation does nothing. Generation and writing run off the UI thread. Failure shows the reason in the existing error presentation; success confirms the exported data-row count (for example **1,040 行を書き出しました。**). Export never reads or writes GitHub and requires no Excel installation.

Export includes every local-document row in plan order, including requirement/summary rows, folded children and filtered-out tasks. There is no row-scope choice. Values are the current local sheet values, including calculated dates, summary effort and calculated Remaining. Empty values are empty cells; unavailable/unsupported extra values retain **取得できません**. Assignees use the full comma-separated sheet names; labels and predecessors use the sheet text (plan row IDs, or 計画外).

The column set is deliberately tied to the sheet configuration:

1. Fixed **ID**, the one-based plan row number.
2. Every visible column from `PlanSheetColumns.All(document)` in its current order, excluding `Id`. Headers are their configured display names (`Name`). Supported standard columns are 状態, タスク名, 工程, 担当者, 見積 h, 残 h, 実績 h, 開始日, 終了日, 先行, 開始日指定, 日程固定 and ステータス; optional columns include other Project TEXT/NUMBER/DATE/SINGLE_SELECT/ITERATION fields, ラベル, マイルストーン and リポジトリ. 状態 exports its accessible state text, empty for an ordinary unchanged row. A visible repository column does not replace the fixed identity column.
3. Fixed **要求事項** (the title of the row's top-level ancestor, so tasks can be filtered and pivoted by requirement in Excel; empty for a top-level row), **リポジトリ** (`owner/name`), **Issue 番号**, **URL**, then **未発行**. Local tasks have no Issue number or URL. 未発行 is **新規** for a new local task, otherwise comma-separated changed-field names as in publish review, or empty for an unchanged row. This uses the same unpublished-change rules as the sheet, including changes to hidden fields.

Effort and Project NUMBER values are invariant decimal numbers without units or grouping; negative numeric values remain numeric. Dates use `yyyy-MM-dd`. The file is UTF-8 **with BOM**, with CRLF record endings and RFC 4180 escaping: fields containing commas, double quotes, CR or LF are quoted and embedded quotes are doubled; embedded line breaks are preserved. Any text cell (including headers and identity values) starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with one apostrophe to neutralize Excel formulas. Exporter-produced numbers and dates are not prefixed. This is an analysis output, not the new-task import template; Gantt, `.xlsx` and import changes are excluded.

## Summary view (#127)

**サマリー** is the selected Project's read-only waterfall status view. Planning edits belong to 計画; rates and whole-Project allowances belong to settings. Undo/Redo, refresh and publish remain in the shell. The status bar has no Gantt legend here. All measures consume the same scheduled result as the sheet; no second scheduling or resource leveling occurs. Requirement/summary rows never contribute to counts or effort.

The header reads 「基準日 yyyy/MM/dd (曜) 時点の状況」 and 「プロジェクト期間 start – end」. Five measures form the Project band:

- 残り稼働日, with 「全 N 稼働日のうち M 日が経過」. The Project calendar excludes weekends, bundled/imported holidays and company days off. Total days use [start, end], elapsed days [start, status date), and remaining days [status date, end]; after the end remaining is zero. Missing endpoints make dependent measures unknown.
- 完了見込 is the latest task end (calculated for open work, close date for closed work, kept dates for kept work). Its signed working-day difference is days in (end, forecast] when late, minus days in (forecast, end] when early. Text is 「終了日より N 稼働日遅れ」, 「N 稼働日前」 or 「終了日どおり」. Caption: 「先行関係と見込み残存工数から計算（担当者の負荷は含まない）」.
- 終了日までに必要な稼働 is remaining hours of all tasks, including unassigned/multiple assignments, divided by configured people's remaining capacity. Show N %, 「残 Xh ÷ 稼働可能 Yh」, and warning color plus 超過 above 100% (「100% を超えると間に合わない」).
- 進捗 is summed Actual / summed Forecast, with 「完了 a / b タスク」 and 「見積 Zh より ±Dh」. Remaining is the scheduler's effective Remaining (closed = 0; blank defaults to max(Estimate − Actual, 0)); Forecast = Actual + Remaining, variance = Forecast − Estimate. Blank Actual counts as zero. Progress is unknown for zero or unknown Forecast. Totals sum known contributors and retain excluded-task counts; no known contributors means unknown. Variance and progress use matching known contributor sets. Missing Estimate and Remaining make open-task Remaining and Forecast unknown. Label exclusions 「工数未入力 N タスクを除く」; never silently present partial totals as complete.
- 要注意 contains identity-set buttons for 期限超過, 見積超過, 残 0・未完了, 担当者なし (残 Nh), and 工数未入力. Hide zero counts. Use existing PlanLateness, IsOverEstimate and IsZeroRemainingOpen rules.

Summary percentages are whole numbers: round to the nearest integer (midpoints away from zero), but round percentages above 100 up so a small overload remains visible (100.4% becomes 101% 超過). Core values stay exact. A person/phase cell without tasks and a month without allocated work show “–”; zero is reserved for a known value of existing work. Unallocated work still has its reason and task route.

Table headers and cells do not wrap. The completed/task column accommodates four-digit counts with digit grouping. Phase selectors are left-aligned plain table text; interactive table cells have no field border or fill at rest, a hover fill, native keyboard focus and an accent fill/outline when selected. Selection reveals the detail heading and filter command; details use the same row IDs as the plan, never internal GitHub/local identities. Horizontal table viewports leave vertical mouse-wheel input to the enclosing vertical viewport at its native rate.

The phase table takes its measured column width and the timeline fills the remaining space beside it. Its month axis uses the Gantt month-tier label style, with labelled 基準日 and 終了日 lines. In the forecast tile, only the date and difference use warning color; the explanatory caption uses secondary text. Attention commands are compact, left-aligned icon/label/count buttons with the sheet's corresponding warning icons.

Without an end date show 「終了日が未設定です」 and **設定を開く**, and 「—」 for dependent measures. Do not compare progress with elapsed-time share: waterfall effort is uneven.

**工程別** has options in mapped field order, then 工程なし only when present, then 全体. Columns: closed/tasks, 見積, 実績, 残, 見込, 差異, 進捗, 目標日, 完了見込, 差, 期限超過, 見積超過. Beside it, **工程の日程** draws each phase from earliest task start to latest end across the Project period, extended for later forecasts; completed share is solid, with 基準日 and 終了日 lines. Mapped milestone targets appear as ◆; the phase difference compares its forecast with that target in Project working days. When unmapped both sections show 「工程のフィールドが未設定です。プロジェクトの単一選択フィールドを 工程 に割り当てると、サマリーで工程別に集計します。」 and **設定を開く**.

**担当者 × 工程** lists configured people in settings order, then nonempty 担当者なし and 担当者が複数 groups, then 合計. Phase columns use the same phase order. Cells retain task identities and switch between 見込み残存工数 h, 見込工数 h, 進捗 and 期限超過. Overdue cells have a critical warning icon and 期限超過 in their accessible names. Row totals show 残 合計, 稼働可能 and 必要稼働率. Capacity = rate / 100 × remaining working days × 8 h, capped by max(allowance − that person's Actual, 0) when allowance is set; display the formula as a caption. Ambiguous groups have no capacity. Required load is Remaining / capacity, unknown for zero or unknown capacity, and above 100% uses warning color and 超過 text.

The **工程別 / 月別** switch selects a secondary person × month grid from the start month through the end month or later forecast month. Reuse PlanPeople's daily allocations and Project calendar capacity: monthly load %, overloaded-day count, maximum daily load % and contributing task identities. Fixed work spreads Remaining evenly across its working days; completed work has no future allocation. Unallocated/unknown work stays identified; zero capacity never yields an invented percentage. Full calendar months are used. Daily overload cannot disappear behind a monthly average.

Selecting a phase row or person × phase/month cell shows 「{person} · {phase} N タスク · 残 Xh · 期限超過 a · 見積超過 b · 残 0・未完了 c」, omitting zero parts, and a read-only list of ID, タスク名, 見積, 実績, 残, 開始日, 終了日 and existing tooltip state text. **この N タスクで計画を絞り込む** switches to 計画 with exactly those identities using the existing changed-task exact-set title filter. Attention buttons directly apply the same exact-set filter. Show its count and select the first task; clearing the title filter restores the full plan.

Detail headers and rows share the same column widths and horizontal origin. ID is a left-aligned identifier; effort and date values are right-aligned under their headers. 状態 is empty for ordinary open tasks; applicable states use the sheet indicator wording (期限超過, 予定より遅れ, 見積超過, 残 0・未完了, 完了), retaining unallocated-work reasons in month details. Long text is trimmed with its full text in the tooltip. Details take their natural height within the page, without an inner vertical scrollbar. Show at most the first 200 tasks in plan order; when more remain, show 「ほか N タスク。計画で絞り込むとすべて表示します」. The selection totals and filter command always include the full set.

At 1920 × 1080 the band and phase table are visible without scrolling. With no milestones, the first person rows are also visible; when present, the milestone table follows the phase table and the person rows remain reachable by vertical scrolling. The card scrolls vertically. At 1280 × 720 horizontal scrolling is confined to wide tables, never the page. Core aggregation should take about 100 ms or less for the 1,040-row evaluation plan; group once rather than rescan the plan per cell.

### Phase and period settings

工程 is an optional mapped Project SINGLE_SELECT field: exact case-insensitive name 工程 and correct type auto-match on first open and in mapping settings; ambiguity stays unassigned. Refresh never creates it and there is no create command. The same mapping appears in the 工程 settings group, with options in field order and leaf-task counts, followed by 工程なし. Unmapped settings show the same explanation as the summary. The optional milestone mapping column selects a GitHub milestone title for each phase; it never edits the milestone or its due date.

The sheet places narrow 工程 immediately after タスク名, visible by default; tooltips expose full option names. Typing, paste, Ctrl+D, fill handle and Delete use normal operations and Undo. Trim input and match exact option names case-insensitively; reject unknown text with 「工程は SA, UI, SS, PS, PG, PT, IT, ST, OT のどれかを入力してください。」 using actual options. Unmapped cells are empty and read-only, with 未設定 in the header tooltip. Summary rows use baseline-only values and cannot edit/publish Phase, like Status. Refresh, conflicts, reset, unpublished markers and publish review follow Status; publication writes the current option ID and review shows option names. Settings export/import preserves the mapping. Task CSV import does not add a phase column.

Settings **期間** contains optional 開始日 and 終了日. These and other settings date text inputs accept `yyyy-MM-dd` and `yyyy/M/d` (including `2026/10/13` and `2026/1/5`), and display `yyyy-MM-dd`. Invalid date text reports 「日付は yyyy-MM-dd または yyyy/M/d で入力してください。」. End before start is rejected without changing accepted settings. End is a reporting boundary, never a scheduling constraint. Both dates export/import and each accepted edit is one settings Undo operation. **担当者** lines contain name, 稼働率 and optional 上限工数 h; empty allowance is valid, invalid input stays editable and blocks navigation. Each accepted rate/allowance edit is one settings operation. Evaluation seeds both dates from the version manifest and auto-maps 工程 at 未発行 0.

On first open only, when the first complete GitHub read creates the local document and auto-matches columns, initialize empty Project start/end and phase milestone settings. Start is the earliest known start among the retrieved Issue rows. End is the latest known due date among the exact-title milestone groups that at least one retrieved Issue row belongs to, falling back to the latest known Issue-row end only when none of those has a due date. Milestones no Issue of this Project uses are ignored, because one repository can hold several concurrent versions, each a separate Project with its own milestones; absent dates stay empty. If the derived start exceeds the end, leave both empty. Phase mapping follows the matching rule in [GitHub milestone targets](#github-milestone-targets-133). Initialization is part of document creation, not a user Undo operation, preserves held GitHub dates and leaves zero unpublished tasks. The dates and mappings are ordinary editable, clearable, exportable/importable settings afterwards; refresh, reopen and reset never derive them again or overwrite explicit values or clears.

## Current publish workspace (#79)

The review header exposes `PlanPublishStatusDate`. When 基準日 is before today (the App's `PlanClock.Today`), show **注意: 基準日 yyyy/MM/dd (曜) は今日より前です。「最新の情報に更新」で今日の進捗を取り込めます。** using the existing unpublished-work amber caution brush, not overdue critical red. Its accessible name carries the full visible text. This warning does not block publication or change the mutations sent. When 基準日 is today or later, show **日付は基準日 yyyy/MM/dd (曜) で計算したものです。** In either case, when the latest planning action released held GitHub dates, append **（最初の取り込みのあとの再計算）** or **（GitHub の状態に戻したあとの再計算）**. This origin survives reopening until a successful publish or refresh; Undo back into the hold clears it.

The review includes the native sub-issue order changes the publish will write before → after (the retained native order → the plan's child order), including non-conflicting changes and a retry of a failed reorder; a child-order difference only GitHub holds is not listed. Relationships outside the plan use a retrieved repository/Issue number when available; otherwise they are labelled as unretrieved external Issues and offer a link to the source Issue's GitHub relationships. They never use the Project caption.

The PMO reviews the changes in the open Project before explicitly confirming publication. **発行** opens a review in the workspace with one group per Issue: readable task title and plan ID, retrieved repository/Issue number when available, and its changed fields with before → after values together. Short field differences share a wrapped line rather than repeating the task identity for every field. Full values wrap within the available width and remain readable without expanding each difference. New Issues are labelled 新規 Issue. Field names use the sheet's full names (見積工数, 実績工数 and 見込み残存工数 for its compact effort headers); dates show `yyyy/M/d (曜)` so before, after and GitHub values keep their year (#109). Empty values are 未入力; assignees and relationships use readable names or plan IDs. Conflict lines show local and GitHub values with explicit choices beside their Issue's differences. Resolving a conflict saves a local operation; it does not send writes, and the review retains the affected Issue or its nearest remaining neighbour in view. Unavailable rows offer discard or copy to a new Issue. Confirmation is disabled while unresolved conflicts or unavailable rows remain.

Version-scale review uses a bounded, virtualized native list. Ordinary short values remain visible together as readable Issue/task identity, field and before → after, without expanding every difference. Supplementary full-text access preserves the user's place. Virtualization must not omit differences or reset conflict choices when rows leave the viewport; every difference and recovery action remains reachable by scrolling and keyboard, while confirmation remains outside the scrolling list.

Opening or closing the review never writes. Confirmation invokes the existing publisher, including its identity and conflict read. A blocking conflict discovered by that read returns to review without sending mutations. Changes arriving after review therefore require another explicit confirmation. During publication the busy panel replaces the review; the review cannot close or reopen until publication finishes. Stages are 新規 Issue, フィールド・担当者, 親子関係, 先行タスク, 表示順 and 検証. There are no invented percentages. During remote work pointer and keyboard input to the plan are blocked. Project switching and settings changes wait until the operation finishes. Closing the window cancels the owned operation and waits for its durable interruption result. Restart never publishes automatically; 最新の情報に更新 reconciles known outcomes, and explicit 発行 resumes remaining work.

The sheet marks conflicted cells 競合 with a critical outline and corner marker but no tinted background, because a critical tint means overdue work. Selecting a conflicted cell replaces the selection line's reason text with 「競合: GitHub では …」 and the GitHub value. The choice between values is made in the publication review. Failed or unverified rows carry the indicator column's failure marker and expose their reason in the selection line and accessibility text. Successful refresh/publish refreshes markers and the distinct unpublished task count. A failed complete-read attempt retains the plan. Refresh, publication and save failures use the work-card InfoBars and retry behavior defined in the workspace contract below. Undo remains a local operation after publication and can produce new unpublished changes.

## Remote operation feedback (#120)

Opening a Project, refreshing and publishing share one centered busy panel inside the work card: a horizontally centered 40 DIP indeterminate ProgressRing, a centered 20 px semibold operation heading, secondary explanatory text and a full-width step list below. Completed steps have a check mark; the current step is semibold with its count right-aligned. The cancel button and its note are centered. Open shows **{title} を開いています**, refresh **最新の情報を取得しています**, and publish **発行しています**. Read operations explain **GitHub からプロジェクトの内容を読み込んでいます。終わるまで計画は操作できません。**; publish explains **GitHub に書き込んでいます。終わるまで計画は操作できません。** Completed steps have a check, the current step is emphasized, and future steps use secondary text. Known counts are right-aligned and grouped in Japanese notation. Opening by URL starts the same busy operation before URL resolution, with **プロジェクトを確認** as its first step and **プロジェクトを開いています** until the title is resolved. Input and a second open are blocked throughout resolution and loading; cancelling resolution returns to the prior page with the cancelled announcement. Reading then reports **プロジェクトの項目を取得**, followed by **日程を計算**; Issue details are read within the item traversal, not a separate stage. Publish starts with **最新情報の確認**, followed by the existing write stages and verification, with completed/total write counts where known. Counts describe observed traversal and successful writes, never invented percentages; inaccessible omitted items are not counted as read. Retries may restart read counts.

The picker shows the selected title immediately and the status bar shows **{title} を読み込み中**. Opening hides the previous surface immediately with an opaque card background; its status panel appears after 300 ms if still running, avoiding a flash for fast local opens. Refresh and publish use a translucent card backdrop over the blocked plan. Remote command labels stay unchanged and buttons are disabled. Local editing, Undo/Redo and settings never show this panel.

Open and refresh offer **中止** and explain that cancellation returns to the state before the operation. Refresh also states that Issues confirmed as already created stay linked to their rows. Cancellation is checked immediately before adopting the complete refresh or creating the first local document. Once adoption starts, the operation completes without further cancellation checks. When **日程を計算** begins, **中止** remains visible but disabled. Cancellation during the connection recheck or the repository/creation lookup for unconfirmed Issue creations is propagated as cancellation before interpreting the API response as a failure. A confirmed creation is saved immediately as a durable link between the existing GitHub Issue and its local row, to prevent duplicate creation on the next publish. These links remain saved if a later lookup or Project read is cancelled. If no creation has been confirmed, cancelling a creation lookup leaves the stored document unchanged. Cancellation before adoption terminates the owned read and retains the previous Project (or no Project), plan and history without an error bar, except that confirmed creation links remain saved; with no previous Project the chooser/connection page remains usable. Announcements reflect the actual result: cancellation before adoption, completion after adoption, or failure. Publish has no cancel button and states **ウィンドウを閉じると発行は中断されます。次に 発行 すると残りを再開します。** The panel is a polite live region named with the heading and current step. Operation start, completion (**{title} を開きました**, **最新の情報に更新しました**, **発行しました**), cancellation and failures are announced; failures retain the existing recovery UI. Progress reporting preserves read completeness, retry and durable publish recovery semantics.

## Current workspace and Project settings (#81 / #109)

The title bar includes a **ヘルプ** question-icon button (`PlanHelp`) beside the settings gear on every screen, including connection before a Project is open. Its tooltip and accessible name are **ヘルプ（F1）**. A root-level F1 keyboard accelerator invokes the same action, without a second accelerator tooltip label; an open dialog retains its own keyboard scope. The app ships `docs/user-manual.md` as **マニュアル.md** beside the executable and `docs/manual/images/*.png` as `manual/images/*.png`, in development, evaluation and published output. Markdown is the single source. Help resolves it from `AppContext.BaseDirectory`, renders it as HTML in a per-user temporary folder and opens that HTML asynchronously through the default shell application (`UseShellExecute = true`). Relative image and document links resolve against the shipped manual, not the temporary HTML directory; images use absolute `file:///` URIs. The Core converter supports headings, paragraphs, bold, inline code, ordered/unordered lists with one nested level, pipe tables, links, images and line breaks, escaping all text with no raw HTML passthrough. Heading IDs keep letters/digits (including Japanese), replace spaces with hyphens, lowercase ASCII and drop other punctuation; duplicate IDs get numeric suffixes. The inline stylesheet uses Yu Gothic UI / Segoe UI, a roughly 960px content width, readable tables and responsive images. Conversion or temporary-file write failure falls back to opening the Markdown; a missing Markdown association falls back to `notepad.exe`. A missing source file shows **マニュアルが見つかりません: <path>** in the existing error presentation and launches nothing. Help does not commit pending input or change the plan, Undo history or unpublished state.

## Current planning editor scheduling contract (#78)

This section is the current contract for the new UI-independent `PlanEditor` model.

### Inputs, identity and calendar

- A task has an opaque Issue/local identity, a positive unique plan-row ID, optional parent identity and predecessor identities. Row IDs are supplied by plan order, never recomputed by filtering. External predecessors retain their reference, do not constrain dates and produce `プロジェクト外の先行タスク: {reference}`. References outside the Project have no plan-row ID. Missing parents are external hierarchy boundaries, with `プロジェクト外の親タスク`; they do not create summary rows.
- Inputs retain Estimate, Remaining, Actual, assignees, closed state and local close date, 開始日指定, 日程固定, current start/end and GitHub baseline start/end separately. Effort inputs are nullable decimal person-hours; valid effort is nonnegative. Missing effort is not zero. Negative refreshed effort or inverted kept dates isolate that row as described below; nonpositive/duplicate row IDs, duplicate/empty identities and invalid settings still reject the calculation without changing inputs.
- Working time is Monday–Friday 09:00–13:00 and 14:00–18:00, excluding bundled Japanese holidays 2025–2027, additional dates from the existing validated holiday CSV importer and company days off. Imported dates supplement the bundle. Beyond the supplied holiday years, weekdays still apply and affected rows warn `祝日データの対象年外`.
- A single person's rate defaults to 100%; allowed rates are greater than 0 and at most 100%. Capacity is 8 hours times rate per day, spread uniformly across both work intervals (50% means 4 person-hours over an eight-hour day). No assignee or multiple assignees use the Project calendar at 100%; multiple assignees warn `担当者が複数`. No resource leveling occurs.
- 基準日 is the stored day of the latest successful first take-in, refresh or reset, unless subsequently picked by the PMO. Every calculation receives the caller's today; a fallback to that day is permitted only for a document never read under this rule. Core never reads the clock. Publishing, including its reconciliation read, preserves the calculation date. A failed or cancelled read changes neither the date nor the plan. Project start is optional. Day inputs become 09:00 boundaries. Internal working-hour endpoints use exact rational arithmetic derived from decimal effort and rate, only during recalculation, never in returned date cells or persisted inputs. No rounding to minutes or tolerance may move an endpoint across a work-interval/day boundary; successors inherit the exact endpoint, also across differing rates. A 4-hour task at 100% finishes at 13:00; its successor starts at 14:00 that day. At 18:00 a positive-work successor starts on its next working day. Kept start/end dates represent 09:00/18:00 even on nonworking days.

### Scheduling precedence and edits

Before these rules, isolate invalid row data as described below.

1. Summary rows roll up children as below, overriding their valid own scheduling inputs.
2. Only closed Issues are complete. Their Remaining is calculated as 0 and their end is the local close date, reason `完了`; their start follows the retained/adopted start rules, capped at the close date when it would be later (including planned, specified and fixed starts). This cap is calculated; the resulting date pair is validated before publication or successor scheduling. Other inverted kept pairs remain invalid. The reader retrieves `closedAt` with state; the snapshot converts its UTC timestamp through an injectable TimeZoneInfo (production: TimeZoneInfo.Local). Closed and CloseDate are GitHub-owned row data, never locally edited; refresh clears the close date on reopening. A closed Issue without readable closedAt makes the reader incomplete and cannot replace the document; a direct Core input without a close date warns `完了タスクの終了日なし`. An open task with no positive Estimate or Actual and zero work remains a milestone; fixed milestone dates stay fixed. An open positive-effort task with effective Remaining 0 is not complete and shows `残 0・未完了`.
3. 日程固定 retains current typed dates, reason `日程固定`. Missing either date warns `日程固定の日付不足`. A start day before any effective predecessor's end day warns `先行タスクより前に開始`; a start on that end day does not warn. Dates do not move.
4. Both Estimate and Remaining absent retain dates, reason `工数なし`.
5. Work is entered Remaining, otherwise max(Estimate − (Actual or 0), 0); when Estimate and Remaining are both absent it is unknown. Earliest start is the maximum of 基準日, optional Project start, 開始日指定 and effective predecessor finishes. Normalize positive work to working time. Unfixed zero work has identical start/end at that boundary without calendar normalization, including open positive-effort work with zero Remaining. Estimate = 0, Actual > 0 and empty Remaining calculates 0 instead of isolating the row.
6. Actual > 0 and positive work retains the existing start; remaining work begins at max(基準日, retained start), normalized to working time, and uses effective Remaining at the person's rate. Dependencies and constraints do not move a historical start; a start day before any effective predecessor's end day warns, while a start on that end day does not. A missing start uses earliest start and warns `進行中タスクの開始日なし`. Re-estimated overruns therefore finish after the remaining work, not automatically on the 基準日.
7. Other positive-work tasks calculate both dates from earliest start and work/rate. Calendar adjustment does not replace the start reason.

Estimate is the original estimate; editing or clearing it never writes Remaining. Empty Remaining stays empty in the document and on GitHub: its default is calculated, editable secondary text and never published. Explicit Remaining uses primary text. A Remaining edit compares against the stored input, not its calculated display. Entering edit mode and committing the displayed default with Enter, Tab or focus departure stores it explicitly even when the text is unchanged; Escape cancels, and selection without edit mode never creates an input. The editor may initially show the calculated value. Subsequent Actual edits preserve an explicit Remaining. Forecast (見込) = (Actual or 0) + effective Remaining; variance (差異) = forecast − Estimate, unknown without Estimate. Open tasks with forecast above Estimate show 見積超過. These values are shared by scheduling and summary totals. Read-only summary task details display scheduled effective Remaining, including calculated defaults and closed zero, consistently with totals and load. Planning edits use the sheet. Core exposes Actual ÷ (Actual + Remaining) as the work-complete fraction, unknown for missing operands or zero total, with scaled arithmetic to avoid overflow. A forecast beyond decimal range is unknown and its overrun marker names the range error. Typing/clearing a start updates both the current start input and 開始日指定; typing a nonempty end updates the end and enables 日程固定, while clearing an end does not silently disable the flag. These pure input transformations are composed by the local document commands below. Estimate, Remaining and Actual edits reject a negative new value; start/end edits reject an inverted resulting pair when dates are kept. An automatic start edit may move past an old GitHub end because its end is recalculated; typing an end enables 日程固定 and validates the resulting pair. Rejection throws a validation error and returns no replacement task, leaving the original input intact. A valid correction to one field is allowed while another refreshed field still needs correction.

Each date cell exposes its day value, `Calculated` or `Kept` origin and a boolean difference from the corresponding GitHub baseline (including null transitions). In-progress start is Kept, end is Calculated. Valid summary cells are Calculated; isolated summaries keep their GitHub dates. Unchanged calculated values are not unpublished changes. Inputs are never overwritten by a calculation.

### Hierarchy, dependencies and reasons

- A row with in-Project children is a summary. Each effort column sums direct children recursively; if any child's value is absent the total remains absent (never turn missing into zero). Check all children for absence before addition, so an unknown total never overflows merely because of child order. Start is the minimum available child start, end the maximum available child end; all absent yields absent. Its own valid effort/date/constraint/closed inputs remain intact but are ignored for summary scheduling; invalid data follows the isolation rule below. Removing its last child restores ordinary task semantics. Publishing writes rolled-up start/end but **not** rolled-up effort; no publish implementation is implied here.
- A predecessor link to a summary waits for its rolled-up internal end. A summary's predecessors constrain every descendant, including nested summaries. Completed/fixed/no-effort descendants still retain dates; fixed and in-progress violations warn. Parent 開始日指定 is not inherited. Duplicate predecessor references have no extra effect.
- Reject parent hierarchy cycles, dependency cycles (also those induced by summary roll-up/inheritance), self-links and any predecessor link between ancestor and descendant. Errors identify the involved plan-row IDs as `循環参照: #1, #2`. Reject the whole calculation, with no partial result or input mutation. Unrelated descendants of a cycle are not named as cycle members.
- Exact start reasons: `基準日`, `プロジェクト開始日`, `開始日指定 M/d`, `#{row ID} の終了後`, `開始日を維持`, `完了`, `日程固定`, `工数なし`, `子タスクの集計`, `入力エラー`. Dates use invariant M/d. For equal constraints, predecessor wins, then 開始日指定, Project start, 基準日; tied predecessors use the smallest plan-row ID. In-progress with a retained start uses `開始日を維持`; a missing start uses the winning earliest-start reason. A valid summary uses `子タスクの集計`; isolated rows use `入力エラー`.
- Warnings are per row, unique strings. Refreshed negative effort, except ignored Remaining on a closed Issue, warns `工数が負の値`; an inverted kept start/end pair warns `開始日が終了日より後`. An unrepresentable calculated schedule warns `日程が日付の範囲外`; effort-total overflow warns `工数の集計が範囲外`. The affected row retains its GitHub baseline dates with Kept origin and reason `入力エラー`; inputs (including invalid values) remain available for correction, and no date change is proposed. Neither date is used as a dependency or summary endpoint. Invalid leaf effort is displayed as received, never included in summary totals.
- A summary containing an isolated child is also isolated, with `子タスクに入力エラー`, retained GitHub dates and unknown rolled-up effort. This propagates through ancestors instead of publishing incomplete summary totals/dates or constraining successors from them. Other children and unrelated tasks still calculate normally; hierarchy and dependency cycle validation still applies to every row. A summary's own invalid refreshed values likewise isolate that summary but do not stop its children.
- Scheduling is bounded by DateOnly's supported range, with no arbitrary short horizon. Dates/settings identities are not silently repaired. Structural errors and cycles remain whole-calculation errors; ordinary refreshed row data problems do not.

## Current local plan document, operations and storage (#78 / #79 / #81)

The internal MovePlanRows primitive places exactly the selected rows, preserving their current relative order, before a specified unselected row or at the end; it does not implicitly move descendants or change parents. Invalid identities, hierarchy or dependency cycles reject the complete command.
- Undo/Redo restores exact row inputs, relationships, order and settings using before/after patches. Local edits leave the baseline unchanged. Keep at most **200 effective operations** in the combined Undo/Redo chain, dropping the oldest reachable Undo step when necessary. Persist changed rows, changed order and changed settings per step rather than 200 copies of the whole Project. Verified publication promotes created identities; published creation is a history barrier while subsequent edits remain undoable.

Closed rows reject edit, paste, fill and clear of Remaining and End atomically without document or history changes. The sheet uses the same Core read-only rule as commands and shows `完了したタスクは Issue のクローズで確定します（編集不可）` in the selection line. Summary details show a plain, non-editable Remaining value without TextBox chrome. Other fields remain editable, subject to the existing summary rule.

Every automatic/recalculated field change requires a mapped column before it counts as unpublished or enters the publish plan. This includes ordinary and summary scheduled dates, closure-adjusted Start/End and closed Remaining 0. Unmapped calculations remain visible and usable locally, but create no corner marker or write; explicit inputs still require their field mapping to publish. Closed leaf Remaining compares calculated 0 with baseline Remaining; its end compares the close date with baseline End, subject to this common mapping rule. Both differences use corner markers without PMO tint and publish through the existing field plan. Other unpublished fields compare current inputs with the baseline: title, repository, Status, Phase, assignees/predecessors as sets, parent, Estimate, Remaining, Actual, 開始日指定 and 日程固定. Start/end compare the scheduler's displayed dates with baseline dates, so mapped calculated differences count and internal typed starts superseded by automatic calculation do not create false date markers. A new row has a NewTask marker regardless of its values. Order compares positions among baseline rows, ignoring inserted local rows (inserting one task does not mark every existing task). Reordering existing rows marks every existing row whose relative position changed. The unpublished task count is the number of distinct rows with any marker, including affected summaries. Local settings alone are not GitHub fields; their changed calculated dates can create markers only for mapped columns. Closed tasks ignore stored Remaining entirely, including negative values, for validation and scheduling; effective Remaining is zero and successors use the close date. Other negative refreshed inputs remain intact under Phase 2 row-isolation rules; commands cannot introduce new negative effort. Unrelated edits do not revalidate an unchanged invalid refreshed date pair; editing start/end or the fixed flag, or changing an automatic task to kept-date semantics, must leave a valid kept pair.

### Settings file

Store column mappings for the eight planning roles (Estimate, Remaining, Actual, Start, End, StartNoEarlierThan, Fixed, Phase), each with a GitHub field ID, name and expected NUMBER/DATE/SINGLE_SELECT type. Mappings may be absent until configured; duplicate roles or reused field IDs are invalid. Known baseline column definitions remain separate from settings. Settings also hold company days off, imported holiday dates and coverage/source metadata, people (stable identity, readable name, rate and nullable nonnegative whole-Project allowance), optional Project start and end, optional phase-to-milestone title mappings, optional default repository and persisted 基準日. Bundled holidays remain a product resource, not repeated in the settings file. The ordered sheet-column choices store stable source keys, visibility and optional display names. They are portable settings, included in export/import and persisted across restart. Clearing a display name restores its default. Hiding a column retains all local values and unpublished changes.

Export writes a versioned, indented UTF-8 JSON settings file, containing no document rows, account binding or history. Import validates the entire schema and all values before replacing portable settings as one Undo step. 基準日 is not portable: import ignores the file's `statusDate` (including null) and preserves the document's current 基準日. Export may include it. Duplicate people/dates, invalid rates/allowances/repositories/mappings, malformed holiday data, unknown JSON properties and unsupported versions are rejected without any document/history change. Explicit null/default settings remain distinct. An imported person absent from baseline assignees, or a field ID absent from baseline column definitions, is retained and reported as `プロジェクトに未確認の担当者: {name}` / `プロジェクトに未確認の列: {name}`; no network lookup, silent dropping or remapping occurs. Settings have no embedded account scope and can be imported into another data root. Existing-file export replacement is atomic and explicit through the export call.

Settings files and local documents reject unknown properties, including `daysOff` on a person. No migration is provided. Before updating, publish local work; a stored plan written by an earlier version opens as [unreadable](#autosave-isolation-and-recovery) and is recovered by reading the Project from GitHub again.

### Autosave, isolation and recovery

Use `<resolved data root>/PlanningEditor/v1/`; resolve `GHPB_DATA_ROOT` as an absolute root when set, otherwise use `%LOCALAPPDATA%/GhProjectsBoards/Registrations`. Use a SHA-256 filename of host/viewer/Project and repeat that scope inside each versioned checkpoint. Never enumerate, read or migrate legacy files outside this new subfolder. Persist baseline, current inputs/settings and Undo/Redo patches together in one atomic checkpoint. No tokens, credentials, scheduler output or transient selection/scroll state are part of the schema. Immutable collections prevent later caller mutation of queued saves or history.

A committed command updates memory synchronously, then schedules autosave on a **single background writer**. Consecutive pending revisions can coalesce into the latest checkpoint, which still includes every retained Undo step. Serialization, file I/O and durable flush never run on the caller's edit path. The returned save task reports durability or failure; `FlushAsync` awaits the latest state before a normal close. An abrupt process exit before successful flush can lose the unsaved tail; never report that tail as durable. This is separate from the 0.2-second edit-to-screen target.

Reuse the existing temp-file / durable-flush / readback / File.Replace (or first File.Move) mechanism, with a last-good `.bak`. A per-Project exclusive writer lock and expected SHA-256 of the loaded/saved file prevent competing or externally changed files from being overwritten, even if a revision number was reused. Check scope, schema, current document and every reachable history state both before replacing the checkpoint and when loading. A primary file that exists but fails parsing, the current schema or validation (an earlier version's format, or damage) returns an unreadable result; transient I/O/access errors and interrupted storage return a blocked result. Neither creates a new session or modifies the file. Unknown `.tmp` candidates or a backup with no primary file are reported as interrupted storage, never silently adopted or discarded. A live writer may remove only its own failed temporary candidate so a retry remains possible.

Any failed save leaves the latest in-memory document and history intact. Transient I/O/access errors return a retryable result; explicit retry writes the latest state, not an older snapshot. Changed/corrupt source files return a non-overwrite result requiring preservation and reconciliation before retry/reopen; they cannot be bypassed by a normal save. New-session creation is permitted only after a missing-file result, and races are checked again under the writer lock. Successful writes update the expected fingerprint; older writes cannot supersede newer in-memory operations. There is no background publish.

Opening a Project whose stored plan is unreadable, including the automatic reopen when connecting, shows the work-card InfoBar **計画を開けませんでした** (`PlanOpenFailure`), not a save failure. Its message names the Project, explains that the plan stored on this PC cannot be read because it was saved by an earlier version or is damaged, states that **GitHub から読み直す** keeps the stored plan under another name and opens the Project from GitHub, and that this PC's unpublished changes are not carried over; the technical detail follows. Connecting still lists the Projects, so another Project can be chosen instead. **GitHub から読み直す** (`PlanReadAgain`) runs under the writer lock only while the stored plan is still unreadable: it renames the backup and then the primary file to `<file>.unreadable-<UTC yyyyMMddHHmmss>` (backup with a trailing `.bak`) in the same folder, never deleting or overwriting either, and opens the Project as a first open. The bar closes when another open or connection starts.

Verification adoption uses B/L/R merging for fields outside the publish, including unrelated remote updates in retained Undo history. Intended unfinished published values remain local. Newly discovered remote rows are retained consistently across every historical order, including after refresh, Undo, save and reopen. Placeholder substitution applies only to identifier input fields; title/body/text values are literal. Issue creation uses persisted start-to-start reservations and a rolling-minute bound; request time overlaps pacing waits, and server backoff is honored on resume. See the [pacing decision](decisions.md#throughput-targets-for-79).
The refresh snapshot reads the built-in Status single-select option's display name independently of optional planning-column mappings; an unavailable or unknown option is a read failure, not an empty Status. Summary-row Estimate, Remaining, Actual, assignee, predecessor, Status, Phase and constraint differences are excluded from unpublished counts as well as writes, including when an earlier effort edit becomes a summary after indenting. Hierarchy publication completes all removals before additions and then reprioritization, stopping dependent phases after a failed batch. Selected publish/live failure reasons include GitHub's error type and a bounded, single-line message with credential-like text redacted; generic transport diagnostics still omit response messages and payloads.

GitHub planning date values use Gregorian `yyyy-MM-dd` with invariant culture; numeric serialization and comparison are also culture independent. The current Windows culture must not change published values or verification.

開始日指定 and 日程固定 mappings are optional. Without a mapping, these are local scheduling constraints: refresh preserves them, they do not create unpublished field differences, and publishing still writes resulting dates through the configured Start/End fields. Adding the corresponding GitHub fields remains an explicit settings action. A parent's children are displayed in the plan's row order, which is the Project item order; the native sub-issue order never selects or sorts displayed rows, so a parent whose two GitHub orders differ displays the Project item order with no unpublished change, no review line and no reorder write. A parent has a child-order difference only when the plan's child order differs from both the baseline child order (the Project item order as read) and the native sub-issue order the plan retains; that one comparison drives the unpublished count, the review line and the relative-order write, so an affected parent counts once and an unchanged order produces no review line. The review shows that difference as the retained native order → the plan's current child order. A parent with fewer than two current children has no relative-order write; relationship additions/removals are reviewed on the affected child, and a remaining child group whose relative order did not change is not rewritten. Children the last read could not deliver keep their displayed position and are excluded from the comparison. When a native-order entry is absent, the comparison uses the baseline child order rather than inventing an empty order; refresh supplies the observed native order. A reorder whose write failed stays pending while the plan still asks for that same order, so an explicit publish retries it. Verification of a publish phase replaces failure records for the identity/field pairs that phase processed and retains unprocessed failures only while they still represent a requested, publishable change. Obsolete failures for converged values or fields excluded from summary publication do not block completion. Successful creation and Project addition preserve still-requested reorder retries for the following phase. Choosing the local side of a child-order conflict retains that order as publish intent even if refresh has advanced the Project baseline to the same order; choosing GitHub cancels that intent. The choice is durable and undoable, and reset discards it. A reorder request writes the parent's complete child order, so a child the PMO did not move takes its plan position on GitHub. On a read, a child-order difference from the baseline child order, a failed reorder still requested by the plan, or an explicitly retained local conflict choice makes a remote native reorder a concurrent divergence to resolve; a remote-only reorder is adopted into those sibling slots when the plan's child order still equals the native order read before it. The evaluation baseline includes native sibling order. Sibling order is tracked and published only for parents that are rows in the current plan; external/archived parents retain their relationship references without a sibling-order conflict. Copying an unavailable task to a new Issue resets Closed to false, CloseDate to empty and Status to empty, while retaining reproducible planning inputs. Only publishable extra values (TEXT, NUMBER, DATE and SINGLE_SELECT) are copied. Read-only, unavailable, unsupported and deleted extra values are omitted. Cached extra observations of standard-owned fields are not copied; the standard roles alone supply their publication values. Verification cannot report publish success while blocking conflicts or unavailable tasks remain, even when the unpublished task count is zero.

### Publish invariants (#79)

- **I1 — Publish outcomes are not Undo state.** History restores local inputs, settings and explicit conflict/unavailable-row dispositions only. It never stores or restores a publish attempt, dispatched/acknowledged writes, verified baseline values or GitHub identities. Title correction and its Undo/Redo may change the input of a definitely unsent/rejected creation, but never a dispatched creation's reconciliation marker or obtained identity. Once creation is observed, its identity is promoted throughout retained local history; an insertion cannot be undone into eligibility for another creation. Later edits remain undoable. Recovery reconciles the retained attempt before planning writes from the latest local inputs, without replaying verified operations. Restoring an unavailable row restores only that row's last-known content, never another row's newer baseline.
- **I2 — Nothing sent, nothing locked.** Identity, complete-read/conflict, field mapping and repository existence/archive/Issue-creation permission checks precede recording a new attempt. If an attempt stops before dispatch, its pending record and wait deadline are released. Local editing, settings correction, Undo/Redo and refresh remain usable, including after restart. Opening a checkpoint containing only Pending writes and no dispatch fact releases that never-dispatched attempt before editing. A dispatch fact survives an absent-result lookup and an incomplete Project read; Pending alone is not evidence that nothing was sent. Once a mutation may have been sent, its outcome remains durable until reconciled; settings and identity-removing operations cannot invalidate that reconciliation.
- **I3 — Relationship phases never pass through a cycle.** For hierarchy and blocked-by relationships, remove all obsolete edges across every row and batch before adding any new edge; hierarchy ordering follows additions. A failed removal stops dependent additions and ordering. The final intended graph is validated locally; remote readback establishes the resulting graph.
- **I4 — Persisted history is always replayable.** Every reachable Undo and Redo state must satisfy the document and publish invariants. Remote adoption (refresh, publish verification and identity promotion) rebases both directions and validates each reachable state before persistence. At the first invalid step, drop that step and all older/further steps in that direction; retain the valid prefix and the other direction. History cannot remove identities needed by a dispatched attempt or change its settings. Validate the serialized checkpoint with the same validation used at load before replacing the last good file.

A Project traversal with changing page totals is classified as concurrent change. Refresh, publish preflight and publish verification retry only classified concurrent change, using a fresh traversal each time: **at most three attempts, three seconds between attempts**. Other incomplete, permission, malformed-response and cancellation outcomes are not treated as churn. No non-Complete traversal is adopted into local inputs, baseline or history. Exhaustion returns a retryable message with outcome/problem classifications, never source payloads. A complete traversal is required before any subsequent mutation.

When a post-write verification read remains non-Complete, rows with dispatched/acknowledged writes are **unverified**, not verification failures. Their attempt, identities and outcomes survive restart and local Undo/Redo. Refresh can reconcile them without mutations; a later publish first reconciles them and only then derives further writes. A response alone is not complete verification, and an incomplete read cannot authorize blind resend. Creation/membership recovery completes before planning remaining fields and relationships from the latest local inputs.

## Connection and API access

- Startup is local. Manual checking detects or uses the selected gh executable, reads its version and active authentication metadata, and obtains the stable numeric viewer ID from `/user` on the explicit hostname. Authentication JSON content determines validity even when `auth status` exits with zero.
- A connection binds hostname, stable viewer ID, and gh executable. Rechecking does not adopt a different binding. Reads and writes recheck authentication and identity immediately before dispatch; mismatches permanently invalidate that context. An explicit new connection creates a new binding. Checked connection state is in memory; a saved profile does not restore authentication.
- Project URLs in the workspace chooser must be HTTPS on the selected host, with explicit repository/owner and number. Each diagnostic independently reports read access, `viewerCanUpdate`, and the relevant OAuth update scope. Absent metadata stays unknown. After a successful explicit connection, the workspace discovers the viewer and organization Projects. Opening a Project retrieves its tasks; connection never creates fields or publishes. Actual permissions and scope presence are separate; neither alone proves a later mutation will succeed.
- Only stored gh authentication is used by child processes. The four token environment variables are excluded without altering global settings. Authentication metadata is projected without the token field. Plaintext storage exposes the `hosts.yml` path and blocks writes; unknown storage blocks writes too. Reads remain available for diagnosis.
- The app never retrieves, stores, or displays credentials. Raw stdout/stderr and payloads are transient parser inputs, not logs or diagnostic output. Safe diagnostics expose outcome, HTTP status, exit code, classified error codes, and timing; remote error messages are omitted.
- REST and GraphQL use explicit host and target, `ArgumentList`, and UTF-8 JSON stdin. No shell interprets the payload. Child prompts, debug output, telemetry, and implicit gh host/repository overrides are disabled.
- The default timeout is 30 seconds per gh process, including stdin transfer. Cancelling or closing the window terminates the owned child process. Multiple commands can make the overall connection check longer than one process timeout.
- Results distinguish success, failure, cancellation, timeout, and unknown outcome, retaining available data and classified GraphQL errors. Partial GraphQL data is not complete success. Interrupted dispatched writes and potentially applied server failures are unknown; preflight failures establish that the target write was not dispatched. No automatic retry is performed.

Preflight cannot atomically lock gh authentication against changes made by another process between the identity check and API dispatch. Do not switch external gh authentication during an operation. Eliminating that race would require a different credential/session mechanism; token extraction is outside this design.

GHEC + EMU IdP/browser authentication, enterprise host behavior, organization policy, required scopes, proxy/TLS connectivity, credential-store availability, and executable restrictions remain unverified until tested in the company environment under [#92](https://github.com/fukuda-yuki/gh-projects-boards/issues/92).

## Data identity and availability

Keep Issue fields, Project item fields, and application work state distinct. Share the same Issue's body fields across Projects while retaining each Project item's own values. Missing, unreadable, unsupported, and explicitly empty values are different states. See [#6](https://github.com/fukuda-yuki/gh-projects-boards/issues/6).

### Bounded Project read contract

The Core Project reader accepts an explicitly selected Project node ID bound to the existing connection's host and stable viewer ID. It uses the guarded connection service for every page. It performs queries only, with the same identity preflight, credential isolation, per-process timeout and cancellation as other reads. PlanWorkspace owns Project discovery and navigation.

Each returned Project has a stable owner ID, node ID, number and URL. Repository and Issue identities also include the connection scope. Items retain their own node ID, content identity, archived flag and field values. Issues are indexed separately from items: two Project results refer to the same logical Issue key, while their item values remain independent. These are immutable read observations; there is no cross-result cache, automatic synchronization or draft state.

| Data | Read behavior |
| --- | --- |
| Issue title and Open/Closed state | Loaded directly from the Issue, never through a field display name |
| Project NUMBER and DATE | Exact numeric spelling and day dates, with empty/unavailable/unsupported values distinguished |
| Issue assignees, blocked-by, parent and sub-issue order | Complete paged relationships by Issue identity |
| Project single-select, including Status | Field ID, Project ownership, option IDs/names and selected option ID |
| Issue-derived or organization Issue fields exposed by a Project | Ownership and Project field identity/type retained; their projected values are unsupported |
| Other Project fields | Identity, type and known ownership retained as unsupported; unknown ownership stays unknown |
| PR / GitHub Draft | Explicit item kinds with content IDs; no ordinary Issue or local-new-row conversion |
| Redacted/null content | Unavailable content with the Project item identity retained |
| Unknown item/value types | Explicitly unsupported, retaining encountered type and available IDs |

Field names and option names are display metadata, never identity or destination selectors. Native Issue properties use their Issue identity and typed title/state properties; a same-named Project field has its own field ID. The bounded editor additionally reads dated Issue and Project viewerCanUpdate observations. Missing/denied observations do not enable editing; creation and remote updates require the explicit publish contract.

The reader traverses Project field definitions, items and every implemented item-value connection to the terminal page, including more than 100 entries. The items connection walks light pages of at most 100 item IDs with total counts and cursors. Detail requests use nodes(ids:) with at most 25 IDs and at most six concurrent sends, overlapping the walk. Details are accepted in traversal order as soon as preceding batches arrive; all reader state changes remain serial. Missing detail nodes indicate concurrent change; mismatched identities are scope errors. A stopped read starts no further requests and observes all in-flight requests before returning. It checks node/ownership identities, duplicate fields/options/items/Issues/value IDs, duplicate field assignments, repeated cursors, missing paging metadata and inconsistent total counts. On API or structural failure it stops further requests, retains already observed data and reports a classified problem. The reader itself does not retry; planning refresh and publishing apply the bounded concurrent-change snapshot retry policy.

Detail failures containing only GraphQL `NOT_FOUND` errors, each with an exact `nodes` index path pointing to a null node, are concurrent change without an API problem. Other errors retain their API failure classification. Concurrent lease responses retain the latest Retry-After deadline; a shorter deadline cannot shorten an existing wait.

Result outcomes are Complete, Partial, Failed, Cancelled and TimedOut. Cancellation/timeout can retain a partial Project. Per-connection completion flags describe traversal, not universal support or readability. A Complete result means the requested traversal completed without detected problems; it can contain explicitly unsupported fields and known unavailable items. It does not establish a transactionally consistent snapshot: GitHub does not pin successive queries to one revision, and equal-count concurrent replacements can escape count/cursor checks.

Values distinguish Present, Empty, Unsupported, Unavailable and NotLoaded. An explicit null option, or an absent supported field after a complete, error-free traversal, is Empty. On a partial read, nulls become Unavailable and absent supported fields stay NotLoaded; redacted content never implies an empty Issue or field. Unknown option IDs retain the observed ID as Unavailable. Partial GraphQL data is retained but never treated as complete. Missing or unsupported data cannot authorize clearing or deletion. The reader is query-only; publication belongs to the explicit publisher boundary.

The scheduling contract above defines the supported work/date/relationship model. Unsupported and unavailable observations remain distinct from empty values.

Schema references: [GitHub Project types](https://docs.github.com/en/graphql/reference/projects), [Project API queries and redacted items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), and [cursor pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api).

## Current planning editor refresh and publishing contract (#79)

A successful PMO refresh sets 基準日 to the read day, merges local work, and recalculates. The read is not an Undo step: rebase both sides of historical settings patches to that date, remove empty settings/operation patches, and retain unrelated edit Undo/Redo. Refresh ends any date hold and removes hold transitions from history. Publication reconciliation does not advance 基準日.

The **最新の情報に更新** split button keeps refresh as its primary action. Its menu offers **GitHub の状態に戻す…** for the whole Project; there is no per-Issue discard. Reset is available even at zero unpublished tasks. It is disabled during any remote operation or while `Sync.Publish` is non-null or `Sync.Unverified` is nonempty, with the accessible explanation **発行の結果を確認するまで使えません** for unreconciled publication. Verified failures do not block reset.

Reset uses the same complete, consistent read as refresh and sends no mutations. Failure, incomplete reads and cancellation before adoption leave the document, history, sync and 基準日 unchanged. Inside one locked transition, adopt the successful refresh (including today's 基準日 and rebased history), then record one Reset operation. That operation replaces planning inputs and ordering with the fresh GitHub values, removes local-only and unavailable rows, clears conflicts and verified failures, and holds GitHub dates with origin Reset. Local calendar, rates, allowances, people, column mappings, default repository and project start/end remain unchanged. Unavailable baseline rows are discarded through the existing reversible row-disposition patch. Undo restores the merged local work, new rows and conflicts over the fresh baseline, releases the date hold, and leaves earlier history undoable; Redo reapplies reset. Undo also restores still-requested failed child reorders as order intent, without restoring historical failure outcomes. No publication outcome is stored in Undo.

The confirmation title is **GitHub の状態に戻しますか？**, with primary **GitHub の状態に戻す**, close **キャンセル**, and Cancel as the default. It names the Project and explains that all unpublished work is discarded. Core supplies the task counts: a new task or a task with any Entered unpublished field counts as entered; all remaining unpublished tasks count as recalculated-date only. Show the total, nonzero entered/recalculated lines and new-task subset; at zero show **未発行の変更はありません。**. Explain today's 基準日, preservation of GitHub dates until the next planning edit, retained local settings and Undo recovery. The existing work-card panel shows **GitHub の状態に戻しています** and refresh read steps. Completion announces **GitHub の状態に戻しました** and uses the existing informational bar with title **GitHub の状態に戻しました（M/d H:mm）**, message **基準日を M/d (曜) にしました。日程は GitHub の値のままです。**, and no filter button. Subsequent recalculation is labelled **（GitHub の状態に戻したあとの再計算）** in publication review.

After first take-in, and after reset (#123), the persisted date hold displays every GitHub baseline Start/End exactly, including empty task and summary dates and closed-task dates. Without other local changes 未発行 is zero and no recalculated markers appear. Lateness compares those dates with 基準日 (予定より遅れ is zero); people load uses those held dates. The selection start reason is **GitHub の日付（次の編集で再計算）**, with no end reason, except that isolated rows retain **入力エラー**, their warnings and exclusion from people-load allocation while still displaying GitHub dates. The next accepted planning command (including settings/import), conflict resolution or unavailable-row resolution releases the hold and applies the scheduler, including the close-date rule. Its single Undo step restores the hold; Redo releases it. The releasing command returns a one-shot, non-persisted result with the status date and the tasks whose Start or End changed from the held GitHub dates, excluding summary rows. The workspace replaces any reset result with the existing refresh result bar, titled **日程を再計算しました**, with **基準日 X で日程を再計算しました。** and the changed-task count and **変更したタスクだけ表示** filter described above. A zero count has no filter. Undo back into the hold closes this bar and clears its filter without restoring an earlier bar; Redo does not reopen it. Reopening the app shows no notice. Only release computes the comparison; ordinary edits do not. The origin is FirstTakeIn or Reset; reset enters Reset.

Sub-issue reprioritization and Project item positioning use one mutation per serial request. Each move depends on the preceding order; retrying only failed aliases from a mixed-success batch cannot preserve that order.

Refresh accepts only a complete, Project-scoped read, including all field values, native Issue relationships and item order. Drafts, pull requests and inaccessible items are counted but never scheduled. A REDACTED item with null content is a valid complete observation; its field values are unavailable and are not traversed. It still counts as a delivered Project item. Project item traversal completes at the end of a valid cursor chain even when fewer nodes arrive than totalCount: totalCount minus delivered unique items is added to the inaccessible count, alongside delivered REDACTED items. Short or empty intermediate item pages may continue with a valid next cursor. Duplicate identities, null nodes, repeated or missing next cursors, GraphQL errors, changing totals during traversal and delivered counts above totalCount remain failures. Other field/value/relationship connections retain their strict completeness checks. The live-proof reader uses the same rule. Failed or partial reads leave the entire local checkpoint unchanged. Merge compares each field against the previous baseline: unchanged local values adopt GitHub; unchanged GitHub values preserve local work; equal changes converge; differing changes retain an explicit conflict until the user chooses a side. Resolution is one local Undo operation. Dates are recalculated after merging.

When progress changes an automatically scheduled task into in-progress or completed work, previously unused null date inputs are not date-clearing intent. Adopt the known GitHub start when an unstarted task begins or completes, while completion derives the end from the close date. Refresh uses the complete incoming snapshot; a local progress edit uses the current baseline. Preserve locally provided date inputs, date conflicts, and explicit clears made while the corresponding date was already retained. Missing GitHub dates remain missing. This adoption does not enable fixed scheduling or add a start constraint; it belongs to the same local operation or remote merge and follows its Undo/history rules.

Removed or deleted remote tasks remain visible as unavailable conflicts, retaining their local content and preventing publish. Resolution discards the unavailable task and its local relationships, or copies it to a new local task; it never recreates an Issue implicitly. Refresh replaces the baseline only after the complete merge has been saved. Unresolved conflicts survive refresh and restart. Conflicts remain stored when a task becomes a summary. Core determines publish-blocking conflicts from the current document: conflicts on the eleven non-title summary sheet fields are inapplicable while that row has children, so they are neither presented nor blocking. When the last child is outdented or removed, or hierarchy is undone, the same stored conflicts become visible and block publication again. Explicit conflict resolution still removes only the conflict being resolved; resolving a parent conflict immediately reevaluates applicability. Blocking-conflict review rows, sheet conflict indicators, publish enablement and Core publication guards use this same predicate. A disabled publish confirmation always has a visible reason on the review page. Hierarchy and order conflict contracts remain unchanged. Summary effort roll-ups never count as unpublished changes because only their start and end dates are published.

Publish reviews before/after values, calculated dates, assignees, hierarchy, dependencies, order and new tasks.

Above the review list, 「<Project title> (<owner> / プロジェクト <n>) の <N> タスクを GitHub に書き込みます」 identifies the destination and counts task groups containing writable changes in that rendered list, and is hidden when that count is zero; informational-only groups and the Project order group do not count as tasks. Each list container has an accessible name containing its task title and change lines. **発行する** is the accent action; the toolbar **発行…** loses its accent while the review is open. **閉じる（変更は保持）** returns to the plan without discarding local edits. Confirmation is disabled with a visible reason when no writable change, interrupted publication or publication failure remains, including after success. An interrupted or partly failed publication remains resumable through explicit confirmation; failure-only and unverified-only groups do not increase the writable task count. Successful publication leaves 「<N> タスクを発行しました（H:mm）」 in the review, using the reviewed task count. Closing and reopening the review retains it; the next accepted change, refresh, reset or Project switch clears it. This result is view-only and is not persisted. Partial failure retains the existing per-task failure lines and does not show a success result.

Publishing requires resolved blocking conflicts and durable storage. Its serial write phases are creation and Project addition, fields and assignees, sub-issue relationships/order, blocked-by relationships, then Project item order. Retry-After and rate-limit reset bound retries.

Bulk Project reads, plan persistence and assist inputs never include this content.

Stable text AutomationIds distinguish no selection/new-task input (**行を選ぶと、その Issue の本文とコメントを表示します**, `PlanDetailEmpty`), an unpublished local task (**GitHub にまだ作成されていないタスクです。発行すると本文を表示できます**, `PlanDetailLocal`), loading (**読み込み中…**, `PlanDetailLoading`) and failure (`PlanDetailFailureText`). A local task shows plan ID and title without a read. New selection clears the previous Issue immediately; loading appears only after the read has run for another 300 ms. The failure InfoBar title is **Issue を読み込めませんでした**, with a bounded ApiResult.FailureReason() and **再試行** (`PlanDetailRetry`). Missing/inaccessible Issues say **Issue が見つからないか、アクセスできません**. Loading and failure text are polite live regions.

Toggling, observing selection, reading, reloading, retrying and following links never commit/cancel pending cell input, alter the plan, Undo/Redo, unpublished count or autosave, or send a mutation. Only 本文を発行 writes, as described below. Focus moving into 詳細 preserves pending input even if a later focus transition precedes its lost-focus notification. Reloading the same Issue keeps its header actions enabled and keyboard focus in the pane; retrying moves focus from the disappearing retry action to reload. Planning remains usable through reads and failures. Tab reaches header buttons and the body, which supports keyboard scrolling. Tab after the body's final link returns to the first enabled header control; Shift+Tab before its first link returns to the last enabled header control. The pane cycles Tab focus within its header and body. In the native header, F6 returns to the selected sheet cell, Shift+F6 returns to the command row, and Ctrl+I closes the pane and returns to the sheet when no cell is being edited. These host shortcuts are unavailable while the WebView2 body has focus: WinUI's public WebView2 API does not expose the controller accelerator-key event or forward browser keys to XAML. Use Tab/Shift+Tab to leave the body before invoking them; scripts remain disabled. Buttons have accessible names and tooltips.

### Editing one Issue body (#216)

The PMO corrects the body of the Issue shown in 詳細 and publishes that one body with its own button. Body publishing is outside the plan document: it is not a local edit, it never enters Undo/Redo, the 未発行 count, autosave or the 発行… review, and it never commits or cancels pending cell input. There is no bulk body publish.

**本文を編集** is enabled only after a successful read of a GitHub Issue whose `viewerCanUpdate` is true. Otherwise it is disabled and explains why in its tooltip and accessible help text: 「GitHub に作成してから編集できます」 for a local task or no selection, 「読み込みが終わると編集できます」 while loading or after a failed read, and 「この Issue の本文を編集する権限がありません」 when the viewer cannot update the Issue.

Edit mode replaces the body document with a native multi-line TextBox (`PlanDetailEditor`, accessible name **Issue の本文**) holding the raw Markdown body. It wraps, scrolls vertically, accepts Enter as a new line and keeps IME composition inside the editor: confirming a conversion never triggers a command. Comments are hidden while editing. The header's third line shows **編集中** (`PlanDetailEditing`). Below the editor, **本文を発行** (`PlanDetailPublishBody`, accent) and **キャンセル** (`PlanDetailCancelEdit`) follow. Ctrl+Enter invokes 本文を発行 when it is enabled; Escape invokes キャンセル unless an IME composition is active, in which case it only ends the composition. Ctrl+Z/Ctrl+Y in the editor act on its text, not on the plan. Entering edit mode focuses the editor; leaving it returns focus to 本文を編集. F6/Shift+F6 and Ctrl+I keep their pane behavior from the editor; leaving the pane keeps the draft.

WinUI TextBox stores line breaks as `\r`. The editor's text, the draft comparison and the sent body use `\n`; text that differs from the starting text only in line endings is unchanged. A hidden plan marker (`<!-- ghpb-plan:… -->`, written when the app created the Issue) is removed from the editor text and appended unchanged after the draft, separated by a blank line (the marker alone when the draft is empty). Other HTML comments stay in the editor.

While editing, the pane stays on the edited Issue: selecting other rows does not switch it. When the sheet's selected row is a different row, a secondary line **編集を終えると、選択中のタスクを表示します** (`PlanDetailPinnedNote`) appears under the header. Leaving edit mode shows the currently selected row's Issue.

**本文を発行** is enabled only when the draft differs from the starting text, no publish of this body is running and no remote work (open, 最新の情報に更新, reset to GitHub, 発行) is running. Publishing never shows a confirmation dialog; the conflict check protects concurrent edits. While it runs, the editor is read-only, both buttons are disabled and **本文を発行しています…** (`PlanDetailPublishing`, polite live region) is shown. Publishing one body:

1. Re-reads the Issue's current body and viewerCanUpdate by node ID. If that body already equals the body to send (ignoring line endings), the publish is complete without a write; this resolves an earlier attempt whose outcome was unknown. If it differs from the body the edit started from, nothing is written: an InfoBar (`PlanDetailConflict`) titled **編集を始めた後に、GitHub で本文が変更されました** offers **上書きして発行** (`PlanDetailOverwrite`) and **GitHub の本文に戻す** (`PlanDetailRevert`). The draft stays until the PMO chooses. 上書きして発行 adopts the body just read as the new starting body and publishes again (another change arriving meanwhile conflicts again). GitHub の本文に戻す discards the draft without a further prompt, leaves edit mode and reads the Issue again.
2. Checks the bound gh identity as other writes do, then sends exactly one `updateIssue(input: {id, body})`. Nothing else on the Issue changes.
3. Verifies that the returned body equals the sent body (ignoring line endings). On success it leaves edit mode, replaces the Issue's cache entry with a fresh read (new bodyHTML and comments) and shows **本文を発行しました（H:mm）** (`PlanDetailPublished`) in place of 最終更新 in the header's third line until the pane shows another Issue or reloads.
4. On failure (including a failed readback), an InfoBar (`PlanDetailPublishFailure`) titled **本文を発行できませんでした** shows a bounded failure reason and **再試行** (`PlanDetailPublishRetry`), which runs the same publish again from step 1. The draft stays. Losing update permission fails with **この Issue の本文を編集する権限がありません**.

Body publishing uses the authenticated connection gate. Detail-read cancellation does not apply to it: once started, it runs to its readback so the outcome is known. Remote work started meanwhile waits for the gate. 最新の情報に更新, reset to GitHub and plan publication keep the draft and clear only read results; the edited Issue's cache entry is replaced after its own publish.

Discarding: キャンセル, Escape, closing the pane with either toggle or Ctrl+I, opening アシスト (which closes 詳細), opening or switching a Project (including 接続…) and closing the app check the draft. With changed text a dialog (`PlanDetailDiscard`) titled **本文の変更を破棄しますか？** offers **破棄** and **編集に戻る** (default). 編集に戻る cancels the triggering action, keeps the pane open with the draft and focuses the editor. Unchanged text leaves edit mode silently. A running body publish finishes before the check. Switching to サマリー or settings hides the pane with its draft, which returns on 計画. Drafts are kept only in memory for the app session and never reach assist, plan storage or logs.
