# Specification

The [requirements](requirements.md) and [decisions](decisions.md) define the planning editor. The ordinary window exposes the workspace, Project settings, an editable native plan sheet with a row-aligned Gantt, a people view for load and forecasts, and explicit refresh and publish review.

## Pending-input invariant (all editing views)

The plan sheet and people view obey the same invariant: **pending input is never hidden or dropped**. A row or cell containing uncommitted, composing or invalid input remains in the visible, focusable presentation until committed or explicitly discarded. Filters, recalculation, drill-down membership, period/zoom changes and redraws cannot remove it. Pending rows remain alongside the normal filtered/period results; they stop being retained when their last pending cell resolves. This retention changes presentation only, never the schedule, totals or assignment.

There is always a way out. Escape in an editor discards only that cell's pending input and restores its current committed display value, clears its validation error and creates no Undo entry. IME conversion Escape belongs to the IME first. Invalid input has an error callout anchored next to its cell. Commands requiring resolved input (navigation, Undo/Redo, Project switching and close) either proceed after resolution or refuse and focus/scroll to the problem cell; they cannot leave the only correction path outside the view. Focus-loss validation may report an error without stealing focus from another edit.

Validation feedback follows task identity and field, not a recycled control instance. When scrolling unloads or rebinds its row, the callout closes or moves to a currently realized editor for that same problem. Scrolling back or a refused command makes the retained error reachable again; another task must never inherit its message.

After a refused or failed operation, toggles, pickers and selectors are synchronized with the current document (or accepted presentation setting), including an in-memory change accepted before a persistence failure. Restoring a control is not another edit. Each view owns its controls and pending inputs; this invariant does not introduce a second document or shared editing framework.

## CSV import of new tasks (#82)

**CSVから追加** in the sheet toolbar opens the native `.csv` picker. Import adds new local tasks to the selected Project only; it never updates existing tasks or writes to GitHub. File selection, validation and duplicate confirmation precede one atomic `InsertPlanRows` operation with kind `CsvImport`. Its rows and any newly resolved people are one Undo step. A successful import clears the title filter and selects the first imported task so the result is reachable. Imported Estimate also initializes Remaining; Actual remains empty. The existing scheduler calculates dates and parent roll-ups, retaining unknown dates for unassigned or incomplete work. Only **発行** creates Issues and publishes their relationships.

The template is [templates/new-tasks.csv](../templates/new-tasks.csv), copied to `templates/new-tasks.csv` in the app output. It is UTF-8 with BOM for Excel. Input accepts strict UTF-8 with or without BOM, then strict Windows-932 (Shift-JIS) if UTF-8 decoding fails, using the framework code-page provider. Files are at most 5 MiB and 10,000 data records. Quoted commas, doubled quotes and quoted line breaks are supported. Error line numbers are physical file lines, including the header; a multiline record is identified by its first line.

| Header | Value |
| --- | --- |
| キー | Required unique, case-sensitive file-local key; no `#`, semicolon or control characters. Numeric keys are allowed. |
| タイトル | Required nonblank task title. |
| 見積 | Required column; empty means unknown, otherwise a nonnegative decimal number of person-hours using `.` as the decimal separator. |
| 担当者 | Optional; GitHub login, or semicolon-separated logins; empty is unassigned. |
| 先行タスク | Optional; semicolon-separated file keys or existing Issue references. |
| 親 | Optional; one file key or existing Issue reference. |
| 開始日指定 | Optional; `yyyy-MM-dd` or `yyyy/M/d`, empty for none. |
| リポジトリ | Optional `owner/repository`; empty uses the current default repository. |

Columns may be reordered. Unknown or duplicate headers and missing required columns are errors. File keys resolve first; `#123` (or a bare number without a matching key) refers to Issue 123 in that row's repository. `owner/repository#123` disambiguates repositories. Existing references must identify an Issue already loaded in this Project. Keys are not sent to GitHub or stored as task identity; each import creates fresh local identities.

Core checks all records before accepting any rows: syntax, duplicate keys, missing titles, invalid numbers/dates, unresolved keys/Issues, repositories and assignable logins, and hierarchy/dependency cycles including existing tasks and inherited summary dependencies. Repository existence and Issue-creation capability and required assignable-user identities are read through the active scoped connection; incomplete reads cannot authorize an import. New people start at 100% rate with no allowance or personal days off; existing resource settings are preserved. Validation uses the same scheduling rules as ordinary editing. Errors appear in a bounded list of **line number + short reason**, with **CSVを選び直す** as the next action. Cancellation changes nothing.

Duplicate detection uses SHA-256 of the original file bytes, retained as local provenance on each imported row. If any current row has that hash, the UI requires **重複して追加** confirmation before adding another copy. It survives save/reopen, identity promotion on publish and refresh; Undo removes it with the imported rows. Changed bytes, including a changed encoding, are a different file; this is an exact-repeat warning, not semantic deduplication. Provenance is excluded from GitHub fields and unpublished markers.

CSV preparation belongs to the workspace operation queue. Pending edits are resolved before the picker opens; closing cancels its owned repository reads and dismisses validation/duplicate dialogs without adding rows.

Publication resolves each new row's repository separately. Every destination must pass preflight before the first dispatch; creation and uncertain-creation reconciliation use that same repository, while batch sizes, pacing and #79 stage order remain unchanged.

The [sandbox evaluation file](evaluation/sandbox-plan.csv) contains a small plan for Project 3, uses only `fukuda-yuki` or no assignee, and targets `fukuda-yuki/codex-sandbox`. Importing it is local preparation; publishing it remains an explicit ordinary-app action.

## Current people view (#80)

**担当者** shows only the selected Project. Each configured or currently assigned person has one row; 担当者なし and 担当者が複数 collect ambiguous assignments once, without duplicating their effort across people. Summary tasks are excluded from effort totals. Actual belongs to the current assignment. Columns are rate, whole-Project allowance (person-hours), Estimate, Actual, Remaining, forecast (Actual + Remaining), and difference (allowance − forecast). The assignment groups have no rate, allowance or difference; all three show 「—」. For a person, an empty allowance still makes the difference 「未入力」. An over-allowance difference includes 超過 in both its visible text and accessible name; the difference column shows a four-digit overrun with this warning without trimming. Empty Actual counts as zero in people totals without changing the stored task input, so forecasts work before work starts. Missing Remaining makes Remaining and forecast unknown, and also difference for a person, and is named 残が未入力. Other missing values propagate only to their corresponding totals; an empty group has known zero effort. Allowance is editable here, stored in Project settings, and is one Undo operation.

The period grid uses calendar days, Monday–Sunday weeks, or calendar months. Capacity is eight working hours × rate, excluding weekends, bundled/imported holidays, company days off and personal days off. Automatic task load uses the scheduler's daily remaining-work allocation, including partial days and FS endpoints; it does not independently reschedule tasks. Fixed tasks distribute Remaining across working days in their inclusive fixed period. Completed tasks contribute no future load. Missing Remaining, missing dates, invalid input or a fixed period with no working day are named as unallocated work, never fabricated zero load. Ambiguous assignment groups have no capacity or percentage. A positive load above capacity has both semantic warning color and 超過 text; zero capacity never produces a fabricated percentage. Period totals sum hours and capacity before dividing. Full weeks/months are used, including across year boundaries.

Week and month cells retain the period average and also expose the number of overloaded days and the maximum daily load percentage, so an average at or below 100% cannot hide a known daily overload. These measures use the same daily allocation and capacity as day view. Positive load on a zero-capacity day remains an overload without a fabricated percentage; missing or unallocated work remains visibly identified and cannot become a zero or a claim of no overload. The existing period drill-down identifies the overload dates and contributing tasks and keeps their correction path available; after an assignee or planning-input change, daily warnings and aggregate measures recalculate together without automatic leveling.

The [pending-input invariant](#pending-input-invariant-all-editing-views) applies to all people editors. Committing a cell preserves queued commits and the focused cell without prematurely committing the next edit. A drill-down retains tasks with pending input even after their Remaining becomes zero or their schedule leaves the selected period. Recalculation retains the current period, expansion and scroll position.

Expanding a person shows the contributing tasks for the selected period, plus unallocated tasks with their reason. Assignee is a choice of the Project people plus 担当者なし. An existing multiple assignment is displayed intact until an explicit selection replaces it; multiple selection remains available from the sheet. Task Assignee, Remaining, Actual and 日程固定 use the same Core cell commands and one-step Undo as the sheet. Recalculation never levels load or reassigns tasks. Period navigation, zoom and expansion are local presentation state. Twenty collapsed person rows plus the two assignment groups fit a 1280×720 logical client area in day, week and month views. Daily-overload text shares the same row; only period columns needing that text widen, without increasing every row height. Required columns remain reachable by horizontal scrolling; task details may require vertical scrolling. Invalid input remains editable and blocks navigation until corrected.

## Current publish workspace (#79)

The review includes native sub-issue order changes before → after, including non-conflicting changes. Relationships outside the plan use a retrieved repository/Issue number when available; otherwise they are labelled as unretrieved external Issues and offer a link to the source Issue's GitHub relationships. They never use the Project caption.

The PMO reviews the changes in the open Project before explicitly confirming publication. **発行** opens a review in the workspace with one group per Issue: readable task title and plan ID, retrieved repository/Issue number when available, and its changed fields with before → after values together. Short field differences share a wrapped line rather than repeating the task identity for every field. Full values wrap within the available width and remain readable without expanding each difference. New Issues are labelled 新規 Issue. Field names use the sheet's column labels; dates show `yyyy/M/d (曜)` so before, after and GitHub values keep their year (#109). Empty values are 未入力; assignees and relationships use readable names or plan IDs. Conflict lines show local and GitHub values with explicit choices beside their Issue's differences. Resolving a conflict saves a local operation; it does not send writes, and the review retains the affected Issue or its nearest remaining neighbour in view. Unavailable rows offer discard or copy to a new Issue. Confirmation is disabled while unresolved conflicts or unavailable rows remain.

Version-scale review uses a bounded, virtualized native list. Ordinary short values remain visible together as readable Issue/task identity, field and before → after, without expanding every difference. Supplementary full-text access preserves the user's place. Virtualization must not omit differences or reset conflict choices when rows leave the viewport; every difference and recovery action remains reachable by scrolling and keyboard, while confirmation remains outside the scrolling list.

Opening or closing the review never writes. Confirmation invokes the existing publisher, including its identity and conflict read. A conflict discovered by that read returns to review without sending mutations. Changes arriving after review therefore require another explicit confirmation. The review can close during publication and reopen on the same operation; progress remains visible in the workspace. Stages are 新規 Issue, フィールド・担当者, 親子関係, 先行タスク, 表示順 and 検証. There are no invented percentages. During remote work the current plan is read-only; scrolling and closing the review remain available. Project switching and settings changes wait until the operation finishes. Closing the window cancels the owned operation and waits for its durable interruption result. Restart never publishes automatically; 最新の情報に更新 reconciles known outcomes, and explicit 発行 resumes remaining work.

The sheet marks conflicted cells 競合 with a critical outline and corner marker but no tinted background, because a critical tint means overdue work. The selection line names the GitHub value. The choice between values is made in the publication review. Failed or unverified rows carry the indicator column's failure marker and expose their reason in the selection line and accessibility text. Successful refresh/publish refreshes markers and the distinct unpublished task count. A failed complete-read attempt retains the plan and shows a retry action. Failed saves expose 保存を再試行 only on failure. Undo remains a local operation after publication and can produce new unpublished changes.

## Current workspace and Project settings (#81 / #109)

The ordinary window opens the planning workspace with the shell in [DESIGN.md](../DESIGN.md#visual-language). The app is light regardless of the Windows app mode; High Contrast uses system colors. The title bar's Project picker shows the open Project's title and lists registered Projects for the authenticated host/viewer; selecting a Project opens it in one action. Registered Project titles occupy their own line; owner and number are secondary metadata. The list scrolls inside the picker, while **Project を開く…** and **接続…** remain reachable below it. Settings opens from the title bar's gear button and returns to the previous view. Below the title bar, the view tabs 計画 and 担当者 mark the current view; the 状況日 picker, **元に戻す**, **やり直し**, 未発行 N (distinct tasks), **最新の情報に更新** and **発行…** sit on the right. Undo and Redo appear only there and apply to the open Project's operation history from every view. The title bar shows the three-bar Gantt app icon, and the settings gear sits immediately left of the caption buttons. Caption buttons use the system caption colors, so they are legible in the active window. The borderless Project picker, settings gear, **元に戻す** and **やり直し** use hover fill. Thin vertical separators divide the command row's right side into 状況日, Undo/Redo, and the unpublished count with the GitHub commands. The open Project is checked in the picker's list. The status-date picker displays `yyyy/MM/dd (曜)`. Positive unpublished counts appear as a caution badge followed by 未発行のタスク; zero remains 未発行 0 タスク. A status bar shows digit-grouped counts of requirements (rows with children) and tasks (rows without children), followed by the overdue and later-than-published task counts when they are not zero (`期限超過 2 · 予定より遅れ 20`). In the plan view it ends with a right-aligned legend for actual work, remaining work, lateness against publication and non-working days; other views show no Gantt legend. During 最新の情報に更新 or 発行, a thin indeterminate progress bar runs below the command row and the running command reads 更新中… or 発行中…. A failed refresh, publication or save appears as an InfoBar at the top of the work card. It states the affected work and offers its retry action. Connecting through gh lists the viewer's and organizations' Projects together. A Project URL is an alternative in the Project chooser. First open reads the whole Project and automatically matches the seven planning fields by exact name (case insensitive) and required type; ambiguous matches remain unassigned. Start date and Target date are the default date names. No remote field is created implicitly. The explicit scheduling-fields button uses the guarded Core operation to create missing 開始日指定 (DATE) and 日程固定 (SINGLE_SELECT, 固定) and map them.

The workspace task area is the editable plan sheet and row-aligned Gantt defined below. Drafts, pull requests and inaccessible items are excluded and counted in settings (参照できない項目).

On the first opening of a Project, the workspace reads the complete paged assignable-user catalog for every repository represented by its Issues before saving or adopting the document. Unassigned Issues can therefore receive a GitHub login directly in the sheet without CSV import or prior assignment. Catalog identities and readable logins are retained as metadata and initialize people at 100% with no allowance; intake changes no task input, creates no Undo operation and sends no remote writes. Issue-creation permission is not required to obtain assignees for existing Issues. A failed, incomplete or identity-mismatched catalog read leaves the previously selected Project intact and creates no partial checkpoint. Reopening a saved document preserves local work without rereading the catalog.

One Project settings page contains column mappings, weekdays 09:00–13:00 / 14:00–18:00, the bundled Japanese holidays (2025–2027), holiday CSV import, company days off, assignee rates and personal days off, optional Project start, default repository, and settings export/import. Rates default to 100%; whole-Project allowances are entered in the people view. If all fetched Issues belong to one repository, it is selected by default; otherwise the repository remains unset. Refreshed assignee display names are retained separately from local rates, so a newly assigned person appears with a readable identity and a default 100% rate. Each accepted control change or file import is one settings operation and one Undo step; invalid input leaves the accepted settings unchanged. Rejected selection/rate controls return to the accepted value; invalid date text stays editable and blocks navigation until corrected. The optional Project start uses yyyy-MM-dd. Company and personal days off use native calendar selection with explicit Add and per-date Remove actions. Dates are unique and sorted; adding an existing date changes nothing. Selecting a date alone does not change settings. Each addition or removal recalculates and is one Undo step. Recalculation uses the real scheduler immediately. Mapping changes apply to the next whole-Project refresh; they never silently discard unpublished values.

Commands received during a pending settings save are serialized: commit pending input, then execute each requested command in order. Project selection, view-tab selections and buttons must not silently lose requests. While view changes are queued, the tabs retain the latest requested selection; they return to the actual page after a rejected switch or when the queue settles. Refresh rebuilds settings from the refreshed people and baseline column definitions, preserving the current page.

The workspace catalog merges registrations with the latest validated catalog under an exclusive writer lock; a stale instance cannot remove another instance's registrations. The selected Project is the last successfully saved selection. The new workspace catalog is stored atomically under PlanningEditor/v1, with registrations scoped by host/viewer/Project. Each Project document and its Undo history remain in the Phase 3 store. Switching retains the in-memory session and restarting restores the saved document before a refresh is requested. Connection is checked again after restart; cached identity never counts as authentication. Failed saves retain the session and expose retry. Save retry first retries persistence without reapplying pending controls, then commits any still-pending input; it must remain usable after storage recovers. A Project switch is adopted only after its catalog save succeeds; failed selection keeps the prior Project, settings controls and selected entry together. Closing cancels the UI-owned gh operation, waits for owned processes to stop, commits the focused text or rate input and flushes durable work, and remains open if saving fails. A failed close permits subsequent commands with a fresh cancellation scope. Cancellation never accepts an incomplete read as an empty Project. Old data files are never read or migrated.

## Current plan sheet and row-aligned Gantt (#78 / #109)

The Project planning surface is one editable sheet beside a row-aligned native Gantt on the workspace card. Both share one virtualized vertical viewport and a sticky header. Sheet and chart have independent horizontal scrolling. Selecting or navigating to an offscreen column brings the whole cell into the sheet viewport without moving the chart. When the window is at least 1,280 effective pixels wide, the default divider position shows the ten default columns, ID through 先行, without horizontal scrolling; the Gantt takes the remaining width. The PMO's ordinary display is 1920 × 1080 at 100% scaling. There, a maximized window gives the Gantt about 1,040 effective pixels, about 18 weeks at 週, beside about 29 rows. In narrower windows the default divider leaves the Gantt at least 320 effective pixels and the sheet scrolls horizontally; no columns are frozen. A draggable, keyboard-adjustable divider changes their relative widths. Rows are 28 effective pixels; larger text scaling may increase that size. The task-name column is wide enough for a requirement title such as 「R05 顧客データの外部連携」 at the default width. Long values remain accessible through cell editing and horizontal scrolling. No Gantt drag editing is available.

The sheet's command bar shows each primary command with its icon and label, grouped by purpose: tasks (行を挿入, インデント, アウトデント, 先行タスクを追加…) and overview (すべて折りたたむ, すべて展開, 選択タスクの日程へ移動). Its overflow holds the clipboard commands with their shortcuts (コピー Ctrl+C, 貼り付け Ctrl+V, 下へコピー Ctrl+D, クリア Delete), CSV から追加 and 表示列. The Gantt scale and the title filter, with a search icon, sit at its right end; the 状況日 picker is in the shell's command row because it applies to the whole Project. When the window is narrow, commands move to the native overflow rather than disappearing.

### Columns and presentation

Columns, in order, are ID, an indicator column, タスク名, 担当者, 見積 h, 残 h, 実績 h, 開始日, 終了日, 先行, 開始日指定, 日程固定 and ステータス. Headers use these standard labels; a GitHub-backed header's tooltip and accessible description name the mapped GitHub field, or 未設定. The first ten columns are visible by default; 開始日指定, 日程固定 and ステータス are available through 表示列. Column visibility is a view setting, not an Undo operation. ID is the task's one-based position in the complete plan, independent of filtering or folding. Predecessors are entered/displayed as those IDs. Filtering by title affects presentation only. A task name that does not fit ends with an ellipsis, and its tooltip shows the full name. Each hierarchy level indents the name, so a child's name starts to the right of its parent's name text, never to the left. 担当者 shows the display name, or the GitHub login when no display name is known. Several assignees show the first followed by ` +N`; a task without an assignee leaves the cell blank.

With no title filter, a parent row can fold or expand its descendants; **すべて折りたたむ** and **すべて展開** provide the whole-version overview and detail. Folding is local presentation state keyed by task identity, initially expanded, and changes no hierarchy, order, schedule, unpublished count or Undo history. A filter temporarily ignores folding and keeps the existing flat list of matching tasks: ancestor-only context rows are not inserted into range-edit targets. Clearing the filter restores the prior folded state. If folding or clearing a filter hides the selected task, selection moves to its nearest visible ancestor. Folding returns cell focus to that ancestor; editing the title filter retains keyboard focus in the filter. Ctrl+Left/Right on a non-editing parent title cell folds/expands that parent. Folding and filter changes first resolve pending valid input and are rejected during composition or invalid input, retaining the accepted view and reachable editor. Sheet rows and Gantt rows always use the same visible identities.

The indicator column's header is an icon with the accessible name インジケーター. Each row shows its most important state as one icon, in this order: failed or unverified publication, overdue (filled critical warning), later than published (outlined critical warning), completed (Remaining 0 with positive Actual), typed start or fixed dates, unpublished change. Its tooltip and accessible name list every state that applies; rows with none show nothing.

Lateness has two levels, after MS Project's Late and Slipping tasks. The published start and end are GitHub's dates as of the last refresh or publication; publishing new dates replaces them. Neither level is a comparison with an agreed plan (#93).

- **Overdue (期限超過)**: an incomplete task whose published end is before the 状況日, or a task with no Actual whose published start is before the 状況日. A published date on the 状況日 itself is not overdue. The tooltip reads 「期限超過: 完了予定 11/10 を過ぎて未完了（残 16h）」 or 「期限超過: 開始予定 11/9 を過ぎて未着手」. The finish tooltip uses scheduled Remaining, falling back to input Remaining and then Estimate. If none is known, it omits the entire remaining-work parenthetical.
- **Later than published (予定より遅れ)**: a task that is not overdue but whose calculated end is after its published end, usually because a predecessor moved. The tooltip reads 「予定より遅れ: 発行済み 12/1 から +2 日」.

A summary row shows the filled warning when any descendant task is overdue. Otherwise it shows the outlined warning when it or a descendant is later than published, including when its own end has not moved. Its tooltip counts them, for example 「配下に期限超過 1、予定より遅れ 17」, omitting zero counts. An overdue row whose own end also moved lists both the missed date and the later-than-published difference. Folding never hides these markers.

Assignee display prefers the configured person's name, then the retrieved GitHub login. Its tooltip lists all assignees; editing and copying retain the full accepted input form rather than the shortened display. A title's ellipsis is presentation only: editing, copying and its automation value retain the complete title.

Calculated dates and summary effort use secondary text; typed and retained values use primary text, without italics. Requirement (summary) rows are semibold. Dates display as `M/d (曜)`, for example `10/14 (水)`; the tooltip and accessible name give `yyyy-MM-dd (曜)`. F2 or double-click shows the edit form `yyyy-MM-dd`; that edit form is the original value for the editing contract, so entering the same date creates no edit. Date input accepts `yyyy-MM-dd`, `yyyy/M/d` and `M/d`; `M/d` takes the year that puts the date nearest the 状況日 (today when unset); a tie chooses the later date. Other text is rejected with 「日付は 2026-10-14、2026/10/14 または 10/14 の形で入力してください。」. Sheet cell editors omit the clear button so the complete ISO edit form fits the 92-pixel date column. Unpublished cells carry a corner marker and an accessible annotation until verified publishing clears their differences. A value the PMO entered also has a tinted background. A start or end date that differs only through recalculation has the corner marker without the tint. Summary effort never receives an unpublished marker. An overdue row's end date uses critical text when its calculated end is later than its published end. A row that is only later than published keeps the ordinary date colors. The selected row has the selection background and a short accent bar at the left of its ID cell. A fixed 36-effective-pixel selection line sits directly above the header, without an idle feedback spacer. With no task selected, it reads 「タスクを選ぶと、開始と終了の理由がここに出ます」 in secondary text. Nonzero overdue and later-than-published counts appear at its right. The command row places labelled task/overview commands and their overflow at the left, with scale and title filter at the right, separated from the selection line by a thin card stroke. The selection line has a very light semantic background and a bottom stroke, including when empty. It shows the selected task's plan ID and title, the scheduler's single-line start reason (開始: prefix for start constraints, predecessor plan IDs without #; summary and state reasons retain their labels), and the end reason. The end reason is 「終了: 状況日 11/11 から残り 16h」 for started work, 「終了: 開始から 40h」 for unstarted work and 「終了: 指定」 for a typed or fixed end; complete tasks and summaries omit it. The lateness pill follows the reasons. Lateness counts Project working days in (published end, calculated end]: weekends, bundled/imported holidays and company days off are excluded, but personal days off are not.

- An overdue task shows a critical tinted pill naming the missed date: 「完了予定 11/10 を過ぎて未完了」 or 「開始予定 11/9 を過ぎて未着手」. When its calculated end is also later than its published end, the pill adds the difference: 「完了予定 11/10 を過ぎて未完了 · +2 日」.
- A later-than-published task shows an outlined critical pill, 「発行済み 12/1 から +2 日」. When its calculated start is also later than its published start and its start reason is a predecessor, secondary text 「先行の遅れによる」 follows.
- A summary shows 「配下: 期限超過 1 · 予定より遅れ 17」 in secondary text. When its own end is later, its pill is tinted if it has the filled marker and outlined otherwise.

The right-aligned Issue reference ends the line. Row warnings and rejected input remain attached to their row/cell; dependency-cycle rejection names the plan IDs and changes nothing.

### Editing and range operations

Pointer range hit-testing accounts for every visible leading non-field column, including ID and the indicator, so range commands affect only the indicated fields. A selected cell is distinct from an active text edit. Typing or F2 begins editing; Escape cancels. Enter commits and moves down, Tab commits and moves right (wrapping at the last visible column). IME conversion confirmation does not commit or navigate; the following Enter does. Focus loss commits a valid edit; invalid text remains available for correction. Navigation, Undo/Redo, remote refresh and close first finish pending valid input, and reject while composition or invalid input remains. A rejected Undo/Redo keeps the invalid cell visible and editable. Returning text to its original value replaces intermediate pending input and creates no edit history. The original value is the edit form when the edit began (ISO for dates, including calculated dates); returning to it must not store a date or enable fixed scheduling. Compare the original form before parsing input so display-only predecessor text such as 計画外 also cancels without blocking close or Project switching. Every completed edit exit (Enter/Tab, Escape, focus loss or navigation) restores the display form after editing ends, including an unchanged F2/double-click edit. Programmatic switches between display and edit forms create no pending user input, including reentrant or later text notifications. A successful queued commit also ends the initiating edit when no pending input remains for that cell. Pending invalid or newer input remains visible, and IME confirmation still does not end the edit. Leaving an unchanged edit restores cell selection behavior on return. A title filter is applied only after pending input validates; rejection restores the accepted filter and keeps the invalid cell reachable.

Numeric predecessor entry remains available. **先行タスクを追加…** searches the complete open Project by requirement context, task title or readable Issue reference, independently of the sheet's filter and folding. Candidates show requirement context, title, plan ID and the retrieved repository/Issue number when available. Selecting a candidate adds its stable identity to the task for which the chooser was opened, preserving all existing predecessors, including out-of-Project references. An accepted addition is one existing cell operation and one Undo step; selecting an already-present predecessor or cancelling changes nothing. The chooser keeps the search input, a usable independently scrolling candidate list, and both confirmation/cancellation controls together inside the client area. Opening the chooser resolves pending input under the same invariant. Existing dependency validation rejects an invalid addition without changing the plan; searching makes no GitHub request.

Shift+click/Shift+arrows and pointer drag select a rectangle. Copy uses tab/newline-separated values in their edit form (dates as `yyyy-MM-dd`) plus scoped typed metadata for internal copies. ## Current planning editor scheduling contract (#78)

This section is the current contract for the new UI-independent `PlanEditor` model.

### Inputs, identity and calendar

- A task has an opaque Issue/local identity, a positive unique plan-row ID, optional parent identity and predecessor identities. Row IDs are supplied by plan order, never recomputed by filtering. External predecessors retain their reference, do not constrain dates and produce `プロジェクト外の先行タスク: {reference}`. References outside the Project have no plan-row ID. Missing parents are external hierarchy boundaries, with `プロジェクト外の親タスク`; they do not create summary rows.
- Inputs retain Estimate, Remaining, Actual, assignees, closed state, 開始日指定, 日程固定, current start/end and GitHub baseline start/end separately. Effort inputs are nullable decimal person-hours; valid effort is nonnegative. Missing effort is not zero. Negative refreshed effort or inverted kept dates isolate that row as described below; nonpositive/duplicate row IDs, duplicate/empty identities and invalid settings still reject the calculation without changing inputs.
- Working time is Monday–Friday 09:00–13:00 and 14:00–18:00, excluding bundled Japanese holidays 2025–2027, additional dates from the existing validated holiday CSV importer, company days off and (only for a single assignee) personal days off. Imported dates supplement the bundle. Beyond the supplied holiday years, weekdays still apply and affected rows warn `祝日データの対象年外`.
- A single person's rate defaults to 100%; allowed rates are greater than 0 and at most 100%. Capacity is 8 hours times rate per day, spread uniformly across both work intervals (50% means 4 person-hours over an eight-hour day). No assignee or multiple assignees use the Project calendar at 100%; multiple assignees warn `担当者が複数`. No resource leveling occurs.
- 状況日 is an optional explicit choice. Every calculation receives the caller's today and uses the explicit date when present, otherwise that supplied today. Clearing the choice restores this daily default; Core never reads the clock. The local document stores the optional choice, not its resolved default. Project start is optional. Day inputs become 09:00 boundaries. Internal working-hour endpoints use exact rational arithmetic derived from decimal effort and rate, only during recalculation, never in returned date cells or persisted inputs. No rounding to minutes or tolerance may move an endpoint across a work-interval/day boundary; successors inherit the exact endpoint, also across differing rates. A 4-hour task at 100% finishes at 13:00; its successor starts at 14:00 that day. At 18:00 a positive-work successor starts on its next working day. Kept start/end dates represent 09:00/18:00 even on nonworking days.

### Scheduling precedence and edits

Before these rules, isolate invalid row data as described below.

1. Summary rows roll up children as below, overriding their valid own scheduling inputs.
2. Closed tasks are complete. Open tasks with Remaining = 0 are complete only when Estimate > 0 or Actual > 0. They retain current GitHub/locally typed dates, reason `完了`; a missing end warns `完了タスクの終了日なし` and imposes no successor constraint. An open task with Estimate and Remaining each absent or zero (at least one zero), and Actual absent or zero, is a milestone. Thus typing Estimate = 0 on a new row (which also fills Remaining = 0) creates a milestone, while finishing planned or performed work creates a completed task. 日程固定 still keeps explicitly fixed milestone dates.
3. 日程固定 retains current typed dates, reason `日程固定`. Missing either date warns `日程固定の日付不足`. A start earlier than any effective predecessor finish warns `先行タスクより前に開始`; dates do not move.
4. Both Estimate and Remaining absent retain dates, reason `工数なし`.
5. Otherwise work is Remaining, falling back to Estimate. Earliest start is the maximum of 状況日, optional Project start, 開始日指定 and effective predecessor finishes. Normalize positive-work starts to the assignee's next working interval. An unfixed zero-work milestone has identical start/end at the earliest boundary's day without calendar normalization (including an 18:00 predecessor endpoint); its reason names that winning constraint just as for positive-work tasks. An unfixed open task with Actual > 0, Estimate = 0 and Remaining absent is neither a milestone nor explicitly complete: isolate it with `残が未入力` until Remaining is supplied.
6. Actual > 0 and positive work retains the existing start cell; remaining work begins at max(状況日, retained start), normalized to working time. Its end uses Remaining (Estimate fallback if Remaining is absent). Dependencies, Project start and 開始日指定 do not move an existing actual start; predecessor violation warns as above. Missing start uses the ordinary earliest start, calculates both dates and warns `進行中タスクの開始日なし`. This preserves recorded history while never placing remaining work before 状況日.
7. Other positive-work tasks calculate both dates from earliest start and work/rate. Calendar adjustment does not replace the start reason.

Entering a nonempty Estimate fills Remaining only when Remaining is absent; subsequent Estimate edits leave Remaining unchanged. Clearing Estimate does not clear Remaining. Typing/clearing a start updates both the current start input and 開始日指定; typing a nonempty end updates the end and enables 日程固定, while clearing an end does not silently disable the flag. These pure input transformations are composed by the local document commands below. Estimate, Remaining and Actual edits reject a negative new value; start/end edits reject an inverted resulting pair when dates are kept. An automatic start edit may move past an old GitHub end because its end is recalculated; typing an end enables 日程固定 and validates the resulting pair. Rejection throws a validation error and returns no replacement task, leaving the original input intact. A valid correction to one field is allowed while another refreshed field still needs correction.

Each date cell exposes its day value, `Calculated` or `Kept` origin and a boolean difference from the corresponding GitHub baseline (including null transitions). In-progress start is Kept, end is Calculated. Valid summary cells are Calculated; isolated summaries keep their GitHub dates. Unchanged calculated values are not unpublished changes. Inputs are never overwritten by a calculation.

### Hierarchy, dependencies and reasons

- A row with in-Project children is a summary. Each effort column sums direct children recursively; if any child's value is absent the total remains absent (never turn missing into zero). Check all children for absence before addition, so an unknown total never overflows merely because of child order. Start is the minimum available child start, end the maximum available child end; all absent yields absent. Its own valid effort/date/constraint/closed inputs remain intact but are ignored for summary scheduling; invalid data follows the isolation rule below. Removing its last child restores ordinary task semantics. Publishing writes rolled-up start/end but **not** rolled-up effort; no publish implementation is implied here.
- A predecessor link to a summary waits for its rolled-up internal end. A summary's predecessors constrain every descendant, including nested summaries. Completed/fixed/no-effort descendants still retain dates; fixed and in-progress violations warn. Parent 開始日指定 is not inherited. Duplicate predecessor references have no extra effect.
- Reject parent hierarchy cycles, dependency cycles (also those induced by summary roll-up/inheritance), self-links and any predecessor link between ancestor and descendant. Errors identify the involved plan-row IDs as `循環参照: #1, #2`. Reject the whole calculation, with no partial result or input mutation. Unrelated descendants of a cycle are not named as cycle members.
- Exact start reasons: `状況日`, `プロジェクト開始日`, `開始日指定 M/d`, `#{row ID} の終了後`, `開始日を維持`, `完了`, `日程固定`, `工数なし`, `子タスクの集計`, `入力エラー`. Dates use invariant M/d. For equal constraints, predecessor wins, then 開始日指定, Project start, 状況日; tied predecessors use the smallest plan-row ID. In-progress with a retained start uses `開始日を維持`; a missing start uses the winning earliest-start reason. A valid summary uses `子タスクの集計`; isolated rows use `入力エラー`.
- Warnings are per row, unique strings. Refreshed negative effort warns `工数が負の値`; an inverted kept start/end pair warns `開始日が終了日より後`. An unrepresentable calculated schedule warns `日程が日付の範囲外`; effort-total overflow warns `工数の集計が範囲外`. The affected row retains its GitHub baseline dates with Kept origin and reason `入力エラー`; inputs (including invalid values) remain available for correction, and no date change is proposed. Neither date is used as a dependency or summary endpoint. Invalid leaf effort is displayed as received, never included in summary totals.
- A summary containing an isolated child is also isolated, with `子タスクに入力エラー`, retained GitHub dates and unknown rolled-up effort. This propagates through ancestors instead of publishing incomplete summary totals/dates or constraining successors from them. Other children and unrelated tasks still calculate normally; hierarchy and dependency cycle validation still applies to every row. A summary's own invalid refreshed values likewise isolate that summary but do not stop its children.
- Scheduling is bounded by DateOnly's supported range, with no arbitrary short horizon. Dates/settings identities are not silently repaired. Structural errors and cycles remain whole-calculation errors; ordinary refreshed row data problems do not.

## Current local plan document, operations and storage (#78 / #79 / #81)

This section defines UI-independent local commands. Refresh, verified Issue creation, conflict resolution and publishing extend it under the current #79 contract below; ordinary local commands never contact GitHub.

### Document and atomic operations

A document belongs to one normalized host, stable numeric GitHub viewer ID and Project node ID. Its immutable baseline holds the last retrieved Issue rows in Project order and the known mapped column identities/names. Each row retains identity, title, repository, Status option identity, closed state, assignees, predecessors, parent, Estimate/Remaining/Actual, start/end, 開始日指定 and 日程固定. CSV rows also retain the original-file SHA-256 as local provenance. Current rows and settings are separate from that baseline; no edit changes it. New rows use `local:<GUID>` identities until publication verifies an Issue identity. Order is the row sequence; displayed IDs are its one-based positions, never affected by filtering.

Each command builds and validates a complete candidate before replacing current state. Cell edit, rectangular paste, fill/Ctrl+D, Delete-clear, inserting one/many rows, indent/outdent, moving rows and settings replacement each create exactly one Undo step. A rejected command changes neither state, history nor the pending save. A no-op creates no history and does not discard Redo. A new effective command clears Redo. Recalculation uses the Phase 2 scheduler and caller-supplied today; calculated dates and reasons are never document inputs.

- Edits use typed Core values (text, decimal hours, DateOnly, boolean, identity lists or null), not locale-dependent string parsing. Estimate/Remaining/Actual/start/end pass through the Phase 2 transformations. Paste validates all cells and applies them in supplied order to a candidate (validate kept date pairs only after all cells, so a valid two-date paste can move both endpoints); an explicit Remaining cell therefore follows an Estimate cell when both are pasted. Fill/Ctrl+D snapshots the source inputs once and expands to the same atomic cell operation. Paste/fill never creates rows. Duplicate target cells in one operation are rejected. Clear uses null, empty identity lists or false according to the field; title becomes empty. Summary effort, date and constraint cells are derived and cannot be edited directly; edit their children instead.
- Insert accepts prepared local rows, defaulting an empty repository from settings; an explicit or default `owner/repository` is required. `PlanCsvImport` submits its fully validated rows and newly resolved people through this same one-step bulk insert. Undo removes imported rows and people; Redo restores their exact identities, relationships and file provenance. Closed state is a retained GitHub input, not an Issue-administration command.
- Indent applies to selected consecutive siblings and reparents them under the preceding sibling. Outdent reparents selected siblings to their parent's parent; a missing/external parent cannot be outdented. Both preserve the explicit row order. Move places exactly the selected rows, preserving their current relative order, before a specified unselected row or at the end; it does not implicitly move descendants or change parents. Invalid identities, hierarchy or dependency cycles reject the complete command.
- Undo/Redo restores exact row inputs, relationships, order and settings using before/after patches. Local edits leave the baseline unchanged. Keep at most **200 effective operations** in the combined Undo/Redo chain, dropping the oldest reachable Undo step when necessary. Persist changed rows, changed order and changed settings per step rather than 200 copies of the whole Project. Verified publication promotes created identities; published creation is a history barrier while subsequent edits remain undoable.

Unpublished fields compare current inputs with the baseline: title, repository, Status, assignees/predecessors as sets, parent, Estimate, Remaining, Actual, 開始日指定 and 日程固定. Start/end compare the scheduler's displayed dates with baseline dates, so calculated differences count and internal typed starts superseded by automatic calculation do not create false date markers. A new row has a NewTask marker regardless of its values. Order compares positions among baseline rows, ignoring inserted local rows (inserting one task does not mark every existing task). Reordering existing rows marks every existing row whose relative position changed. The unpublished task count is the number of distinct rows with any marker, including affected summaries. Local settings alone are not GitHub fields; their changed calculated dates can create markers. Negative refreshed inputs remain intact under Phase 2 row-isolation rules; commands cannot introduce new negative effort. Unrelated edits do not revalidate an unchanged invalid refreshed date pair; editing start/end or the fixed flag, or changing an automatic task to kept-date semantics, must leave a valid kept pair.

### Settings file

Store column mappings for the seven planning roles (Estimate, Remaining, Actual, Start, End, StartNoEarlierThan, Fixed), each with a GitHub field ID, name and expected NUMBER/DATE/SINGLE_SELECT type. Mappings may be absent until configured; duplicate roles or reused field IDs are invalid. Known baseline column definitions remain separate from settings. Settings also hold company days off, imported holiday dates and coverage/source metadata, people (stable identity, readable name, rate, personal days off and nullable nonnegative whole-Project allowance), optional Project start, optional default repository and optional explicit 状況日. Bundled holidays remain a product resource, not repeated in the settings file. No UI layout or column visibility is stored in this phase.

Export writes a versioned, indented UTF-8 JSON settings file, containing no document rows, account binding or history. Import validates the entire schema and all values before replacing settings as one Undo step. Duplicate people/dates, invalid rates/allowances/repositories/mappings, malformed holiday data, unknown JSON properties and unsupported versions are rejected without any document/history change. Explicit null/default settings remain distinct. An imported person absent from baseline assignees, or a field ID absent from baseline column definitions, is retained and reported as `プロジェクトに未確認の担当者: {name}` / `プロジェクトに未確認の列: {name}`; no network lookup, silent dropping or remapping occurs. Settings have no embedded account scope and can be imported into another data root. Existing-file export replacement is atomic and explicit through the export call.

### Autosave, isolation and recovery

Use `<resolved data root>/PlanningEditor/v1/`; resolve `GHPB_DATA_ROOT` as an absolute root when set, otherwise use `%LOCALAPPDATA%/GhProjectsBoards/Registrations`. Use a SHA-256 filename of host/viewer/Project and repeat that scope inside each versioned checkpoint. Never enumerate, read or migrate legacy files outside this new subfolder. Persist baseline, current inputs/settings and Undo/Redo patches together in one atomic checkpoint. No tokens, credentials, scheduler output or UI state are part of the schema. Immutable collections prevent later caller mutation of queued saves or history.

A committed command updates memory synchronously, then schedules autosave on a **single background writer**. Consecutive pending revisions can coalesce into the latest checkpoint, which still includes every retained Undo step. Serialization, file I/O and durable flush never run on the caller's edit path. The returned save task reports durability or failure; `FlushAsync` awaits the latest state before a normal close. An abrupt process exit before successful flush can lose the unsaved tail; never report that tail as durable. This is separate from the 0.2-second edit-to-screen target.

Reuse the existing temp-file / durable-flush / readback / File.Replace (or first File.Move) mechanism, with a last-good `.bak`. A per-Project exclusive writer lock and expected SHA-256 of the loaded/saved file prevent competing or externally changed files from being overwritten, even if a revision number was reused. Check scope, schema, current document and every reachable history state both before replacing the checkpoint and when loading; malformed or unreadable data returns a blocked result without creating a new session or modifying the file. Unknown `.tmp` candidates or a backup with no primary file are reported as interrupted storage, never silently adopted or discarded. A live writer may remove only its own failed temporary candidate so a retry remains possible.

Any failed save leaves the latest in-memory document and history intact. Transient I/O/access errors return a retryable result; explicit retry writes the latest state, not an older snapshot. Changed/corrupt source files return a non-overwrite result requiring preservation and reconciliation before retry/reopen; they cannot be bypassed by a normal save. New-session creation is permitted only after a missing-file result, and races are checked again under the writer lock. Successful writes update the expected fingerprint; older writes cannot supersede newer in-memory operations. This phase introduces no recovery dialog or background publish.

Verification adoption uses B/L/R merging for fields outside the publish, including unrelated remote updates in retained Undo history. Intended unfinished published values remain local. Newly discovered remote rows are retained consistently across every historical order, including after refresh, Undo, save and reopen. Placeholder substitution applies only to identifier input fields; title/body/text values are literal. Issue creation uses persisted start-to-start reservations and a rolling-minute bound; request time overlaps pacing waits, and server backoff is honored on resume. See the [pacing decision](decisions.md#throughput-targets-for-79).
The refresh snapshot reads the built-in Status single-select option's display name independently of optional planning-column mappings; an unavailable or unknown option is a read failure, not an empty Status. Summary-row Estimate, Remaining and Actual differences are excluded from unpublished counts as well as writes, including when an earlier effort edit becomes a summary after indenting. Hierarchy publication completes all removals before additions and then reprioritization, stopping dependent phases after a failed batch. Selected publish/live failure reasons include GitHub's error type and a bounded, single-line message with credential-like text redacted; generic transport diagnostics still omit response messages and payloads.

GitHub planning date values use Gregorian `yyyy-MM-dd` with invariant culture; numeric serialization and comparison are also culture independent. The current Windows culture must not change published values or verification.

開始日指定 and 日程固定 mappings are optional. Without a mapping, these are local scheduling constraints: refresh preserves them, they do not create unpublished field differences, and publishing still writes resulting dates through the configured Start/End fields. Adding the corresponding GitHub fields remains an explicit settings action. Sibling-order differences use the same comparison for unpublished counts and review: an affected parent counts once, and an unchanged order produces no review line. A parent with fewer than two current children has no relative-order write; relationship additions/removals are reviewed on the affected child. When a native-order entry is absent, the comparison uses the baseline child order rather than inventing an empty order; refresh supplies the observed native order. The evaluation baseline includes native sibling order. Sibling order is tracked and published only for parents that are rows in the current plan; external/archived parents retain their relationship references without a sibling-order conflict. Copying an unavailable task to a new Issue resets Closed to false and Status to empty, while retaining reproducible planning inputs. Verification cannot report publish success while conflicts or unavailable tasks remain, even when the unpublished task count is zero.

### Publish invariants (#79)

- **I1 — Publish outcomes are not Undo state.** History restores local inputs, settings and explicit conflict/unavailable-row dispositions only. It never stores or restores a publish attempt, dispatched/acknowledged writes, verified baseline values or GitHub identities. Title correction and its Undo/Redo may change the input of a definitely unsent/rejected creation, but never a dispatched creation's reconciliation marker or obtained identity. Once creation is observed, its identity is promoted throughout retained local history; an insertion cannot be undone into eligibility for another creation. Later edits remain undoable. Recovery reconciles the retained attempt before planning writes from the latest local inputs, without replaying verified operations. Restoring an unavailable row restores only that row's last-known content, never another row's newer baseline.
- **I2 — Nothing sent, nothing locked.** Identity, complete-read/conflict, field mapping and repository existence/archive/Issue-creation permission checks precede recording a new attempt. If an attempt stops before dispatch, its pending record and wait deadline are released. Local editing, settings correction, Undo/Redo and refresh remain usable, including after restart. Opening a checkpoint containing only Pending writes and no dispatch fact releases that never-dispatched attempt before editing. A dispatch fact survives an absent-result lookup and an incomplete Project read; Pending alone is not evidence that nothing was sent. Once a mutation may have been sent, its outcome remains durable until reconciled; settings and identity-removing operations cannot invalidate that reconciliation.
- **I3 — Relationship phases never pass through a cycle.** For hierarchy and blocked-by relationships, remove all obsolete edges across every row and batch before adding any new edge; hierarchy ordering follows additions. A failed removal stops dependent additions and ordering. The final intended graph is validated locally; remote readback establishes the resulting graph.
- **I4 — Persisted history is always replayable.** Every reachable Undo and Redo state must satisfy the document and publish invariants. Remote adoption (refresh, publish verification and identity promotion) rebases both directions and validates each reachable state before persistence. At the first invalid step, drop that step and all older/further steps in that direction; retain the valid prefix and the other direction. History cannot remove identities needed by a dispatched attempt or change its settings. Validate the serialized checkpoint with the same validation used at load before replacing the last good file.

A Project traversal with changing page totals is classified as concurrent change. Refresh, publish preflight and publish verification retry only classified concurrent change, using a fresh traversal each time: **at most three attempts, three seconds between attempts**. Other incomplete, permission, malformed-response and cancellation outcomes are not treated as churn. No non-Complete traversal is adopted into local inputs, baseline or history. Exhaustion returns a retryable message with outcome/problem classifications, never source payloads. A complete traversal is required before any subsequent mutation.

When a post-write verification read remains non-Complete, rows with dispatched/acknowledged writes are **unverified**, not verification failures. Their attempt, identities and outcomes survive restart and local Undo/Redo. Refresh can reconcile them without mutations; a later publish first reconciles them and only then derives further writes. A response alone is not complete verification, and an incomplete read cannot authorize blind resend. Creation/membership recovery completes before planning remaining fields and relationships from the latest local inputs.

Checked connection state is in memory; a saved profile does not restore authentication.
- Project URLs in the workspace chooser must be HTTPS on the selected host, with explicit repository/owner and number. Each diagnostic independently reports read access, `viewerCanUpdate`, and the relevant OAuth update scope. Absent metadata stays unknown. After a successful explicit connection, the workspace discovers the viewer and organization Projects. Opening a Project retrieves its tasks; connection never creates fields or publishes. Actual permissions and scope presence are separate; neither alone proves a later mutation will succeed.
- Only stored gh authentication is used by child processes. The four token environment variables are excluded without altering global settings. Authentication metadata is projected without the token field. Plaintext storage exposes the `hosts.yml` path and blocks writes; unknown storage blocks writes too. Reads remain available for diagnosis.
- The app never retrieves, stores, or displays credentials. Raw stdout/stderr and payloads are transient parser inputs, not logs or diagnostic output. Safe diagnostics expose outcome, HTTP status, exit code, classified error codes, and timing; remote error messages are omitted.
- REST and GraphQL use explicit host and target, `ArgumentList`, and UTF-8 JSON stdin. No shell interprets the payload. Child prompts, debug output, telemetry, and implicit gh host/repository overrides are disabled.
- The default timeout is 30 seconds per gh process, including stdin transfer. Cancelling or closing the window terminates the owned child process. Multiple commands can make the overall connection check longer than one process timeout.
- Results distinguish success, failure, cancellation, timeout, and unknown outcome, retaining available data and classified GraphQL errors. Partial GraphQL data is not complete success. Interrupted dispatched writes and potentially applied server failures are unknown; preflight failures establish that the target write was not dispatched. No automatic retry is performed.

Preflight cannot atomically lock gh authentication against changes made by another process between the identity check and API dispatch. Do not switch external gh authentication during an operation. Eliminating that race would require a different credential/session mechanism; token extraction is outside this design.

GHEC + EMU IdP/browser authentication, enterprise host behavior, organization policy, required scopes, proxy/TLS connectivity, credential-store availability, and executable restrictions remain unverified until tested in the company environment under [#92](https://github.com/fukuda-yuki/gh-projects-boards/issues/92).

## Data identity and availability

Keep Issue fields, Project item fields, and application work state distinct. Share the same Issue's body fields across Projects while retaining each Project item's own values. Missing, unreadable, unsupported, and explicitly empty values are different states. See [#6](https://github.com/fukuda-yuki/gh-projects-boards/issues/6).

### Bounded Project read contract

The Core Project reader accepts an explicitly selected Project node ID bound to the existing connection's host and stable viewer ID. It uses the guarded connection service for every page. It performs queries only, with the same identity preflight, credential isolation, per-process timeout and cancellation as other reads. PlanWorkspace owns Project discovery and navigation.

Each returned Project has a stable owner ID, node ID, number and URL. Repository and Issue identities also include the connection scope. Items retain their own node ID, content identity, archived flag and field values. Issues are indexed separately from items: two Project results refer to the same logical Issue key, while their item values remain independent. These are immutable read observations; there is no cross-result cache, automatic synchronization or draft state.

| Data | Read behavior |
| --- | --- |
| Issue title and Open/Closed state | Loaded directly from the Issue, never through a field display name |
| Project NUMBER and DATE | Exact numeric spelling and day dates, with empty/unavailable/unsupported values distinguished |
| Issue assignees, blocked-by, parent and sub-issue order | Complete paged relationships by Issue identity |
| Project single-select, including Status | Field ID, Project ownership, option IDs/names and selected option ID |
| Issue-derived or organization Issue fields exposed by a Project | Ownership and Project field identity/type retained; their projected values are unsupported |
| Other Project fields | Identity, type and known ownership retained as unsupported; unknown ownership stays unknown |
| PR / GitHub Draft | Explicit item kinds with content IDs; no ordinary Issue or local-new-row conversion |
| Redacted/null content | Unavailable content with the Project item identity retained |
| Unknown item/value types | Explicitly unsupported, retaining encountered type and available IDs |

Field names and option names are display metadata, never identity or destination selectors. Native Issue properties use their Issue identity and typed title/state properties; a same-named Project field has its own field ID. The bounded editor additionally reads dated Issue and Project viewerCanUpdate observations. Missing/denied observations do not enable editing; creation and remote updates require the explicit publish contract.

The reader traverses Project field definitions, items and every implemented item-value connection to the terminal page, including more than 100 entries. It checks node/ownership identities, duplicate fields/options/items/Issues/value IDs, duplicate field assignments, repeated cursors, missing paging metadata and inconsistent total counts. On API or structural failure it stops further requests, retains already observed data and reports a classified problem. No automatic retry occurs.

Result outcomes are Complete, Partial, Failed, Cancelled and TimedOut. Cancellation/timeout can retain a partial Project. Per-connection completion flags describe traversal, not universal support or readability. A Complete result means the requested traversal completed without detected problems; it can contain explicitly unsupported fields and known unavailable items. It does not establish a transactionally consistent snapshot: GitHub does not pin successive queries to one revision, and equal-count concurrent replacements can escape count/cursor checks.

Values distinguish Present, Empty, Unsupported, Unavailable and NotLoaded. An explicit null option, or an absent supported field after a complete, error-free traversal, is Empty. On a partial read, nulls become Unavailable and absent supported fields stay NotLoaded; redacted content never implies an empty Issue or field. Unknown option IDs retain the observed ID as Unavailable. Partial GraphQL data is retained but never treated as complete. Missing or unsupported data cannot authorize clearing or deletion. The reader is query-only; publication belongs to the explicit publisher boundary.

The scheduling contract above defines the supported work/date/relationship model. Unsupported and unavailable observations remain distinct from empty values.

Schema references: [GitHub Project types](https://docs.github.com/en/graphql/reference/projects), [Project API queries and redacted items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), and [cursor pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api).

## Current planning editor refresh and publishing contract (#79)

Sub-issue reprioritization and Project item positioning use one mutation per serial request. Each move depends on the preceding order; retrying only failed aliases from a mixed-success batch cannot preserve that order.

Refresh accepts only a complete, Project-scoped read, including all field values, native Issue relationships and item order. Drafts, pull requests and inaccessible items are counted but never scheduled. A REDACTED item with null content is a valid complete observation; its field values are unavailable and are not traversed. It still counts as a delivered Project item. Project item traversal completes at the end of a valid cursor chain even when fewer nodes arrive than totalCount: totalCount minus delivered unique items is added to the inaccessible count, alongside delivered REDACTED items. Short or empty intermediate item pages may continue with a valid next cursor. Duplicate identities, null nodes, repeated or missing next cursors, GraphQL errors, changing totals during traversal and delivered counts above totalCount remain failures. Other field/value/relationship connections retain their strict completeness checks. The live-proof reader uses the same rule. Failed or partial reads leave the entire local checkpoint unchanged. Merge compares each field against the previous baseline: unchanged local values adopt GitHub; unchanged GitHub values preserve local work; equal changes converge; differing changes retain an explicit conflict until the user chooses a side. Resolution is one local Undo operation. Dates are recalculated after merging.

When progress changes an automatically scheduled task into in-progress or completed work, previously unused null date inputs are not date-clearing intent. Adopt the known GitHub start when an unstarted task begins or completes, and the known GitHub end when automatic work completes. Refresh uses the complete incoming snapshot; a local progress edit uses the current baseline. Preserve locally provided date inputs, date conflicts, and explicit clears made while the corresponding date was already retained. Missing GitHub dates remain missing. This adoption does not enable fixed scheduling or add a start constraint; it belongs to the same local operation or remote merge and follows its Undo/history rules.

Removed or deleted remote tasks remain visible as unavailable conflicts, retaining their local content and preventing publish. Resolution discards the unavailable task and its local relationships, or copies it to a new local task; it never recreates an Issue implicitly. Refresh replaces the baseline only after the complete merge has been saved. Unresolved conflicts survive refresh and restart. Summary effort roll-ups never count as unpublished changes because only their start and end dates are published.

Publish reviews before/after values, calculated dates, assignees, hierarchy, dependencies, order and new tasks. It requires resolved conflicts and durable storage. Its serial write phases are creation and Project addition, fields and assignees, sub-issue relationships/order, blocked-by relationships, then Project item order. NUMBER/DATE-only field requests use at most 50 aliases; contiguous numeric/date prefixes can retain that capacity even when the same field phase also contains assignee or other values. Short mixed prefixes use at most 10 without reordering writes. Other mixed field/assignee and relationship addition/removal requests start at 10, and Issue creation and Project addition use at most 10 each. Resource-limit failures split unsuccessful aliases into half-sized serial requests down to one; successful aliases are retained, and later requests in that phase use the reduced ceiling for the current attempt. A failed operation blocks its dependents, not independent later phases. Actual request sizes remain available as execution evidence. The ordinary app can append publish duration, creation wait and actual mutation batch sizes to the local file specified by `GHPB_PUBLISH_METRICS`; this opt-in diagnostic contains no request payloads or credentials. Identity preflight and a complete conflict read precede writes. Creation/membership is verified and adopted before planning remaining fields/relationships, followed by their complete verification read; each traversal follows the bounded concurrent-change retry policy. Successful aliases are retained even when siblings fail. An exact already-present Project addition is reconciled by Issue identity; resource-limit failures remain distinct. Retry-After and rate-limit reset bound retries.

Every newly created Issue receives an explicit Project-add request. Auto-add membership cannot mark a never-dispatched addition complete, including after creation-response loss or restart; that addition stays pending until explicit publish sends it. An Auto-add collision is resolved by reading its existing item. Membership verification retries at most four reads with one-second cancellable delays; a verified creation without confirmed membership remains resumable without recreating the Issue. Partial membership does not prevent attempts to add the other created Issues. Once memberships are confirmed, publishing continues with fields, assignees, hierarchy and dependencies. Saved incomplete creation progress follows the same recovery path.

Publish failures display a bounded GitHub message or a short Japanese explanation, including `Project への追加を確認できません` for unconfirmed membership. New-Issue review lines show the proposed value without a fictitious empty previous value. The add-scheduling-fields command is omitted when both matching fields exist. CSV repository not-found/no-access responses are line-level validation failures; transport failures remain operation errors.

When a newly created Issue is adopted after membership confirmation, unset local fields adopt observed GitHub values, including Project workflow defaults. Explicit local values remain the publishing intent.

An unresolved mutation outcome stops all later mutation requests in the current publish attempt after its result is saved. Missing aliases, a missing response or an unclassified global GraphQL error are unresolved, not ordinary alias rejections. Already acknowledged aliases remain recorded; unsent writes stay pending, and refresh or explicit publish reconciles uncertain writes before any further dispatch. The interruption explains that GitHub's response could not be confirmed and asks the user to refresh before publishing again. Persist any Retry-After/reset deadline before stopping; a deadline is not proof of an outcome or its cause. Explicit RESOURCE_LIMITS_EXCEEDED outcomes retain their bounded split recovery and creation-marker guard, but a mixed response containing any other unresolved outcome stops before splitting. Known rejected aliases may still allow independent work under the preceding rule.

Status is the Project-owned SINGLE_SELECT field named `Status`. Publication resolves the entered option name to its current option ID and writes it in the fields-and-assignees phase; clearing uses clearProjectV2ItemFieldValue. Unknown names or unavailable fields stop before dispatch. Review and verification include Status, with the same local Undo and three-way merge rules as other fields.

Before dispatch, durable progress records the immutable desired operation and a unique creation marker. Uncertain creation is reconciled by that marker before another create is allowed; incomplete lookup cannot authorize retry. Verified successes are not resent. Never-dispatched operations remain pending with a readable not-sent reason; the sheet and review label these as 未送信 rather than 発行失敗. Verification mismatch applies only to an operation sent and read back differently; those differences remain for the next publish. Closing or losing the network preserves reasons, created identities and pending work. Undo after publish changes only the local plan; published Issue creation cannot be undone. Authentication remains entirely in gh, without token access or storage.

The explicit settings operation creates missing DATE `開始日指定` and SINGLE_SELECT `日程固定` (option `固定`) and maps their returned identities. Refresh and publish never create fields implicitly. Live validation is opt-in, confined to the approved sandbox, and records three complete samples for each #79 workload with independent owned-resource cleanup and baseline verification. Core timings do not establish UI ceilings.

During an active remote operation, editing is blocked. Between attempts, local cell edits and their Undo/Redo may proceed without changing recorded outcomes; settings or history operations that would remove an identity involved in unresolved publication remain blocked until reconciliation. Resume reconciles outcomes first. A complete verification releases ordinary failed field changes back to editing, retaining their reasons separately; their differences are rebuilt on the next publish. Choosing GitHub for a conflict cancels only that pending field write. Refresh reconciles an unfinished publish without dispatching its remaining writes. Field-setup requests are explicit settings operations; reusing an existing correctly typed named field avoids duplicates on retry.

Refresh preserves inserted-row anchors, rebases reachable Undo operations against external changes and clears Redo. Known rejected creations may have their titles corrected while successful sibling identities remain frozen. Once those Issues are published, insertion and pre-creation title correction cannot be undone. New tasks receive explicit Project positions after creation/add so auto-add timing does not change the reviewed order.
