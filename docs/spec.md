# Specification

This document records agreed behavior from [Epic #1](https://github.com/fukuda-yuki/gh-projects-boards/issues/1). Acceptance and remaining scope belong to the owning Issues.

## Workspace presentation

Source: #31, with the functional contracts below. Ordinary startup opens the local workspace. The user explicitly selects a saved account and Project; this neither authenticates the account nor starts communication. The compact common area shows host, account, connection state and connection settings. The Project header shows its title, cached retrieval time, independent **最新を取得**, **GitHubに反映…** and **反映結果・履歴**. These Apply commands remain together when narrow layout reflows them. The default destination for new rows is available in Project settings and never changes existing row destinations. A cache timestamp does not claim that GitHub is current.

The collapsible navigation pane groups Projects through their owner/repository associations without filtering Project contents. Routine draft saves preserve expanded/collapsed branches and visible keyboard focus. Collapsing an ancestor can clear the native tree's hidden selection without closing the active Project. Initial window sizing respects the display scale and available desktop work area. Narrow windows use overlay navigation and reflow Project commands, while the cache caption uses the width below the title and commands.

Frequent editing operations use the native command bar and its overflow. The table fills the remaining workspace, with aligned cell boundaries, row numbers and a column header that stays visible during vertical scrolling and follows horizontal data scrolling. Compact markers identify local changes, pending input, conflicts and unavailable values. The optional bottom details pane exposes the selected cell's effective value, pending text, identity, validation and available B/L/R observations; it does not create a second editor or transaction.

The row number, title and compact repository/Issue identity remain visible beside later columns. One vertical viewport aligns them with their fields. Its scrollbar and wheel use the system line/page amount without committing, redirecting pending input or changing a select value; Shift+wheel moves horizontally. Single-select cells center their value, revealing the arrow mainly on hover, selection or focus. Arrow/Tab/Enter navigation follows the input contract below.

F6 and Shift+F6 move between the table, any currently visible reapplication command and selected-details command. These transitions preserve pending text and defer during native composition. After settings close, focus returns to the visible active cell or an available view/details command when the active cell became hidden.

Project settings contain information, exact identities, retrieval completeness, destination settings, target-access diagnostics and local unregister. Execution history is reached directly from the Apply command group. The compact table footer reports the field/range in rows and cells, Project-local unreflected cells, pending input and local saving separately. It surfaces conflicts, failed saves and work hidden by the view; irrelevant zero diagnostics are omitted. Full status remains keyboard accessible from settings and, when no Project is selected or attention is required, the workspace status area. Partial retrieval stays separately labelled as an unaccepted observation. Ordinary 1280×720 logical client layout with details closed reserves at least 70% of its height for the table; 960×600 uses collapsed navigation and command overflow. Approval, durable dispatch and recovery retain their safety contracts.

Row and column definitions are persisted under their scoped contracts. Pane visibility, viewport position and active selection are transient UI state, not restored profile settings.

## Project row views

Source: #5/#7, with #8 durability. Each host/account/Project owns one local row definition: source order, ordinal case-insensitive Title order, or one supported Project single-select ordered by its current option definitions. Both directions put present values first, followed by Empty, local Unspecified, and Unknown; equal values use stable row identity. Title filtering is a literal ordinal case-insensitive substring. Option IDs and explicit states are ORed within each field; fields and Title are ANDed. Duplicate names never resolve identities. A committed local clear is intended Empty, not evidence of remote emptiness. Pending text is excluded; local committed intent takes precedence over accepted observation and conflict/availability markers remain available.

The transient row projection composes with column mapping and never replaces canonical rows, placement records or complete snapshots. Open/switch, explicit Save/Reapply and accepted explicit refresh evaluate it. Edits and save/journal notifications preserve its arrangement. Reapplication is indicated only when a field used by the active sort or filter, or another projection input, changes; unrelated edits in unfiltered source order do not request reapplication. Explicit new rows, duplication and append remain temporarily visible at the end until reapplication. Promotion uses durable identity mapping and retains position. Composition defers reapplication without committing text. Membership/order changes clear the old rectangle and retain only a visible active identity; hidden buffers survive. Clipboard work captures displayed row/cell keys and generation before awaiting, and rejects changed mappings. Undo uses original keys, including hidden rows, without changing view preferences.

When removal Undo restores a local row whose identity was absent from the current projection, notably after reopening while the row was removed, that row becomes temporarily visible at the end. A removed row whose identity remains in the projection resumes its previous view position. Previously hidden rows stay hidden and existing displayed rows keep their order. Restored identities, values, buffers and canonical placement are preserved; the temporary display does not change row or column preferences. Explicit Reapply removes the temporary exception and evaluates the restored rows against the saved criteria, so a nonmatching restored row can become hidden again without losing work.

Apply starts with displayed-row candidates and no approved selection. Total candidates, displayed candidates and selected rows retain distinct scopes; this does not require separate, always-visible counters. One candidate/selection summary describes the current scope without conflating those counts. Hidden changes, when present, distinguish exclusion, explicit candidate inclusion and selection; inclusion alone never selects them. Summarizing or omitting a count never changes candidate membership or selection. Pre-Apply complete refresh re-evaluates visibility and requires new selection when membership changes. Newly visible rows are not automatically selected, and newly hidden defaults are not silently retained. Selected rows still review all applicable changed fields, including hidden columns. Approved payloads remain frozen across later view changes, and recovery/history remain reachable regardless of row visibility.

Local Save/Cancel/Reset changes the definition; Reset leaves columns intact. Checkpoint v7 adds definitions to the latest coherent profile candidate and migrates v1–6 with default row order and no filters, preserving column preferences and all work/history. Transient projection/selection/counts are not saved. Save failure preserves the accepted view and candidate. Stale candidates, missing options and incompatible fields require repair or reset; criteria keep their IDs and are never silently removed to broaden the view. Invalid saved criteria expose an empty projection with a repair/reset explanation while preserving the complete underlying dataset. Partial retrieval never replaces accepted definitions or preferences.

## Existing-field Apply

Source: #10 and the #8/#9 existing-field contracts. Only existing Issue titles and Project-owned single-select values (including explicit clear) are supported. Creation and Project addition follow the separate #11 contract below. Draft conversion, Issue state, other field types, all-Project execution and remote Undo are outside this slice.

Apply defaults to the selected Project. **GitHubに反映…** opens one **反映内容の確認** screen containing changed existing rows and local creation work, explicit initially empty selection, automatic latest-state checking and differences. Unchanged existing Issues are omitted; incomplete/unresolved work is labelled with reasons. The app saves local work, retrieves a complete Project observation and reconciles it on opening and selection changes. There is no separate manual reconciliation step or prerequisite refresh button. Adding hidden candidates and selecting them are separate explicit decisions. Selected-row hidden-column changes remain visible in review.

Confirmation uses one selectable Issue comparison table, including unselected candidates, with columns identified by field ID. Repository groups preserve the editing view's order within each group and retain their context while scrolling. Common headings explain **GitHubの値 → 反映する値**, Issue-shared attributes and Project fields; duplicate names retain identifiers. The header's three-state selection control selects all from partial/none and clears all from all. Updated Issues, creations, selected rows and field changes are distinct count units, not a checklist of counters to display. Any count shown must make its unit and scope clear; visibility follows the information policy below. The candidate/selected summary and final button agree on confirmed effective Issue counts; a difference is explained, creation/update breakdown appears only when creations exist, and an unfinished check is never reported as zero. Only the main list scrolls vertically; headings, problem summary and final actions stay available. Narrow or enlarged text layouts label fields within each row instead of reducing text size.

Choose information by whether it changes the user's current decision or next action: **always visible** for target identity, selection, differences and final actions; **conditional** for actual problems, hidden work, creation breakdown and excluded pending input; **on request** for complete identity/value details, exact IDs, normal check timestamps and relevant diagnostics; **omitted** for redundant counts/explanations, meaningless zeroes, field-change totals and repeated ownership prose. Do not move purposeless information into details or conceal an actionable problem. Authentication recovery belongs beside its failure reason; recheck, check information and history are secondary actions.

Each row has a keyboard-accessible full-details action independent of selection, with explicit ellipsis for shortened values and a title-change marker. Detail close restores its initiating control. Stable row identities retain selection, viewport and focus across ordinary rechecks and detail changes. Selected problems are summarized even when their rows are offscreen, with a direct jump. Resolve a conflict beside its field or explicitly deselect the entire row. An unresolved selected field blocks approval; it cannot be silently omitted. Pending strings remain labelled as excluded input in their cells; active composition defers the transition with a reason. Failed/incomplete retrieval shows its failure class and stale/unverified state with retry and applicable connection recovery. Unset, not loaded, unavailable, unchanged, explicit clear and numeric zero remain distinct. No common-change aggregation may erase a different before or after value.

Only **GitHubに反映（N件）** starts writes after this review. Zero effective changes, zero selection, incomplete checks, changed local revision or connection/project state disable approval with a reason. Late asynchronous results cannot replace a newer selection. Returning from same-identity connection recovery rechecks without automatic sending; a different host/account discards the previous selection/approval while preserving its scoped drafts. Closing confirmation keeps local edits and pending input. Confirmed field payloads are immutable and shared Issue titles are deduplicated.

Execution is sequential. Each operation checks account/host, membership, typed values, field/options and capability again before dispatch, including after waits and explicit resume. New incompatible remote values block the operation. Only the changed field is sent. A durable Running intent precedes dispatch; save failure prevents sending. Verified acknowledgement, remaining local values, shared title caches, baseline and execution history share one checkpoint commit. Later committed values and pending buffers survive acknowledgement of an earlier payload. Affected old Undo entries cannot restore pre-Apply baselines.

Dispatch validation and independent readback may use a scoped field observation: complete field definitions plus the exact target item and its complete value connection. It cannot replace the registration cache, reconcile unrelated fields, or promote creation without a separately accepted complete Project snapshot. The initial review remains a complete Project read. See the [observation boundary](performance.md#scoped-observation-safety-mapping).

The journal distinguishes Pending, Running, Succeeded, Failed, Unknown, Waiting, Blocked, Cancelled and Superseded. Running recovered after interruption is potentially sent. Startup never dispatches. Explicit resume observes current values; convergence with the intended value is acknowledged as observed convergence, not proof of the original request. Old or different values following uncertainty require a new decision. Withdrawing an old approval retains all attempt records; a subsequent fresh review can authorize a new operation. Ordinary unregister blocks unresolved history. Navigation/connection changes cancel and settle owned work; a running batch keeps its original target.

During execution the workspace shows each field's progress and each creation stage, with a command to stop unsent work. All-success completion stays in the table and announces completion to assistive technology. Incomplete work shows a brief warning with failed, unsent and verification counts; dismissing it selects and reveals the first affected cell in the originating Project. **次の問題へ** visits remaining stable row/field identities. Cell markers and a nearby reason distinguish failures from uncertainty. Hidden targets are temporarily revealed without saving different filters, ordering or column preferences; reapplication or Project switching removes that exception. Missing targets explain their absence and link to history without selecting another cell. Native composition defers the warning and navigation, and a Project/account transition invalidates deferred feedback. Pending text is preserved.

**反映結果・履歴** remains directly available from the Apply command group and confirmation. Its default presentation emphasizes failed, unsent and uncertain work, including incomplete creation stages and retained uncertainty from older attempts. **完了分を含む保存履歴** explicitly reveals the complete durable record. **確認して再開** and **承認を撤回** belong to the displayed execution; **閉じる** only closes the view. Supplementary explanations use a native information button with hover, click and keyboard access. Partial row success is not whole-row success. Cancellation stops unsent operations without reverting completed updates. Viewing results, navigating to a problem, returning from settings and restarting never approve, dispatch or delete history, or resend verified successes. Source: #53.

The APIs do not provide a documented compare-and-swap precondition for these inputs. Read/write races remain; there is no exactly-once guarantee, multi-record transaction or rollback. See the API/storage decision below and #10 for execution evidence and remaining acceptance.

## Connection and API access

Source: [#3](https://github.com/fukuda-yuki/gh-projects-boards/issues/3), with the settings/workflow separation in #31.

Every **接続設定** entry opens the same connection-only screen. Its ordinary content is host, account, status and checking; optional details contain CLI path/browse/detect, version and diagnostics. Explicit paths are retained. Project/Issue target URLs, discovery, registration/unregistration, default creation destinations and Apply commands belong to Project workflows, never to this screen, including collapsed sections. **元の作業へ戻る** is distinct from cancelling a check. Opening/closing without changes preserves the selected Project and editing context. Same-host/account recovery preserves the calling registration or confirmation work but requires new validation and explicit execution. Changing host/account retains old drafts separately and cannot transfer approval or targets.

- Startup is local. Manual checking detects or uses the selected gh executable, reads its version and active authentication metadata, and obtains the stable numeric viewer ID from `/user` on the explicit hostname. Authentication JSON content determines validity even when `auth status` exits with zero.
- A connection binds hostname, stable viewer ID, and gh executable. Rechecking does not adopt a different binding. Reads and writes recheck authentication and identity immediately before dispatch; mismatches permanently invalidate that context. An explicit new connection creates a new binding. Checked connection state is in memory; a saved profile does not restore authentication.
- Issue and Project URLs in the independent Project registration/information diagnostics must be HTTPS on the selected host, with explicit repository/owner and number. Each diagnostic independently reports read access, `viewerCanUpdate`, and the relevant OAuth update scope. Absent metadata stays unknown. Connection checking itself performs no Project search, retrieval, registration or mutation. Actual permissions and scope presence are separate; neither alone proves a later mutation will succeed.
- Only stored gh authentication is used by child processes. The four token environment variables are excluded without altering global settings. The UI reports variable names, never values. Authentication metadata is projected without the token field. Plaintext storage exposes the `hosts.yml` path and blocks writes; unknown storage blocks writes too. Reads remain available for diagnosis.
- The app never retrieves, stores, or displays credentials. Raw stdout/stderr and payloads are transient parser inputs, not logs or diagnostic output. Safe diagnostics expose outcome, HTTP status, exit code, classified error codes, and timing; remote error messages are omitted.
- REST and GraphQL use explicit host and target, `ArgumentList`, and UTF-8 JSON stdin. No shell interprets the payload. Child prompts, debug output, telemetry, and implicit gh host/repository overrides are disabled.
- The default timeout is 30 seconds per gh process, including stdin transfer. Cancelling or closing the window terminates the owned child process. Multiple commands can make the overall connection check longer than one process timeout.
- Results distinguish success, failure, cancellation, timeout, and unknown outcome, retaining available data and classified GraphQL errors. Partial GraphQL data is not complete success. Interrupted dispatched writes and potentially applied server failures are unknown; preflight failures establish that the target write was not dispatched. No automatic retry is performed.

Preflight cannot atomically lock gh authentication against changes made by another process between the identity check and API dispatch. Do not switch external gh authentication during an operation. Eliminating that race would require a different credential/session mechanism; token extraction is outside this design.

GHEC + EMU IdP/browser authentication, enterprise host behavior, organization policy, required scopes, proxy/TLS connectivity, credential-store availability, and executable restrictions remain unverified until tested in the company environment under [#13](https://github.com/fukuda-yuki/gh-projects-boards/issues/13).

## Project registration and cache

Source: [#4](https://github.com/fukuda-yuki/gh-projects-boards/issues/4), with bounded navigation from [#5](https://github.com/fukuda-yuki/gh-projects-boards/issues/5).

- The ordinary window exposes owner/repository-linked discovery, owner search and direct user/organization Project URLs after normal connection checking. Discovery queries use READ permission, existing URL validation and guarded preflight; they never require update permission or keyring storage merely to read. All discovery connections traverse to a terminal cursor; errors prevent a complete-list result.
- Repository association is read from GitHub's repository/Project connections, never inferred from contained Issues. Initial retrieval uses the production ProjectReader for the whole Project. Identity confirmation displays title, owner, host, bound viewer and duplicate-registration status before retrieval.
- Registration identity is normalized host + stable viewer ID + Project node ID. Multiple repository navigation entries select the same saved record. Left navigation groups the explicitly selected profile by owner and actual repository links, with a separate unlinked group.
- Only a Complete reader result plus successful durable local save publishes registration success. Unsupported field types and unavailable content do not negate a completed traversal. Partial first attempts are not registrations. Cancelled/failed refreshes preserve the previous saved snapshot. Stage/count progress has no invented percentage.
- Startup and navigation are local. Saved profiles require explicit selection and are marked cached/unverified; they do not restore authentication. A checked matching connection is required for server operations. Switching profile/context cancels and settles owned work. Obsolete results cannot publish into another profile or save after cancellation.
- The preview displays all retrieved items, Issue repository/number/title/Open-Closed and single-select values. Other item kinds, archived items and unsupported/unavailable/empty/not-loaded values remain distinct. The registered workspace supports the bounded editing contract below; partial retrieval remains a read-only preview.
- Default repository is an optional local `owner/repo` setting for new local-row destinations and does not filter retrieval. Unregistration confirms removal of only the selected scoped registration and its owned cache/backup/temp data, after settling retrieval. No GitHub data is mutated. When drafts or operation history exist, cancellation is the default; the user explicitly chooses retention or discard of exclusively owned work. Shared Issue drafts and their baseline provenance survive while another registration references them.
- Version 1 registration JSON is an atomic settings/snapshot record with schema and nested identity validation. Saves flush and verify temporary data before replacement, retain the previous file as a backup and reject concurrent writers. Corruption, unsupported schema, access/save failures and interrupted files are diagnosed without automatic data reset. See [storage and recovery instructions](../README.md#local-registration-storage).

## Editing and drafts

Editing, Project switching, and local saving do not write to GitHub. Preserve drafts across refresh and restart. Existing-cell blank paste means no change by default; clearing a value is explicit. Local new rows are distinct from GitHub Draft items. See [#7](https://github.com/fukuda-yuki/gh-projects-boards/issues/7) and [#8](https://github.com/fukuda-yuki/gh-projects-boards/issues/8).

### Local new rows

Source: #7, with #8 recovery and #9 retention. A selected saved profile can prepare local rows without authentication or existing-Issue update permission. These records have independent local IDs and no remote baseline, Issue identity or Project-item identity. The grid composes them after fetched rows. Each row retains its title, actual destination, supported single-select IDs and saved labels, incomplete buffers and stable placement. Missing title/destination is validation, never storage corruption or implicit removal. Remote readiness is unverified; local edits produce no creation operations.

**新規行を追加** captures the registration's current default repository, or an empty destination. Its last column edits the actual destination using local `owner/repository` syntax validation. Changing the default affects later additions only. **選択行を複製** copies committed supported values, including local edits, and excludes pending text. Existing-Issue copies capture the current default; local-row copies retain their chosen destination. Conflict, unknown field/value or unavailable selected option blocks the entire duplication with a reason. Copies are independent of later refresh/Apply of their sources.

**新規行として貼り付け** explicitly appends a rectangular TSV using title then the displayed single-select order. Titles are required, nonempty options must match exactly one label, and one invalid row or shape adds nothing. Missing default repository remains row validation. The entire append or multi-row duplication is one Undo unit. Normal paste remains bounded to allocated rows and never allocates overflow. **新規行を削除** removes only a wholly local selection; mixed remote/local selection is rejected. Removal Undo restores the same identities, committed values, buffers and placement, including after recovery and other-Project work.

Refresh and existing-field Apply preserve local records. Missing fields/options retain saved IDs and labels with actionable validation, including fields no longer in the fetched column set. Identical remote titles never identify a local row. Unregister-retain preserves rows for re-registration of the same scoped Project. Apply selection/review/history keeps new-row creation distinct from existing Issue updates under the creation contract below; local identities are never presented as existing remote targets. A stale review is rejected without losing newer preparation. Remote acknowledgement invalidates only remote Undo state; the guarded local portion of a mixed paste remains recoverable.

Version 6 uses the existing whole-profile checkpoint, serialized save gate and guarded Undo history, adding Project column preferences. Versions 1–5 migrate without discarding Apply attempts, successful/unresolved outcomes, conflicts or pending work. Older writers cannot overwrite the new schema. Repository existence, creation permission, Issue creation, Project addition and returned remote IDs follow the #11 creation contract below.

### Existing fetched fields

This production slice does not finalize or reduce #2's broader MVP matrix.

| Field/item | Read | Local edit | Explicit clear | Validation and identity |
| --- | --- | --- | --- | --- |
| Existing Issue title | Loaded Issue title | Yes, with observed Issue update capability | Rejected | Nonblank, no tabs/newlines; scoped Issue node ID |
| Project-owned single-select, including Status | Option ID and label | Yes, with observed Project update capability | Yes | Existing option ID; Project/item/field IDs; labels are display/input metadata |
| Repository/number and Issue Open/Closed | Read-only reference column | No | No | Native Issue identity, never the Status label |
| Other fields | Explicit supported-read/unsupported classification in reference column | No | No | Preserve fetched ownership and field IDs |
| PR / GitHub Draft / unavailable / unknown item | Explicit classification retained as a row | No | No | Never convert to an Issue or local new row |
| Unsupported/unavailable/not-loaded value | Distinct classification | No | No | Never interpret as editable empty |

The reader obtains `Issue.viewerCanUpdate` and `ProjectV2.viewerCanUpdate` as nullable, dated observations. Only explicit true with an observation timestamp permits the corresponding local editor. Old registration records remain readable with unknown capability. Cached capability does not authenticate a profile or promise a future mutation will succeed. No keystroke makes a permission/network request. See the official [Issue schema](https://docs.github.com/en/graphql/reference/issues) and [Project schema](https://docs.github.com/en/graphql/reference/projects).

### Selection, input and rectangular operations

Default columns are title, Project-owned single-select fields in retrieved order, then existing-row reference metadata or the editable destination repository for a local new row. Project-specific visibility, order and widths follow the column contract below. The row number and title remain visible during horizontal scrolling; the title cell also identifies the repository/Issue number or a local new row. One vertical viewport keeps these identities aligned with their fields. Scrolling does not change a control's stable row/field keys. Native controls are created when a row is realized and released when an inactive row leaves realization. Active and pending native editors retain their identity and caret offscreen; no live editor is rebound to another row. Workload-specific performance and human usability acceptance remain separate evidence.

Selection prepares native TextBox focus and replacement selection before direct typing. Actual native text/composition or F2 starts editing. Arrows while selected move one cell; Shift+arrows extend a rectangle. Arrows while editing retain native caret/candidate behavior. Enter during composition confirms the IME only; the later Enter validates/commits the cell and moves down one row. Tab/Shift+Tab commit an active editor then move in row-major order. Enter/arrows clamp at an edge; Tab clamps at the first/last cell. No navigation creates a row. Escape outside composition cancels the cell buffer; native composition/candidate cancellation remains separate. Navigating to another cell preserves incomplete buffers instead of committing or discarding them.

Clicking a cell body selects it; dragging the body, Shift+click and Shift+arrows extend a contiguous rectangle while not editing. The native choice menu opens through its arrow, F2, F4 or Space, and commits an explicitly selected option ID. A wheel gesture never changes the selected option. Delete or **値をクリア** explicitly clears selected cells. An existing Issue title or read-only target rejects the whole clear. Local-row titles and destinations may be explicitly cleared without removing the row. During text editing/composition Ctrl+C/V/Z belong to the native editor; while selected they belong to grid copy/paste/operation Undo.

TSV uses literal tabs and LF/CRLF row separators, without quoted-cell escaping. One final row separator is accepted; internal/trailing empty cells are preserved. Rows must have equal widths and fit entirely in existing rows/columns. Empty pasted cells mean no change, including empty trailing cells; they never mean clear. Every destination must be editable, even for a blank cell. A nonempty single-select label must match exactly one option; duplicate labels are rejected, while the choice editor selects by ID. Invalid shape, bounds, permission or values cause no partial operation and report a position/reason where a cell is identifiable. Unknown/unavailable values cannot be copied as empty cells.

With one selected cell, a rectangular TSV starts there as its top-left corner. With multiple selected cells, a multi-cell TSV must exactly match the selection shape. One nonempty value broadcasts over a selected vertical range in one column; broadcasting one value across multiple columns is rejected. Normal paste and fill never append rows. Internal copy preserves scope, Project/field IDs and option IDs; external labels still require a unique match.

The lower-right fill handle copies a nonempty source value vertically upward or downward. Dragging previews the logical range and scrolls at the viewport edges; values change only on release. Escape, capture loss, Project/view-generation changes, or changed source/target state cancel it without an edit. **下へコピー (Ctrl+D)** copies the top cell of a selected vertical range into the cells below. Empty-source fill is disabled with guidance to use explicit clear. Fill and broadcast reject source/target pending input or active composition rather than committing/discarding it; ordinary rectangular paste retains the existing recoverable-buffer contract.

All destinations are resolved by stable row/field IDs in the captured displayed order, including matching rows outside the viewport and excluding filtered-out rows/hidden columns. Validate the whole batch before applying it. Read-only, permission, conflict, unknown-option or pending-input failures identify the target and leave values/history unchanged. Clipboard waits and fill retain their starting mapping generation and workspace revision; stale work is cancelled rather than retargeted.

Each successful paste, fill, copy-down or clear is one transaction and Undo unit. An earlier source edit is a separate unit: the first Undo restores destinations, and the next restores the source. A value/draft-state no-op creates no difference or Undo entry; returning to the baseline removes the difference. Undo restores original IDs even if now hidden, including explicit clear and recoverable buffers. It checks all affected expected states before changing anything; later shared-Issue edits or an active buffer reject the whole Undo. Project histories cannot undo another Project's independent work. Selection, local edits, copy/fill/paste, saving and Undo perform no network permission check, GitHub write or automatic Apply dispatch.

Ordinary cells have a neutral value-first background. Selection uses a subtle fill and outer range border, with a stronger active-cell frame. Committed unreflected changes use a subtle distinct fill plus a fixed upper-right diamond; the lower-right fill handle has separate geometry. These overlays never move values, arrows, column widths or row heights. Pending native input uses the editing frame/caret, separately from committed differences. Warning/read-only shapes, accessible descriptions and keyboard-reachable details supplement color. Details expose Issue/field identity, baseline/local/fetched GitHub values and problem reasons. Local saving does not remove an unreflected-change marker.

### Project-specific columns

Source: #5, integrated with #7 editing and #8 checkpoint storage. The native **列の設定** dialog edits a local candidate. **ローカル保存** commits it durably before accepting the layout; **キャンセル** leaves the accepted preferences unchanged. **既定値に戻す** resets the current Project's candidate and still requires Save. Cached Projects can configure columns offline. Header menus provide common width, move and hide actions using the same durable preferences and field identities. Dragging a header boundary previews the width and saves on release; failure restores the accepted width. Title and row identity stay visible during horizontal scrolling. New field types and overall human design acceptance remain outside this contract.

Title is always visible and first; **Repository** is always visible and last. Existing-row repository metadata is read-only; local-new-row destinations are editable and explained as creation targets. Supported Project-owned single-select columns can be hidden or moved. Every displayed column has a finite width of 80–1200 logical layout units. Initial defaults preserve retrieved field order, with a 30-unit row height, 360-unit title width, 144-unit single-select widths and a 200-unit Repository width. Previously saved widths are retained. Header and row containers use one arrangement and aligned content origins.

In a narrow viewport, the frozen title's rendered width leaves at least 160 logical units for the other fields, subject to the 80-unit minimum. The saved preferred width is retained and can take effect again in a larger window. This responsive constraint affects header and data together.

Column identity is a presentation role (Title, Reference, or Project field ID), independent of Issue/item/local-row cell identity. Resolve display coordinates against each actual row before preparing an operation. All editors, selection, keyboard movement and rectangular copy/paste/clear use the same visible projection. Hidden columns are never implicit rectangle destinations. Reader ordering, business values, operation keys and whole-row duplication remain canonical; duplication includes hidden supported committed fields.

Width-only changes retain the existing native editors, active cell and rectangle. Reordering/visibility changes preserve the active cell by row/field identity when visible and collapse the former rectangle to that cell. Hiding the active field clears data selection; after the settings dialog closes, focus returns to the available view/details command. Pending buffers survive without implicit commit and are indicated when the field is shown again. Composing native editors are never rebuilt/reparented: the request remains held with a visible reason until composition naturally ends and the user retries. Settings saves do not consume data-edit Undo; earlier Undo retains original field IDs after reordering or hiding.

Header menus expose the full qualified field name, sorting and a field-local filter flyout. The always-visible title filter applies on its button or Enter and has an explicit title-condition clear action. These routes preserve the row-view contract: literal title matching, option/state IDs, committed-value filtering, durable save before reapplication, retained hidden work and explicit reapply after data edits. They do not filter per keystroke or commit pending cell input. The comprehensive settings dialog remains available. Failed saves retain the accepted view and report the failure beside the table.

Asynchronous clipboard and UI actions capture the view generation and resolved destinations. Mapping changes, Project transitions and unload invalidate late actions. New-row append confirms the captured TSV input mapping: Title, then visible supported single-select IDs in display order, excluding the destination role. Hidden fields remain Unspecified; the captured default destination is retained. Cancel and invalid batches append nothing.

Visibility is not an Apply selector. Review includes hidden field differences and creation intents, marks them as hidden in the grid, and shows actual IDs/values/clear intent. Planners, conflicts, histories and setup retain full field data. Pending text remains excluded from dispatch. Settings cause no mutation or Apply operation and cannot alter confirmed payloads. The workspace indicates changed, pending, conflicted and configured local work in hidden columns; unavailable work remains in diagnostics.

Version 6 adds scoped Project column preferences to the authoritative host/account checkpoint. Versions 1–5 restore default columns while preserving work and execution records. Saved preferences follow field IDs through renames. New supported fields appear after previously configured fields and before Reference. Removed/incompatible IDs retain unavailable entries; a same-name replacement does not inherit them. Partial observations do not erase preferences or drafts. Obsolete definition candidates cannot save silently. Save merges the candidate into the current checkpoint under the existing gate and final revision/lifetime guard, preserving later edits and acknowledgements. Failure keeps the accepted layout and candidate for retry. Malformed v6 settings reject the damaged checkpoint without rewriting it or resetting unrelated work; recovery diagnostics retain existing corruption/interruption distinctions.

### Local durability and lifecycle

Fetched observations, editor buffers and committed local differences remain separate. Committing/saving never modifies the baseline; returning to baseline removes the effective difference. Titles share a host/viewer/Issue identity across Projects; selects remain scoped to Project/item/field IDs. Opening another cached observation never replaces an active draft's pinned baseline. The UI distinguishes per-Project and profile-wide changed-field counts and local saving/saved/failed states from GitHub synchronization.

One versioned JSON draft record per host/stable viewer under `Drafts/` holds baseline value/source Project/retrieval time, clear/value intent, recoverable text, field stamps and transaction history. Version 2 adds observations, conflicts and the authoritative registration checkpoint described below; version 1 is still readable. It contains neither credentials, raw API payloads nor private IME state. Startup/profile selection restore it locally. A restored buffer is pending text, not a committed cell.

Draft saves are serialized. Under a filesystem writer lock, the expected durable revision is checked, a temporary record is flushed and validated, and the complete profile record is atomically replaced with a last-good backup. A cross-field operation is recovered wholly or not at all. The session advances its acknowledged revision only after success and drains later changes before reporting a successful flush. Competing-process/stale saves fail instead of overwriting. Corruption, incompatible schema, mismatched scope and interrupted files are diagnosed without resetting source data. Intermediate edits after the last successful save may be lost on forced termination; normal transitions/close wait for a successful flush. Save failure keeps in-memory text and cancels navigation/close.

Refresh reconciles existing titles and Project-owned single-select fields using the contract below. The final checkpoint replacement rechecks local revision, operation generation, connection identity and active composition synchronously immediately before replacement. Unregistration settles owned work and defaults to cancellation, offering explicit retention or discard. Discard never removes Issue work shared by another registration; its pinned source provenance remains in the surviving draft record. Discard plus registration removal is one durable checkpoint decision; legacy files remain recovery material after migration.

## Data identity and availability

Keep Issue fields, Project item fields, and application work state distinct. Share the same Issue's body fields across Projects while retaining each Project item's own values. Missing, unreadable, unsupported, and explicitly empty values are different states. See [#6](https://github.com/fukuda-yuki/gh-projects-boards/issues/6).

### Bounded Project read contract

The Core Project reader accepts an explicitly selected Project node ID bound to the existing connection's host and stable viewer ID. It uses the guarded connection service for every page. It performs queries only, with the same identity preflight, credential isolation, per-process timeout and cancellation as other reads. Project registration/navigation UI is separate work.

Each returned Project has a stable owner ID, node ID, number and URL. Repository and Issue identities also include the connection scope. Items retain their own node ID, content identity, archived flag and field values. Issues are indexed separately from items: two Project results refer to the same logical Issue key, while their item values remain independent. These are immutable read observations; there is no cross-result cache, automatic synchronization or draft state.

| Data | Read behavior |
| --- | --- |
| Issue title and Open/Closed state | Loaded directly from the Issue, never through a field display name |
| Project single-select, including Status | Field ID, Project ownership, option IDs/names and selected option ID |
| Issue-derived or organization Issue fields exposed by a Project | Ownership and Project field identity/type retained; their projected values are unsupported in this slice |
| Other Project fields | Identity, type and known ownership retained as unsupported; unknown ownership stays unknown |
| PR / GitHub Draft | Explicit item kinds with content IDs; no ordinary Issue or local-new-row conversion |
| Redacted/null content | Unavailable content with the Project item identity retained |
| Unknown item/value types | Explicitly unsupported, retaining encountered type and available IDs |

Field names and option names are display metadata, never identity or destination selectors. Native Issue properties use their Issue identity and typed title/state properties; a same-named Project field has its own field ID. The bounded editor additionally reads dated Issue and Project viewerCanUpdate observations. Missing/denied observations do not enable editing; creation and remote application require the separate explicit Apply contracts.

The reader traverses Project field definitions, items and every implemented item-value connection to the terminal page, including more than 100 entries. It checks node/ownership identities, duplicate fields/options/items/Issues/value IDs, duplicate field assignments, repeated cursors, missing paging metadata and inconsistent total counts. On API or structural failure it stops further requests, retains already observed data and reports a classified problem. No automatic retry occurs.

Result outcomes are Complete, Partial, Failed, Cancelled and TimedOut. Cancellation/timeout can retain a partial Project. Per-connection completion flags describe traversal, not universal support or readability. A Complete result means the requested traversal completed without detected problems; it can contain explicitly unsupported fields and known unavailable items. It does not establish a transactionally consistent snapshot: GitHub does not pin successive queries to one revision, and equal-count concurrent replacements can escape count/cursor checks.

Values distinguish Present, Empty, Unsupported, Unavailable and NotLoaded. An explicit null option, or an absent supported field after a complete, error-free traversal, is Empty. On a partial read, nulls become Unavailable and absent supported fields stay NotLoaded; redacted content never implies an empty Issue or field. Unknown option IDs retain the observed ID as Unavailable. Partial GraphQL data is retained but never treated as complete. Missing or unsupported data cannot authorize clearing or deletion; this slice has no writes or apply implementation.

The broader MVP field/item editing matrix remains under [#2](https://github.com/fukuda-yuki/gh-projects-boards/issues/2). Body, assignees, labels, milestone, text/number/date/iteration/multi-select, Issue fields and relationships remain candidates requiring separate read/edit/clear decisions.

Schema references: [GitHub Project types](https://docs.github.com/en/graphql/reference/projects), [Project API queries and redacted items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), and [cursor pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api).

## Refresh and apply

The bounded #9 workflow refreshes registered Projects with existing local work. It covers Issue titles and Project-owned single-select option IDs only. B is the pinned baseline, L the committed local value (never unfinished editor text), and R the fetched observation. For known valid values: L=B adopts R cleanly; R=B retains L; L=R adopts R cleanly; otherwise keep B/L/R as an unresolved conflict. Explicit select clear is distinct from unavailable, unsupported or not-loaded values. Apply these rules independently per field. Repeated refresh retains original B/L until explicit resolution or valid convergence.

Title observations and drafts are shared by scoped Issue ID; Project/item/field select keys remain independent. Opening another cached Project only initializes missing keys and never rebases an accepted observation. Fetched timestamps order accepted observations within the profile; they are client observation times, not GitHub locks or revision tokens. Structural changes report added/no-longer-observed items, archive state, missing/type-changed fields and renamed/deleted option IDs. Absence from a complete Project traversal is not proof of Issue deletion. Unknown capabilities and detached values stay blocked and retain identifiers, drafts and buffers.

Persist local work before retrieval. Reconcile against current local state after I/O; a revision or connection-generation change before durable replacement rejects that candidate. Active composition defers refresh with an actionable message. Inactive buffers remain pending, never auto-committed. Failed/cancelled/timed-out/partial reads do not commit a reconciliation or replace the complete cache. Staged observations and unknown ranges are separate from the accepted workspace.

The comparison UI shows B/L/R, observation time, ownership, IDs and current blocking reason. Resolvable conflicts offer fetched GitHub, local, or another valid value. A decision is bound to the displayed local revision and remote observation ID; stale decisions require a new comparison. On resolution R becomes the baseline and the chosen value becomes local state; choosing R is clean. Remote observations never create user Undo units. Preserve unaffected history; explicitly invalidate affected stale operations and deleted-option entries. Resolution Undo is subject to the same state checks and cannot overwrite a subsequent observation.

Version 7 profile checkpoints atomically contain registrations/caches, baselines, observations, drafts, buffers, conflicts, local rows, guarded operation history, Project column and row preferences and Apply journals. A checked, flushed temporary file and one atomic replacement form the commit; there is no second cache write. Root/profile locks and expected durable revision reject competing writers; first migration also compares all legacy registrations under the lock. Restore registrations and drafts from the same checkpoint object. Broken profiles do not prevent independent valid profiles from restoring. Version 1 records remain readable and previous files/backups are retained. Publish success only after durable replacement; failures leave the original in-memory work and last coherent checkpoint intact. A crash after replacement but before UI notification recovers the committed checkpoint on restart.

Existing-field Apply must revalidate target identity, value and capability immediately before dispatch, including queued operations whose observations can become stale while waiting. Refresh is an observation, not a server-side lock or a transactionally consistent multi-page snapshot, and cannot eliminate the read/write race. Local rows retain their identities, values and pending text across refresh; broader fields remain outside this slice. See [#9](https://github.com/fukuda-yuki/gh-projects-boards/issues/9), [#10](https://github.com/fukuda-yuki/gh-projects-boards/issues/10), [GitHub Project schema](https://docs.github.com/en/graphql/reference/projects) and [pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api).

## New Issue creation

Track Issue creation, returned IDs, Project addition, field assignment, and result verification separately. An uncertain creation result must not trigger automatic recreation. See [#11](https://github.com/fukuda-yuki/gh-projects-boards/issues/11).

Apply batches contain distinct existing-field operations and creation operations. Creation approval binds the per-row revision, Project and resolved stable Repository ID. Only selected rows are validated. Repository lookup disables rename following; Issue enablement, archive state and `viewerCanCreateIssues` are independent creation prerequisites. `createIssue` sends only `repositoryId` and `title`; membership uses separate `addProjectV2ItemById`. No tracking body/label/template metadata is added. `clientMutationId` is not treated as a deduplication guarantee. The official [Repository](https://docs.github.com/en/graphql/reference/repos), [Issue](https://docs.github.com/en/graphql/reference/issues), [Project](https://docs.github.com/en/graphql/reference/projects) and [Project API](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects) contracts define these operations.

The durable pre-dispatch creation flag survives approval withdrawal and remains a cross-batch creation veto. Post-dispatch failures are conservatively held; no transport outcome automatically authorizes another Issue creation. Partial response IDs remain typed evidence even when other response fields or GraphQL results are incomplete. Independent Issue-by-ID observation establishes identity before membership/setup. Known identity never reverts to a fresh local row after unreadability, transfer or title mismatch. Explicit URL binding checks host, repository, Issue type and lineage ownership. A separately approved duplicate-risk retry has a new attempt ID and a retained predecessor; historical uncertainty stays visible without blocking unrelated new Apply.

Complete Project traversal determines exact membership; incomplete traversal cannot establish absence. Existing/auto-added membership is reused. Project-add uncertainty is reconciled independently from creation. Returned item ownership/content is validated, persisted and independently observed. Initial select intents are Unspecified, Set(option ID) and ExplicitClear; unspecified makes no field request. Version 4 null/absent select values migrate as Unspecified. Initial field observations are saved before assignment. Later incompatible values are held for explicit setup review; new setup approvals retain previous operations/attempts and intents. Only supported Project-owned single-select setup is authorized.

One scoped logical row is retained through creation and promotion. Verified full Project observations and durable lineage mappings prevent duplicate presentation. Promotion preserves later title/select edits and buffers, and defers rather than discarding unavailable work or overwriting shared drafts. Creation-related lifetime Undo cannot resurrect eligibility; unaffected mixed-operation parts remain independently undoable. Active native composition defers replacement. No successful operation is described as rolled back.
