# Specification

The [requirements](requirements.md) and [decisions](decisions.md) define the planning editor. The ordinary window exposes the workspace, Project settings, an editable native plan sheet with a row-aligned Gantt, a read-only summary view for phase status and load, and explicit refresh and publish review.

## Pending-input invariant (all editing views)

The plan sheet and settings obey the same invariant: **pending input is never hidden or dropped**. A row or cell containing uncommitted, composing or invalid input remains in the visible, focusable presentation until committed or explicitly discarded. Filters, recalculation, drill-down membership, period/zoom changes and redraws cannot remove it. Pending rows remain alongside the normal filtered/period results; they stop being retained when their last pending cell resolves. This retention changes presentation only, never the schedule, totals or assignment.

There is always a way out. Escape in an editor discards only that cell's pending input and restores its current committed display value, clears its validation error and creates no Undo entry. IME conversion Escape belongs to the IME first. Invalid input has an error callout anchored next to its cell. Commands requiring resolved input (navigation, Undo/Redo, Project switching and close) either proceed after resolution or refuse and focus/scroll to the problem cell; they cannot leave the only correction path outside the view. Focus-loss validation may report an error without stealing focus from another edit. Leaving an unchanged, already rejected settings value does not restart focus recovery or dismiss the Project picker. Choosing a navigation command still refuses the transition and returns to that invalid input.

Validation feedback follows task identity and field, not a recycled control instance. The cell callout is announced to assistive technology and overlays the view without inserting a line above the sheet or moving its rows. When scrolling moves its cell outside the sheet viewport, unloads or rebinds its row, the callout closes or moves to a visible editor for that same problem. An offscreen cached editor is not a callout target. Scrolling back or a refused command makes the retained error reachable again; another task must never inherit its message.

After a refused or failed operation, toggles, pickers and selectors are synchronized with the current document (or accepted presentation setting), including an in-memory change accepted before a persistence failure. Restoring a control is not another edit. Each view owns its controls and pending inputs; this invariant does not introduce a second document or shared editing framework.

## CSV import of new tasks (#82)

**CSV から追加…** in the sheet toolbar opens the native `.csv` picker. Import adds new local tasks to the selected Project only; it never updates existing tasks or writes to GitHub. File selection, validation and duplicate confirmation precede one atomic `InsertPlanRows` operation with kind `CsvImport`. Its rows and any newly resolved people are one Undo step. A successful import clears the title filter and selects the first imported task so the result is reachable. Imported Estimate leaves Remaining and Actual empty; Remaining is displayed and scheduled from its calculated default. The existing scheduler calculates dates and parent roll-ups, retaining unknown dates for unassigned or incomplete work. Only **発行** creates Issues and publishes their relationships.

The template is [templates/new-tasks.csv](../templates/new-tasks.csv), copied to `templates/new-tasks.csv` in the app output. It is UTF-8 with BOM for Excel. Input accepts strict UTF-8 with or without BOM, then strict Windows-932 (Shift-JIS) if UTF-8 decoding fails, using the framework code-page provider. Files are at most 5 MiB and 10,000 data records. Quoted commas, doubled quotes and quoted line breaks are supported. Error line numbers are physical file lines, including the header; a multiline record is identified by its first line.

| Header | Value |
| --- | --- |
| キー | Required unique, case-sensitive file-local key; no `#`, semicolon or control characters. Numeric keys are allowed. |
| タイトル | Required nonblank task title. |
| 見積 | Required column; empty means unknown, otherwise a nonnegative decimal number of person-hours using `.` as the decimal separator. |
| 担当者 | Optional; GitHub login, or semicolon-separated logins; empty is unassigned. |
| 先行タスク | Optional; semicolon-separated file keys or existing Issue references. |
| 親 | Optional; one file key or existing Issue reference. |
| 開始日 | Optional plan start of the new task; `yyyy-MM-dd` or `yyyy/M/d`, empty for none. |
| リポジトリ | Optional `owner/repository`; empty uses the current default repository. |

Imported rows use stable parent-first order, preserving sibling CSV order and accepting forward parent references without renumbering keys. Subtrees attached to existing plan parents go after their last current descendant; other imported subtrees append at the end.

Columns may be reordered. Unknown or duplicate headers and missing required columns are errors. File keys resolve first; `#123` (or a bare number without a matching key) refers to Issue 123 in that row's repository. `owner/repository#123` disambiguates repositories. Existing references must identify an Issue already loaded in this Project. Keys are not sent to GitHub or stored as task identity; each import creates fresh local identities.

Core checks all records before accepting any rows: syntax, duplicate keys, missing titles, invalid numbers/dates, unresolved keys/Issues, repositories and assignable logins, and hierarchy/dependency cycles including existing tasks and inherited summary dependencies. Repository existence and Issue-creation capability and required assignable-user identities are read through the active scoped connection; incomplete reads cannot authorize an import. New people start at 100% rate with no allowance; existing resource settings are preserved. Validation uses the same scheduling rules as ordinary editing. Errors appear in a bounded list of **line number + short reason**, with **CSVを選び直す** as the next action. Cancellation changes nothing.

Duplicate detection uses SHA-256 of the original file bytes, retained as local provenance on each imported row. If any current row has that hash, the UI requires **重複して追加** confirmation before adding another copy. It survives save/reopen, identity promotion on publish and refresh; Undo removes it with the imported rows. Changed bytes, including a changed encoding, are a different file; this is an exact-repeat warning, not semantic deduplication. Provenance is excluded from GitHub fields and unpublished markers.

CSV preparation belongs to the workspace operation queue. Pending edits are resolved before the picker opens; closing cancels its owned repository reads and dismisses validation/duplicate dialogs without adding rows.

Publication resolves each new row's repository separately. Every destination must pass preflight before the first dispatch; creation and uncertain-creation reconciliation use that same repository, while batch sizes, pacing and #79 stage order remain unchanged.

The [sandbox evaluation file](evaluation/sandbox-plan.csv) contains a small plan for Project 3, uses only `fukuda-yuki` or no assignee, and targets `fukuda-yuki/codex-sandbox`. Importing it is local preparation; publishing it remains an explicit ordinary-app action.

## CSV export (#173)

**CSV に書き出し…** (`PlanSheetCsvExport`) sits beside **CSV から追加…** in the plan sheet overflow. With a Project open, it resolves pending cell input through the ordinary command gate before opening a native save picker; invalid or composing input prevents export. The suggested name is `<Project title>.csv`, with a `.csv` file type. Cancellation does nothing. Generation and writing run off the UI thread. Failure shows the reason in the existing error presentation; success confirms the exported data-row count (for example **1,040 行を書き出しました。**). Export never reads or writes GitHub and requires no Excel installation.

Export includes every local-document row in plan order, including requirement/summary rows, folded children and filtered-out tasks. There is no row-scope choice. Values are the current local sheet values, including calculated dates, summary effort and calculated Remaining. Empty values are empty cells; unavailable/unsupported extra values retain **取得できません**. Assignees use the full comma-separated sheet names; labels and predecessors use the sheet text ([task names](#task-names-263), or 計画外).

The column set is deliberately tied to the sheet configuration:

1. Fixed **ID**, the [task name](#task-names-263) (`#407`, `repo#407` or `新1`).
2. Every visible column from `PlanSheetColumns.All(document)` in its current order, excluding `Id`. Headers are their configured display names (`Name`). Supported standard columns are 状態, タスク名, 工程, 担当者, 見積 h, 残 h, 実績 h, 開始日, 終了日, 先行 and ステータス; optional columns include other Project TEXT/NUMBER/DATE/SINGLE_SELECT/ITERATION fields, ラベル, マイルストーン and リポジトリ. 状態 exports its accessible state text, empty for an ordinary unchanged row. A visible repository column does not replace the fixed identity column.
3. Fixed **要求事項** (the title of the row's top-level ancestor, so tasks can be filtered and pivoted by requirement in Excel; empty for a top-level row), **リポジトリ** (`owner/name`), **Issue 番号**, **URL**, then **未発行**. Local tasks have no Issue number or URL. 未発行 is **新規** for a new local task, otherwise comma-separated changed-field names as in publish review, or empty for an unchanged row. This uses the same unpublished-change rules as the sheet, including changes to hidden fields.

Effort and Project NUMBER values are invariant decimal numbers without units or grouping; negative numeric values remain numeric. Dates use `yyyy-MM-dd`. The file is UTF-8 **with BOM**, with CRLF record endings and RFC 4180 escaping: fields containing commas, double quotes, CR or LF are quoted and embedded quotes are doubled; embedded line breaks are preserved. Any text cell (including headers and identity values) starting with `=`, `+`, `-`, `@`, tab or CR is prefixed with one apostrophe to neutralize Excel formulas. Exporter-produced numbers and dates are not prefixed. This is an analysis output, not the new-task import template; Gantt, `.xlsx` and import changes are excluded.

## Summary view (#127)

**サマリー** is the selected Project's read-only waterfall status view. Planning edits belong to 計画; rates and whole-Project allowances belong to settings. Undo/Redo, refresh and publish remain in the shell. The status bar has no Gantt legend here. All measures consume the same scheduled result as the sheet; no second scheduling or resource leveling occurs. Requirement/summary rows never contribute to counts or effort.

The header reads 「期間 start – end」; the 基準日 the figures use is the toolbar's 基準日. The page opens with the **verdict** (#260, R6-4), then four measures form the Project band:

- 残り稼働日, with 「M / N 稼働日が経過」. The Project calendar excludes weekends, bundled/imported holidays and company days off. Total days use [start, end], elapsed days [start, status date), and remaining days [status date, end]; after the end remaining is zero. Missing endpoints make dependent measures unknown.
- 完了見込 is the latest task end on the forecast schedule: the forecast end for open work, the close date for closed work, and the retained plan end for kept work and any task with no forecast. A task with no end at all, such as an inserted row without effort or dates, is left out and labelled 「（日程なし N タスクを除く）」 after the date, as phase and person finishes are; only when no task has an end is it unknown. Its signed working-day difference is days in (end, forecast] when late, minus days in (forecast, end] when early. Text is 「終了日より N 稼働日遅れ」, 「N 稼働日前」 or 「終了日どおり」. Caption: 「担当者の負荷は含まない」; its tooltip reads 「先行関係と見込み残存工数から計算（担当者の負荷は含まない）」.
- 終了日までに必要な稼働 is remaining hours of all tasks, including unassigned/multiple assignments, divided by the remaining capacity of the people assigned in this Project. Show N % and warning color plus 超過 above 100%; the card tooltip carries 「残 Xh ÷ 稼働可能 Yh」 and 「100% を超えると間に合わない」.
- 進捗 is summed Actual / summed Forecast, with 「完了 a / b タスク」 and 「見積 Zh より ±Dh」; the card tooltip carries 「実績 Xh ÷ 見込 Yh」. Remaining is the scheduler's effective Remaining (closed = 0; blank defaults to max(Estimate − Actual, 0)); Forecast = Actual + Remaining, variance = Forecast − Estimate. Blank Actual counts as zero. Progress is unknown for zero or unknown Forecast. Totals sum known contributors and retain excluded-task counts; no known contributors means unknown. Variance and progress use matching known contributor sets. Missing Estimate and Remaining make open-task Remaining and Forecast unknown. Label exclusions 「工数未入力 N タスクを除く」; never silently present partial totals as complete.
- 要注意 contains identity-set buttons for 残 0・未完了 and 工数未入力 and the 担当者なし filter (「担当者なし N · 残 Xh」, with 「（工数未入力 N タスクを除く）」 after a partial sum and no 残 part when no unassigned task has a known remaining), which opens 計画 with 担当者 set to 担当者なし. Hide zero counts. 残 0・未完了 is reported here only, not on the plan sheet.

The **verdict** comes first and states the result in plain words:

1. The worst slip: among the version (完了見込 against the Project 終了日) and every 工程 with a 目標日, the one with the largest positive working-day difference, as 「SS が目標日 12/18 より 21 稼働日遅れ」 or 「完了見込 4/27 (火) が終了日 4/22 (木) より 3 稼働日遅れ」, in the critical colour. When nothing slips it reads 「目標日と終了日に遅れはありません」 in ordinary text.
2. The overall forecast 「完了見込 4/27 (火) · 終了日より 2 稼働日前」 (the 完了見込 measure below), and the slipping 工程 in difference order: 「目標日より遅れている工程: SS +21日 · PS +5日」.
3. The attention counts as buttons in the strip's order, 遅れ, 遅れの原因, 見積超過, 未更新, each shown when nonzero; pressing one opens 計画 with that toggle pressed and only that filter.

Summary percentages are whole numbers: round to the nearest integer (midpoints away from zero), but round percentages above 100 up so a small overload remains visible (100.4% becomes 101% 超過). A progress percentage never reads 100% while a counted task is open: it shows at most 99% until every task it counts is closed. Core values stay exact. A person/phase cell without tasks, a finished cell in the person × phase grid and a month without work show 「—」; zero is reserved for a known value of existing work. Unallocated work still has its reason and task route.

Table headers and cells do not wrap. A table's header row stays visible while its rows scroll: the person matrix keeps its header above its own scrolling body, and the page scrolls only the sections beside it. The completed/task column accommodates four-digit counts with digit grouping. Phase selectors are left-aligned plain table text; interactive table cells have no field border or fill at rest, a hover fill, native keyboard focus and an accent fill/outline when selected. Selection reveals the detail heading and filter command; details use the same row IDs as the plan, never internal GitHub/local identities. Horizontal table viewports leave vertical mouse-wheel input to the enclosing vertical viewport at its native rate.

The phase table takes its measured column width and the **工程の日程** timeline sits below it in the left column. Its month axis uses the Gantt month-tier label style, with labelled 基準日 and 終了日 lines. In the forecast tile, only the date and difference use warning color; the explanatory caption uses secondary text. Attention commands are compact, left-aligned icon/label/count buttons with the sheet's corresponding warning icons.

### Phase and period settings

工程 is an optional mapped Project SINGLE_SELECT field: exact case-insensitive name 工程 and correct type auto-match on first open and in mapping settings; ambiguity stays unassigned. Refresh never creates it and there is no create command. The same mapping appears in the 工程 settings group, with options in field order and leaf-task counts; a line 「工程なし n タスク」 appears only when n > 0 (the mapped field is already named by its selector). Unmapped settings show 「工程のフィールドが未設定です。」, as the summary does. The optional milestone mapping column selects a GitHub milestone title for each phase; it never edits the milestone or its due date.

The sheet places narrow 工程 immediately after タスク名, visible by default; tooltips expose full option names. Typing, paste, Ctrl+D, fill handle and Delete use normal operations and Undo. Trim input and match exact option names case-insensitively; reject unknown text with 「工程は SA, UI, SS, PS, PG, PT, IT, ST, OT のどれかを入力してください。」 using actual options. Unmapped cells are empty and read-only, with 未設定 in the header tooltip. Summary rows use baseline-only values and cannot edit/publish Phase, like Status. Refresh, conflicts, reset, unpublished markers and publish review follow Status; publication writes the current option ID and review shows option names. Settings export/import preserves the mapping. Task CSV import does not add a phase column.

Settings **期間** contains optional 開始日 and 終了日 date pickers, displayed `yyyy/MM/dd (曜)` like the 基準日. End before start is rejected without changing accepted settings. End is a reporting boundary, never a scheduling constraint. Both dates export/import and each accepted edit is one settings Undo operation. **担当者** lists only the people assigned in this Project: each line contains name and login, 稼働率, optional 上限工数 h and the read-only タスク and 残 h. A stored person with no task is hidden while their rate and allowance are kept, and returns unchanged when a row holds them again. Empty allowance is valid, invalid input stays editable and blocks navigation. Each accepted rate/allowance edit is one settings operation. Evaluation seeds both dates from the version manifest and auto-maps 工程 at 未発行 0.

On first open only, when the first complete GitHub read creates the local document and auto-matches columns, initialize empty Project start/end and phase milestone settings. Start is the earliest known start among the retrieved Issue rows. End is the latest known due date among the exact-title milestone groups that at least one retrieved Issue row belongs to, falling back to the latest known Issue-row end only when none of those has a due date. Milestones no Issue of this Project uses are ignored, because one repository can hold several concurrent versions, each a separate Project with its own milestones; absent dates stay empty. If the derived start exceeds the end, leave both empty. Phase mapping follows the matching rule in [GitHub milestone targets](#github-milestone-targets-133). Initialization is part of document creation, not a user Undo operation, leaves GitHub's dates as the plan dates and leaves zero unpublished tasks. The dates and mappings are ordinary editable, clearable, exportable/importable settings afterwards; refresh, reopen and reset never derive them again or overwrite explicit values or clears.

## Current publish workspace (#79)

The review header exposes `PlanPublishStatusDate`. When 基準日 is before today (the App's `PlanClock.Today`), show **基準日 yyyy/MM/dd (曜) は今日より前です。** using the existing unpublished-work amber caution brush, not overdue critical red. Its accessible name carries the full visible text. This warning does not block publication or change the mutations sent. When 基準日 is today or later, the line is hidden: the review's dates are the plan's own values and need no caption. A reset (GitHub の状態に戻す) moves no dates, so the line names no recalculation origin or calculation origin after one.

The review includes the native sub-issue order changes the publish will write, including non-conflicting changes and a retry of a failed reorder; a child-order difference only GitHub holds is not listed. The parent's 子タスクの順序 line names the children that changed the order and shows only them with their neighbours in the new order (#224): 「子タスクの順序  新2 の追加による  #305, 新2, #306」. A new task is 追加; a published child that moved, entered or left is 移動; separate neighbourhoods are joined with 「…」. A new parent and a child-order conflict still show the whole order. Relationships outside the plan use a retrieved repository/Issue number when available; otherwise they are labelled as unretrieved external Issues and offer a link to the source Issue's GitHub relationships. They never use the Project caption.

The PMO reviews the changes in the open Project before explicitly confirming publication. **発行** opens a review in the workspace in three sections, in this order (#224 D1): **競合** (only when a blocking conflict or an unavailable task remains), **あなたの変更** and **再計算で動いた日程**. Each section heading carries its count. A 競合 row shows the task, the field, 「この PC」 and 「GitHub」 values and **この PC の値にする** / **GitHub の値にする** on one row; who changed each value and when is not shown, because the read does not keep it. あなたの変更 has one group per Issue for what the PMO entered: typed values (on the sheet's typed tint), assignees, links, state commands, new tasks (「新規 Issue  <owner/repo> に作成」), moved rows and child orders, and the informational lines (held, deleted-field, failure and unverified). 再計算で動いた日程 lists the dates and closed-task remaining work the scheduler moved (#131 publishes them), grouped by the edit that moved them: 「#226 の見込み残存工数の変更で 5 タスク」, 「新2 の追加で 3 タスク」, or 「入力した変更によらない再計算で N タスク」 when no task edit reaches them (a 基準日, settings or GitHub-side change). A group is attributed in Core (`PlanPublishGrouping`) to the nearest edited task upstream in the scheduler's dependency graph (predecessors, ancestors' predecessors and, for a summary, its children), walking only through tasks whose dates differ from GitHub's; equal distances go to the earlier plan row, and an edited task whose own dates moved belongs to its own group. Each group starts closed and opens or closes with its header; **すべて開く** / **すべて閉じる** toggles them all, and the groups start closed again each time the review opens. A task can appear under あなたの変更 and in a recalculation group; the heading counts distinct tasks. Within each section a group shows: readable task title and [task name](#task-names-263), retrieved repository/Issue number when available, and its changed fields with before → after values together. Short field differences share a wrapped line rather than repeating the task identity for every field. Full values wrap within the available width and remain readable without expanding each difference. New Issues are labelled 新規 Issue with the repository the Issue is created in. Field names use the sheet's full names (見積工数, 実績工数 and 見込み残存工数 for its compact effort headers); dates use the plan's `M/d (曜)` form, prefixed with the year (`yyyy/M/d (曜)`) only when it differs from the 基準日's year, so before, after and GitHub values in another year still name it (#109). Empty values are 未入力; assignees and relationships use readable names or task names. Conflicts are not repeated in a task's group; they appear only in 競合. Resolving a conflict saves a local operation; it does not send writes, and the review retains the affected Issue or its nearest remaining neighbour in view. ### Task names (#263)

A task is named the way the team names it on GitHub: by its Issue number, which is MS Project's Unique ID rather than the row position (ID). A published task's name never changes when rows are inserted, moved, folded, filtered or deleted (owner-agreed PMO decision, #263).

- A row with an Issue is `#N`. When the plan's Issues belong to more than one repository, every Issue row is `repo#N`, with the repository name and no owner. Only rows with an Issue decide this, so adding or moving a local row never renames a published task.
- A row without an Issue yet is 「新1」, 「新2」…, numbered in plan order among those rows. The number is derived whenever the plan is shown and is never stored, so the plan file keeps its schema; inserting, moving or deleting a local row may renumber the other local rows. Publishing replaces 新N with the new Issue's number.
- A predecessor outside the open Project shows 計画外, as before.

The sheet's ID column and 先行, the selection line, the start reason, lateness text, messages (indent and delete refusals, untitled rows, dependency cycles, publish guards), 詳細, the publish review, the summary drill-down, CSV export, the add-predecessor chooser, the assist pane and accessible names all use this name. A sheet row, a requirement row included, has the accessible name 「{task name} {title}」, for example 「#17 コードレビュー」, built only from what the row shows; it never announces the Issue's GitHub node ID, and the empty new-task row is 「新しいタスク」 (#242). The announced name follows the row's content, so editing the title refreshes it while the row is realized. No message names a task by its row position. The scheduler's stored start reason (`{row} の終了後`) and the lateness cause stay internal values keyed by row; only their display converts them to the predecessor's task name.

The row's position stays visible as the unlabelled secondary number at the left of the ID cell, like Excel's row header. It helps the eye find a row and is never accepted or shown as a task reference.

#### Naming a task in 先行

Typing, clipboard or TSV paste and fill into 先行 read one grammar, entry by entry, after the [folding](#cell-text-input-239):

- `N` or `#N`: the row whose Issue number is N. When rows of more than one repository carry N, the entry is refused with 「#524 は複数のリポジトリにあります: api#524, web#524」.
- `repo#N` (repository name, case-insensitive) or `owner/repo#N`: that repository's Issue N.
- `新N`: the Nth row without an Issue, as currently shown.
- An Issue or 新N with no row in this plan is refused with 「#99 はこの版にありません。」 or 「新5 はこの版にありません。」. Anything else is refused with 「先行タスクは #524、repo#524 または 新2 の形で指定してください: {value}」. Every refusal carries the folded value and changes nothing; nothing is linked by guess.

Because the sheet copies 先行 as task names, copying 先行 from one row to another keeps its meaning. **CSVから追加** keeps its own reference rule: a file key, `N` or `#N` for the row's repository, `repo#N` or `owner/repo#N`.

### Cell text input (#239)

Cell text the PMO types or pastes passes through one normalisation before the column rule runs. This is a specification change recorded in [#239](https://github.com/fukuda-yuki/gh-projects-boards/issues/239), and it is the single contract the `#N` reference rule of [#237](https://github.com/fukuda-yuki/gh-projects-boards/issues/237) builds on: full-width ASCII forms (`！`–`～`, U+FF01–U+FF5E, which covers `Ａ`–`Ｚ`, `ａ`–`ｚ`, `０`–`９` and the full-width symbols) become their half-width forms, and the ideographic space (U+3000) becomes a space. Nothing is deleted, trimmed, reordered or case-folded, so `＃` becomes `#` and reaches the column rule, and `・`, `月` and `日` are preserved. The CSV file format keeps its own invariant forms.

- **Effort** (見積 h, 残 h, 実績 h): a nonnegative decimal person-hour number, optionally followed by the unit the sheet shows, `h`, or by `d` for whole days where one day is eight hours (`8`, `8h`, `1d`, `1.5h`, `８`, `１ｄ`). A Project NUMBER column takes the folded number without a unit. Anything else keeps 「工数は0以上の数値で入力してください。」 or 「数値を入力してください。」.
- **Dates** (開始日, 終了日 and DATE columns): `yyyy-MM-dd`, `yyyy/M/d`, `M/d` and `M月d日`, with `・` accepted where those forms show `/`, so `２・１０` is 2/10 and `１０月１４日` is 10/14. A form without a year takes the year nearest the 基準日 by the rule above. Anything else keeps 「日付は 2026-10-14、2026/10/14 または 10/14 の形で入力してください。」.
- **Choice columns** (工程, single-select columns, labels and milestones): the folded text is matched against the configured names ignoring case. Anything else keeps that column's message.
- **Predecessors** (先行): the folded text is a comma- or `、`-separated list whose entries are read one by one, from this folded text and nothing else, by the [task name grammar](#naming-a-task-in-先行) (#263). A bare number and `#N` both name Issue N; neither is ever read as a row position.
- **Assignees** (担当者): logins are matched as typed, without folding, because a GitHub login is an ASCII identifier; `ぺrそn` and `ｐｅｒｓｏｎ` are refused with 「担当者を確認してください: {value}」. A login that already names one of the Project's people (a stored person or an assignee the read returned) is matched locally and sends no request. Any other login is verified with one read-only lookup for that login against the row's repository before the cell commits. GitHub answers the lookup as a substring search on login and name ordered by login, so `rob` also returns `a-rob` ahead of `rob`; the lookup reads further pages only while none of the returned logins equals the typed one. A case-insensitive exact match on the returned login is accepted and registered as a stored person at 100% in the same Undo step and save as the assignment; no match, an inaccessible repository, a changed account or a failed lookup is refused at the cell with 「担当者を確認できません: {value}」, 「担当者のリポジトリを確認できません。」, 「接続先のアカウントが変わりました。再接続してください。」 or 「担当者の確認に失敗しました。再試行してください。」 and nothing is written. Pasted cells use the same rule, deduplicating logins per repository. A typed login that cannot be assigned never changes the row, the settings, the save revision or the Undo history and sends no mutation. While that lookup runs, the sheet status line reads 「担当者 {login} を確認しています…」 while the typed text stays in the editing cell; Escape, a cancelled operation or closing the workspace cancels the lookup and writes nothing, and the lookup never blocks the sheet's other input. A `;` separates assignment values like `,` and `、`.

While a 担当者 cell is edited — by typing, F2 or double-click — a list of the Project's known people opens under the cell, and Alt+↓ opens the same list from a selected cell that is not being edited. The list overlays the sheet: it inserts no line, reflows no row and moves no selection. Candidates are the people stored in settings plus the assignees the last read returned, each once; building the list makes no GitHub request. Each candidate shows the configured display name and the retrieved GitHub login, 「福田 有輝 · fukuda-yuki」, or only the one name that is known when they are the same. The list filters as the PMO types on both the login and the display name, ignoring ASCII case; the search text is the value after the last `,`, `、` or `;` separator, and full-width forms are folded for finding only, never for the login that is accepted. An IME composition changes the list only after it is confirmed. ↑/↓ move the highlight and wrap at the ends; Enter takes the highlighted person, or, with none highlighted, commits the typed text through the assignee rules above; Escape closes the list and leaves the editor with its typed text, and a second Escape cancels the edit. Taking a candidate replaces the value being typed with that login and commits the cell as one Undo step, so a second person chosen after 「;」 is added to the cell. The list applies only to the edited cell: one person on a selected range stays the existing Ctrl+D or paste and one Undo step. A typed login the list does not know still follows the rules above; when that refuses the value, the message stays at the cell and the list stays open with the closest known people, ranked by how many leading characters their login or display name shares with the typed value.

### Typed start moved by a predecessor (#229)

A typed 開始日 is the task's own plan start — a floor, start no earlier than — so a predecessor that ends later wins the scheduled start. The typed value is never rewritten: the notice says that this typed date lost and what the schedule holds instead. - The command is one ordinary 先行 cell operation: it removes exactly that predecessor, creates one Undo step, and the typed 開始日 then holds if nothing else constrains it. Closing the notice keeps the link and changes nothing.
- It appears only for a single typed 開始日 committed with Enter, Tab, focus departure or F2. 貼り付け, 下へコピー, クリア, Undo/Redo and a refresh never raise it, and a range commit raises no notice.
- It takes this one place in the selection line and moves no row. Its command and close control are ordinary focusable controls in the window's keyboard order with those accessible names; closing it by either one selects the 開始日 cell again, so keyboard focus returns there.

### Row state commands (#231)

**完了にする**, **中止にする**, **この版から外す** and **未完了に戻す** change what a task is in the version without leaving the plan. They apply to the rows of the selection, and a requirement row stands for itself and every descendant it can apply to, as with Link. Each command is one local operation and one Undo step; nothing other than the plan's own state changes until the PMO publishes.

- **完了にする** (open tasks): the row becomes locally complete (`Closed`). On the 基準日 it counts as done, so its remaining work leaves the schedule, the totals, the load and the forecast, its 終了日 is the provisional close day, and it is never late. On publish it sends `closeIssue` with state reason `COMPLETED`; the Issue's own 残 field is not written. After the publish the read supplies the close day and the ordinary closed-task rule applies.
- **中止にする** (open tasks): the row becomes locally complete **and** cancelled, so it leaves the schedule, totals and load like 完了, and its successors no longer treat it as a predecessor in the current schedule or in a later rescheduling. It keeps its stored values and stays in the plan. On publish it sends `closeIssue` with state reason `NOT_PLANNED`.
- **この版から外す** (rows that have a Project item): the row is marked as pending removal and contributes nothing to the schedule, totals or load, like 中止. On publish it sends `archiveProjectV2Item` for the item; the Issue and its field values remain on GitHub. Archived items are not returned by the default item read, so the row leaves the plan when a read no longer returns it — the read is not expected to report `isArchived`, and the removal is confirmed by that absence rather than by reading the item back. An archive becomes visible in the item connection about three seconds later, so a read immediately after the publish may still return the row; while the local removal is pending the row stays marked and the plan does not treat its return as a new task. Verified archived identities are remembered in the saved plan: when GitHub returns the item after an unarchive, the plan re-adopts the position the read reports and writes nothing for it, and the rule that a newly found Issue is placed after its parent's last child (#245) applies only to a genuinely new Issue.
- **未完了に戻す** (complete or cancelled tasks): the row becomes open again and keeps its dates, its remaining work and its values. On publish it sends `reopenIssue`. The read reports the open state; a `stateReason` of `DUPLICATE` or `NOT_PLANNED` reads as 中止, and any other state reason reads as 完了.

Eligibility is per row: a command applies to the rows it fits and skips the others without failing the whole operation, reporting how many rows it skipped and why (an unpublished row has no Issue to close, a complete row cannot be completed again, and so on). A selection where no row is eligible changes nothing and says so. Every command refuses while a remote operation runs.

The commands live in the **row context menu**, which opens with a right click on any part of a row (the ID cell, the 状態 cell, the fold control, or a cell that is not being edited) and from Shift+F10 or the menu key inside any cell. Opened from a cell, the menu starts with コピー and 貼り付け, which act on the selected cells exactly like Ctrl+C and Ctrl+V; a cell being edited keeps the text box's own menu for its characters. The menu holds 行を削除 with its Ctrl+- shortcut and the four state commands. The sheet's **overflow** (その他のオプション) also holds 行を削除 and the four state commands, with the same enabled state, hints, reasons and shortcut, so the keyboard and pointer routes never disagree. Right-clicking a row outside the selection selects that cell first, so the commands always act on what the PMO is looking at. An item is disabled with its reason when it cannot apply to any selected row (「この操作ができる行がありません。」, or the row-specific reason), and when it applies to some but not all it stays enabled and its tooltip states how many rows it will skip and why. A command that applies reports the pending operation on the sheet's status line — 完了にする（未発行）, 中止にする（未発行）, この版から外す（未発行） or 未完了に戻す（未発行） — followed by the skipped-row sentence when it skipped rows; choosing another row or cell dismisses it, and a history change (元に戻す/やり直し, Ctrl+Z/Ctrl+Y) dismisses it too so the report never outlives the operation it describes. No report claims a past-tense outcome before the publish confirms it. The Project read observes each Issue's `viewerCanUpdate`, and a row the viewer cannot update is skipped by every row-state command with 「この Issue を更新する権限がありません」: the command is disabled when no selected row may be updated, and stays enabled with that reason when only some may. That observation is a read result, not a plan value, so it never becomes an unpublished difference, a publish write or a conflict, and it is forgotten for a row the next read no longer returns.

A row whose state command is pending carries a tag naming the command that produced it — 完了にする, 中止にする, この版から外す or 未完了に戻す — in its タスク名 cell, and the same tag appears on the selection line with （未発行）. 中止 and この版から外す dim the whole row, write the task name in secondary text and carry the grey ⊘ mark for a set-aside task; 中止 is additionally struck through with a one-pixel line across its name, because a WinUI editable cell cannot carry a text decoration and the sheet never fakes one with italics. A pending 完了 keeps ordinary weight. These are row-state marks, not lateness marks, so they never use the outlined red/yellow grammar of 期限超過, 予定より遅れ and 見積超過. A locally completed row's 残 h and 終了日 are still read-only, but their reason becomes 「完了にする を発行すると確定します（未発行）」 (「未完了に戻す を発行すると編集できます（未発行）」 after a pending reopen) instead of the GitHub-owned sentence, which would claim a close that has not been published.

The review names each pending state operation in plain words before its field differences — 「GitHub: Issue を完了として閉じます」, 「GitHub: Issue を完了としてではなく閉じます（中止）」, 「GitHub: Issue を再オープンします」, 「GitHub: プロジェクトからアーカイブします（Issue とフィールドの値は残ります）」 — and lists only the writes the publish sends: a close or reopen adds its 状態 line (完了/未完了) but no 開始日, 終了日, 見込み残存工数 or 中止にする line, because those follow the close day the read reports; a pending この版から外す shows the archive line alone, since archiving sends nothing else. A row already changed elsewhere survives as an ordinary conflict line on the same field, and a failed or unverified write keeps the row pending with its reason (「発行失敗: …」/「未確認」) until 再試行 publishes again.

None of these commands reschedules another task's plan dates (#236). Their writes are planned per row, so one row's failure keeps that row's write pending with its reason and does not stop the others.

## Current planning editor scheduling contract (#78)

This section is the current contract for the new UI-independent `PlanEditor` model.

### Inputs, identity and calendar

- A task has an opaque Issue/local identity, a positive unique plan-row position, optional parent identity and predecessor identities. Positions are supplied by plan order, never recomputed by filtering; they are internal keys and are shown only through [task names](#task-names-263). External predecessors retain their reference, do not constrain dates and produce `プロジェクト外の先行タスク: {reference}`. References outside the Project have no plan-row position. Missing parents are external hierarchy boundaries, with `プロジェクト外の親タスク`; they do not create summary rows.
- Inputs retain Estimate, Remaining, Actual, assignees, closed state and local close date, current start/end and GitHub baseline start/end separately. Effort inputs are nullable decimal person-hours; valid effort is nonnegative, and the cell accepts the displayed `8h`, the day unit `d` at eight hours and full-width digits (see [cell text input](#cell-text-input-239)). Missing effort is not zero. Negative refreshed effort or inverted kept dates isolate that row as described below; nonpositive/duplicate row IDs, duplicate/empty identities and invalid settings still reject the calculation without changing inputs.
- Working time is Monday–Friday 09:00–13:00 and 14:00–18:00, excluding bundled Japanese holidays 2025–2027, additional dates from the existing validated holiday CSV importer and company days off. Imported dates supplement the bundle. Beyond the supplied holiday years, weekdays still apply and affected rows warn `祝日データの対象年外`.
- A single person's rate defaults to 100%; allowed rates are greater than 0 and at most 100%. Capacity is 8 hours times rate per day, spread uniformly across both work intervals (50% means 4 person-hours over an eight-hour day). No assignee or multiple assignees use the Project calendar at 100%; multiple assignees warn `担当者が複数`. No resource leveling occurs.
- 基準日 is the stored day of the latest successful first take-in, refresh or reset, unless subsequently picked by the PMO. Every calculation receives the caller's today; a fallback to that day is permitted only for a document never read under this rule. Core never reads the clock. Publishing, including its reconciliation read, preserves the calculation date. A failed or cancelled read changes neither the date nor the plan. Project start is optional. Day inputs become 09:00 boundaries. Internal working-hour endpoints use exact rational arithmetic derived from decimal effort and rate, only during recalculation, never in returned date cells or persisted inputs. No rounding to minutes or tolerance may move an endpoint across a work-interval/day boundary; successors inherit the exact endpoint, also across differing rates. A 4-hour task at 100% finishes at 13:00; its successor starts at 14:00 that day. At 18:00 a positive-work successor starts on its next working day. Kept start/end dates represent 09:00/18:00 even on nonworking days.

### Scheduling precedence and edits

Before these rules, isolate invalid row data as described below.

1. Summary rows roll up children as below, overriding their valid own scheduling inputs.
2. Only closed Issues are complete. Their Remaining is calculated as 0 and their end is the local close date, reason `完了`; their start follows the retained/adopted start rules, capped at the close date when it would be later. This cap is calculated; the resulting date pair is validated before publication or successor scheduling. Other inverted kept pairs remain invalid. The reader retrieves `closedAt` with state; the snapshot converts its UTC timestamp through an injectable TimeZoneInfo (production: TimeZoneInfo.Local). Closed and CloseDate are GitHub-owned row data, never locally edited; refresh clears the close date on reopening. A closed Issue without readable closedAt makes the reader incomplete and cannot replace the document; a direct Core input without a close date warns `完了タスクの終了日なし`. An open task with no positive Estimate or Actual and zero work remains a milestone and keeps its dates. An open positive-effort task with effective Remaining 0 is not complete and shows `残 0・未完了`.
3. Both Estimate and Remaining absent retain dates, reason `工数なし`.
4. Work is entered Remaining, otherwise max(Estimate − (Actual or 0), 0); when Estimate and Remaining are both absent it is unknown. **Start and end are plan values** (#236): a task that already has a start keeps it, so the earliest start is the maximum of that planned start, optional Project start and effective predecessor finishes. A typed 開始日 is therefore the floor of the schedule. The 基準日 is that floor only for a task that has no start yet, so a task receives its first dates no earlier than the 基準日 and no later refresh, 基準日 change or reset moves them (see the [refresh contract](#current-planning-editor-refresh-and-publishing-contract-79)). Normalize positive work to working time. Zero work has identical start/end at that boundary without calendar normalization, including open positive-effort work with zero Remaining. Estimate = 0, Actual > 0 and empty Remaining calculates 0 instead of isolating the row.
5. Actual > 0 and positive work retains the plan start; its end is the working day on which Actual + Remaining is used up from that start at the person's rate, so the result can lie before the 基準日 and the task's 終了日 has then passed (遅れ). Dependencies and constraints do not move a historical start; a start day before any effective predecessor's end day warns, while a start on that end day does not. A missing start uses earliest start and warns `進行中タスクの開始日なし`.
6. Other positive-work tasks calculate their end from the start and work/rate. Calendar adjustment does not replace the start reason.

Rescheduling is edit-driven, and the plan values are what it moves. Editing 開始日, 終了日, 見積, 実績, 残 or 先行, pasting, filling, CSV import, Undo/Redo, indent/outdent and moves that change inherited predecessors, and a settings change to the calendar or the Project start all reschedule the edited task, its transitive successors and the summary roll-ups as one Undo step, in the same calculation above: no separate command exists. A settings change reschedules the tasks that have dates; a task with no dates keeps none until a PMO edit gives it effort, dates or a predecessor. Nothing else reschedules — not 最新の情報に更新, not a 基準日 change, not GitHub の状態に戻す, not 担当者, 完了にする or 中止にする. A moved date is an unpublished date difference and the publish review lists it like any other change. A typed 開始日 remains the task's plan start — a floor, start no earlier than — and is never rewritten, but a predecessor that ends later still sets the scheduled start and the end the edit writes, so the 開始日 cell shows the scheduled date as calculated while the typed value stays the stored input. That commit is reported to the PMO once — whose typed date lost to which predecessor, the resulting date and the one command that removes that link — under the [plan sheet notice](#typed-start-moved-by-a-predecessor-229). A start moved only by the Project start is not reported.

Estimate is the original estimate; editing or clearing it never writes Remaining. Empty Remaining stays empty in the document and on GitHub: its default is calculated, editable secondary text and never published. Explicit Remaining uses primary text. A Remaining edit compares against the stored input, not its calculated display. Entering edit mode and committing the displayed default with Enter, Tab or focus departure stores it explicitly even when the text is unchanged; Escape cancels, and selection without edit mode never creates an input. The editor may initially show the calculated value. Subsequent Actual edits preserve an explicit Remaining. Forecast (見込) = (Actual or 0) + effective Remaining; variance (差異) = forecast − Estimate, unknown without Estimate. Open tasks with forecast above Estimate show 見積超過. These values are shared by scheduling and summary totals. Read-only summary task details display scheduled effective Remaining, including calculated defaults and closed zero, consistently with totals and load. Planning edits use the sheet. Core exposes Actual ÷ (Actual + Remaining) as the work-complete fraction, unknown for missing operands or zero total, with scaled arithmetic to avoid overflow. A forecast beyond decimal range is unknown and its overrun marker names the range error. Typing/clearing a start updates the plan start. Typing a nonempty end sets the plan end: that edit keeps the typed end on its task while its successors reschedule from it, and a later edit of the task's effort, start or predecessors recalculates it. Clearing an end reschedules the task. These pure input transformations are composed by the local document commands below. Estimate, Remaining and Actual edits reject a negative new value; start/end edits reject an inverted resulting pair when dates are kept, and a typed end before the start is rejected with 「終了日は開始日以降にしてください。」. An automatic start edit may move past an old GitHub end because its end is recalculated. Rejection throws a validation error and returns no replacement task, leaving the original input intact. A valid correction to one field is allowed while another refreshed field still needs correction.

Each date cell exposes its day value, `Calculated` or `Kept` origin and a boolean difference from the corresponding GitHub baseline (including null transitions). A plan start that the PMO typed or that a refresh adopted is Kept; a start or end the scheduler moved is Calculated. Valid summary cells are Calculated; isolated summaries keep their GitHub dates. Unchanged calculated values are not unpublished changes. Inputs are never overwritten by a calculation.

### Forecast (#236)

The **見込終了** forecast is derived on every calculation and is never stored, never published and never a plan value. It is today's scheduler with remaining work placed no earlier than the 基準日 and propagated through predecessors:

- An unstarted task starts at the latest of its planned start, the 基準日 and its predecessors' forecast ends, and its forecast end is that start plus effective Remaining at the person's rate.
- An in-progress task places its remaining work from the later of its plan start and the 基準日.
- A closed or 中止 task has no forecast, and its successors ignore it. A task whose end was typed gets a forecast too, and can be late through it.
- A task with no dates has no forecast until it receives its first dates, and a task without effort has none. It can still be late from its plan dates.
- A summary's forecast is the roll-up of its children's forecast, by the same minimum-start and maximum-end rule as the plan.

Because the forecast never feeds the plan, it changes no date cell, no unpublished difference and no publish write. It exists for 見込終了, the Gantt slip segment, the lateness sets below and the people load: an automatic task's remaining work is allocated on the days its forecast places it, so work waiting on a late predecessor is loaded after that predecessor's forecast end rather than on the 基準日.

### Lateness sets (#236)

Lateness compares the plan with the forecast and never with a previous publish or a previous read (#260). `PlanLateness` classifies every open task and exposes these identity sets of tasks (requirement rows never count), each reported as a count and usable as a filter:

- **遅れ, date passed** (the red 状態 mark): an open task whose planned 終了日 is before the 基準日, or an open task with absent or zero Actual whose planned 開始日 is before the 基準日. A plan date on the 基準日 itself does not count. A summary carries the red mark when a descendant is late this way. The tooltip reads 「終了日 11/10 を過ぎて未完了 · +2日」 or 「開始日 11/9 を過ぎて未着手」, adding the forecast slip only when the 見込終了 is later.
- **遅れ, forecast after 終了日** (the ochre 状態 mark): a task that is not late by a passed date whose forecast end is later than its planned end. The tooltip reads 「見込終了 12/3 (金) · +2日（自分の残による）」 or 「見込終了 12/3 (金) · +2日（先行 #193 の遅れによる）」. A task with a typed end and an in-progress task can be late this way; a task without effort cannot.
- **見積超過**: Actual + Remaining above 見積. The overrun shows as `+16h` in ochre inside the 見積 h cell, with the tooltip 「見積超過: 見込 32h（見積 16h）」; it adds no 状態 mark.
- **遅れの原因**: every passed-date 遅れ, plus every forecast-late task caused by the task's own remaining work. A task late only because a predecessor moved is not a cause.

A summary row carries the strongest mark of its descendants: red when a descendant's 終了日 has passed, otherwise ochre when it or a descendant is late or 見積超過. 残 0・未完了 carries no mark and no count on the plan sheet; closing it is 完了にする (#231). The old "calculated end later than published" meaning disappears with the moving dates: an edit's impact stays visible as an unpublished change and in the publish review.

### Hierarchy, dependencies and reasons

- A row with in-Project children is a summary. Each effort column sums direct children recursively. Estimate and Remaining sum the known values and keep, per summary, the number of leaf descendants whose value is absent (#245); a missing value is never shown as zero, and the count says how much the sum leaves out. Actual counts an absent leaf value as zero, as Forecast and the summary view already do. Overflow of the known sum is still `工数の集計が範囲外`. Start is the minimum available child start, end the maximum available child end; all absent yields absent. Its own valid effort/date/constraint/closed inputs remain intact but are ignored for summary scheduling; invalid data follows the isolation rule below. Removing its last child restores ordinary task semantics. Publishing writes rolled-up start/end but **not** rolled-up effort; no publish implementation is implied here.
- A predecessor link to a summary waits for its rolled-up internal end. A summary's predecessors constrain every descendant, including nested summaries. Completed/no-effort descendants still retain dates; in-progress violations warn. Duplicate predecessor references have no extra effect.
- Reject parent hierarchy cycles, dependency cycles (also those induced by summary roll-up/inheritance), self-links and any predecessor link between ancestor and descendant. Errors identify the involved tasks in plan order; the sheet shows them by task name, `循環参照: #12, #14`. Reject the whole calculation, with no partial result or input mutation. Unrelated descendants of a cycle are not named as cycle members.
- Exact start reasons: `基準日`, `プロジェクト開始日`, `{row position} の終了後` (displayed as `{task name} の終了後`), `開始日を維持`, `完了`, `工数なし`, `日付未定`, `子タスクの集計`, `入力エラー`. Dates use invariant M/d. For equal constraints, predecessor wins, then Project start, 基準日; a planned start participates in the maximum without replacing an equal constraint's reason; tied predecessors use the smallest plan-row position. A retained plan start, including an in-progress task's historical start, uses `開始日を維持`; a missing start uses the winning earliest-start reason. A valid summary uses `子タスクの集計`; isolated rows use `入力エラー`.
- Warnings are per row, unique strings. Refreshed negative effort, except ignored Remaining on a closed Issue, warns `工数が負の値`; an inverted kept start/end pair warns `開始日が終了日より後`. An unrepresentable calculated schedule warns `日程が日付の範囲外`; effort-total overflow warns `工数の集計が範囲外`. The affected row retains its GitHub baseline dates with Kept origin and reason `入力エラー`; inputs (including invalid values) remain available for correction, and no date change is proposed. Neither date is used as a dependency or summary endpoint. Invalid leaf effort is displayed as received, never included in summary totals.
- A summary containing an isolated child is also isolated, with `子タスクに入力エラー`, retained GitHub dates and unknown rolled-up effort. This propagates through ancestors instead of publishing incomplete summary totals/dates or constraining successors from them. Other children and unrelated tasks still calculate normally; hierarchy and dependency cycle validation still applies to every row. A summary's own invalid refreshed values likewise isolate that summary but do not stop its children.
- Scheduling is bounded by DateOnly's supported range, with no arbitrary short horizon. Dates/settings identities are not silently repaired. Structural errors and cycles remain whole-calculation errors; ordinary refreshed row data problems do not.

## Current local plan document, operations and storage (#78 / #79 / #81)

This section defines UI-independent local commands. Refresh, verified Issue creation, conflict resolution and publishing extend it under the current #79 contract below; ordinary local commands never contact GitHub.

### Document and atomic operations

- Project item order is the one authoritative row sequence. Opening, refresh and reset adopt it unchanged without implicit repair or local changes, with one exception (#245): an Issue that a refresh, or a publication read-back, finds for the first time (in neither the previous GitHub read nor the plan, so not one this app created) and whose parent is a plan row is placed after the last row of that parent's subtree, after any earlier such Issue there; its own newly found sub-issues follow it in GitHub order. Only those rows change position. The ordinary minimum-move comparison below decides which rows count as Order changes; when placed rows jump over more rows than they number (the usual case at version scale), exactly the placed rows count, and publishing writes their Project positions. A newly found Issue without a parent in the plan keeps GitHub's position. Placement is part of the merge, so historical states rebased by the same read place it identically; it adds no Undo step. IDs remain 1-based positions; no Order ID column exists. An unpublished Order change belongs only to the minimum set of moved rows: the complement of a longest increasing subsequence of baseline positions among identities shared by baseline and plan. New and deleted rows are excluded from this comparison. Among equally long subsequences, keep the lexicographically earliest sequence of positions in the current plan (prefer keeping rows encountered earlier in the plan). Rows merely shifted by those moves are unchanged. Counts, CSV export, discard counts, review and publication use this same comparison. Review shows each moved row with its baseline and plan position.
- MovePlanSubtrees moves roots and all descendants before an unmoving sibling or after the final sibling subtree. Mixed parents and invalid destinations reject the command. ArrangePlanOutline explicitly repairs scattered outlines with stable pre-order DFS, treating external parents as top-level. Both are one persisted Move Undo/Redo step, preserving identities, with no GitHub write until publish. No-op outline commands keep dates and history unchanged.

A document belongs to one normalized host, stable numeric GitHub viewer ID and Project node ID. Its immutable baseline holds the last retrieved Issue rows in Project order and the known mapped column identities/names. Each row retains identity, title, repository, Status and Phase option names, GitHub milestone title, closed state, assignees, predecessors, parent, Estimate/Remaining/Actual and start/end. CSV rows also retain the original-file SHA-256 as local provenance. Current rows and settings are separate from that baseline; no edit changes it. New rows use `local:<GUID>` identities until publication verifies an Issue identity. Order is the row sequence; displayed IDs are its one-based positions, never affected by filtering.

Each command builds and validates a complete candidate before replacing current state. Cell edit, rectangular paste, fill/Ctrl+D, Delete-clear, inserting one/many rows, deleting rows, indent/outdent, moving rows and settings replacement each create exactly one Undo step. A rejected command changes neither state, history nor the pending save. A no-op creates no history and does not discard Redo. A new effective command clears Redo. Rescheduling and date reasons use the Phase 2 scheduler and caller-supplied today; dates the PMO enters are document inputs, and derived forecast dates are never document inputs.

- Edits use typed Core values (text, decimal hours, DateOnly, boolean, identity lists or null), not locale-dependent string parsing. Estimate/Remaining/Actual/start/end pass through the Phase 2 transformations. Paste validates all cells and applies them in supplied order to a candidate (validate kept date pairs only after all cells, so a valid two-date paste can move both endpoints); an explicit Remaining cell therefore follows an Estimate cell when both are pasted. Fill/Ctrl+D snapshots the source inputs once and expands to the same atomic cell operation. Paste/fill never creates rows. Duplicate target cells in one operation are rejected. Clear uses null, empty identity lists or false according to the field; a ClearPlanCells command never targets タスク名, so Delete cannot empty a title. Only Title is editable among summary sheet cells; hierarchy changes retain their existing command contract. Edits, paste, fill/Ctrl+D and clear targeting any other sheet field reject the whole operation without changing the document, history or unpublished count. Effort and dates explain 子タスクから集計（編集不可）; the other fields explain 要求事項の行では編集できません.
- Insert inherits the in-plan parent of its Before row, otherwise null (including bottom insertion). Ordinary insertion accepts prepared local rows, defaulting an empty repository from settings; an explicit or default `owner/repository` is required. `PlanCsvImport` instead preserves its validated parent identities and submits parent-first subtrees and newly resolved people through the CsvImport path, splicing children of existing parents at their subtree tails and appending other subtrees. Undo removes imported rows and people; Redo restores their exact identities, relationships and file provenance. Closed state is a retained GitHub input, not an Issue-administration command.
- Delete rows (#247) removes the selected rows with their whole subtrees as one command and one Undo step, restoring rows, values, relationships and positions on Undo. Only rows with no GitHub counterpart are deletable: when any row of any selected subtree is a baseline (published) row, the command is refused whole and changes nothing, with `GitHub の Issue は削除できません（#N）。完了・中止・この版から外す を使ってください` naming the first such row by task name. Deleting an Issue stays on GitHub; 完了・中止・この版から外す belong to #231. The deleted identities are removed from the surviving rows' 先行 memberships, and the survivors the removal reaches — successors and parent roll-ups — are rescheduled.
- Indent applies to selected consecutive siblings and reparents them under the preceding sibling. Outdent reparents selected siblings to their parent's parent; a missing/external parent cannot be outdented. Outdent moves the selected subtrees immediately after the former parent's whole subtree, preserving their relative order and leaving remaining sibling parents unchanged. The internal MovePlanRows primitive places exactly the selected rows, preserving their current relative order, before a specified unselected row or at the end; it does not implicitly move descendants or change parents. Invalid identities, hierarchy or dependency cycles reject the complete command.
- Undo/Redo restores exact row inputs, relationships, order and settings using before/after patches. Local edits leave the baseline unchanged. Keep at most **200 effective operations** in the combined Undo/Redo chain, dropping the oldest reachable Undo step when necessary. Persist changed rows, changed order and changed settings per step rather than 200 copies of the whole Project. Verified publication promotes created identities; published creation is a history barrier while subsequent edits remain undoable.

Closed rows reject edit, paste, fill and clear of Remaining and End atomically without document or history changes. The sheet uses the same Core read-only rule as commands and shows `完了したタスクは Issue のクローズで確定します（編集不可）` in the selection line. Summary details show a plain, non-editable Remaining value without TextBox chrome. Other fields remain editable, subject to the existing summary rule.

Every automatic/recalculated field change requires a mapped column before it counts as unpublished or enters the publish plan. This includes ordinary and summary scheduled dates, closure-adjusted Start/End and closed Remaining 0. Unmapped calculations remain visible and usable locally, but create no corner marker or write; explicit inputs still require their field mapping to publish. Closed leaf Remaining compares calculated 0 with baseline Remaining; its end compares the close date with baseline End, subject to this common mapping rule. Both differences use corner markers without PMO tint and publish through the existing field plan. Other unpublished fields compare current inputs with the baseline: title, repository, Status, Phase, assignees/predecessors as sets, parent, Estimate, Remaining and Actual. Start and end compare the plan dates with the baseline dates, so a date the scheduler moved for an edit counts as a calculated difference and a plan date that already equals the baseline creates none. A new row has a NewTask marker regardless of its values. Order compares positions among baseline rows, ignoring inserted local rows (inserting one task does not mark every existing task). Reordering existing rows marks every existing row whose relative position changed. The unpublished task count is the number of distinct rows with any marker, including affected summaries. Local settings alone are not GitHub fields; their changed calculated dates can create markers only for mapped columns. Closed tasks ignore stored Remaining entirely, including negative values, for validation and scheduling; effective Remaining is zero and successors use the close date. Other negative refreshed inputs remain intact under Phase 2 row-isolation rules; commands cannot introduce new negative effort. Unrelated edits do not revalidate an unchanged invalid refreshed date pair; editing start/end, or changing an automatic task to kept-date semantics, must leave a valid kept pair.

### Settings file

Store column mappings for the six planning roles (Estimate, Remaining, Actual, Start, End, Phase), each with a GitHub field ID, name and expected NUMBER/DATE/SINGLE_SELECT type. Mappings may be absent until configured; duplicate roles or reused field IDs are invalid. Known baseline column definitions remain separate from settings. Settings also hold company days off, imported holiday dates and coverage/source metadata, people (stable identity, readable name, rate and nullable nonnegative whole-Project allowance), optional Project start and end, optional phase-to-milestone title mappings, optional default repository and persisted 基準日. Bundled holidays remain a product resource, not repeated in the settings file. The ordered sheet-column choices store stable source keys, visibility and optional display names. They are portable settings, included in export/import and persisted across restart. Clearing a display name restores its default. Hiding a column retains all local values and unpublished changes.

Export writes a versioned, indented UTF-8 JSON settings file, containing no document rows, account binding or history. Import validates the entire schema and all values before replacing portable settings as one Undo step. 基準日 is not portable: import ignores the file's `statusDate` (including null) and preserves the document's current 基準日. Export may include it. Duplicate people/dates, invalid rates/allowances/repositories/mappings, malformed holiday data, unknown JSON properties and unsupported versions are rejected without any document/history change. Explicit null/default settings remain distinct. An imported person absent from baseline assignees, or a field ID absent from baseline column definitions, is retained and reported as `プロジェクトに未確認の担当者: {name}` / `プロジェクトに未確認の列: {name}`; no network lookup, silent dropping or remapping occurs. A stored person with no assignment in this Project keeps their rate and allowance in the file but is not listed in 担当者 settings or counted in the summary until a row holds them again; no migration prunes such entries. Settings have no embedded account scope and can be imported into another data root. Existing-file export replacement is atomic and explicit through the export call.

Settings files and local documents reject unknown properties, including `daysOff` on a person. No migration is provided, except that the lateness mark switches an earlier version stored as Project settings (`showOverdueMark`, `showLaterMark`, `showOverEstimateMark`) are dropped when a plan or settings file is read, after their one-time carry-over to this PC's display preferences ([lateness marks](#columns-and-presentation)). Before updating, publish local work; a stored plan written by an earlier version opens as [unreadable](#autosave-isolation-and-recovery) and is recovered by reading the Project from GitHub again.

### Autosave, isolation and recovery

Use `<resolved data root>/PlanningEditor/v1/`; resolve `GHPB_DATA_ROOT` as an absolute root when set, otherwise use `%LOCALAPPDATA%/GhProjectsBoards/Registrations`. Use a SHA-256 filename of host/viewer/Project and repeat that scope inside each versioned checkpoint. Never enumerate, read or migrate legacy files outside this new subfolder. Persist baseline, current inputs/settings and Undo/Redo patches together in one atomic checkpoint. No tokens, credentials, scheduler output or transient selection/scroll state are part of the schema. Immutable collections prevent later caller mutation of queued saves or history.

A committed command updates memory synchronously, then schedules autosave on a **single background writer**. Consecutive pending revisions can coalesce into the latest checkpoint, which still includes every retained Undo step. Serialization, file I/O and durable flush never run on the caller's edit path. The returned save task reports durability or failure; `FlushAsync` awaits the latest state before a normal close. An abrupt process exit before successful flush can lose the unsaved tail; never report that tail as durable. This is separate from the 0.2-second edit-to-screen target.

Reuse the existing temp-file / durable-flush / readback / File.Replace (or first File.Move) mechanism, with a last-good `.bak`. A per-Project exclusive writer lock and expected SHA-256 of the loaded/saved file prevent competing or externally changed files from being overwritten, even if a revision number was reused. Check scope, schema, current document and every reachable history state both before replacing the checkpoint and when loading. A primary file that exists but fails parsing, the current schema or validation (an earlier version's format, or damage) returns an unreadable result; transient I/O/access errors and interrupted storage return a blocked result. Neither creates a new session or modifies the file. Unknown `.tmp` candidates or a backup with no primary file are reported as interrupted storage, never silently adopted or discarded. A live writer may remove only its own failed temporary candidate so a retry remains possible.

Any failed save leaves the latest in-memory document and history intact. Transient I/O/access errors return a retryable result; explicit retry writes the latest state, not an older snapshot. A source file that another window or another app saved returns a non-overwrite result that the unchanged retry cannot resolve, so it is never presented as the way out: the workspace names that cause and offers both escapes from the refusal. **Reload and reapply** loads the stored checkpoint, replays this window's edits that were not yet stored onto it, validates the merged document and saves it, so both writers' work survives; a merge that cannot be validated is refused with the conflict state and the edit kept. **Save as a copy** writes this window's checkpoint to the path the PMO chooses and leaves the stored plan exactly as the other writer left it. Changed or corrupt source files still cannot be bypassed by a normal save, and a reopen that would adopt them still requires the named recovery path. New-session creation is permitted only after a missing-file result, and races are checked again under the writer lock. Successful writes update the expected fingerprint; older writes cannot supersede newer in-memory operations. There is no background publish.

Opening a Project whose stored plan is unreadable, including the automatic reopen when connecting, shows the work-card InfoBar **計画を開けませんでした** (`PlanOpenFailure`), not a save failure. Its message names the Project, explains that the plan stored on this PC cannot be read because it was saved by an earlier version or is damaged, states that **GitHub から読み直す** keeps the stored plan under another name and opens the Project from GitHub, and that this PC's unpublished changes are not carried over; the technical detail follows. Connecting still lists the Projects, so another Project can be chosen instead. **GitHub から読み直す** (`PlanReadAgain`) runs under the writer lock only while the stored plan is still unreadable: it renames the backup and then the primary file to `<file>.unreadable-<UTC yyyyMMddHHmmss>` (backup with a trailing `.bak`) in the same folder, never deleting or overwriting either, and opens the Project as a first open. The bar closes when another open or connection starts.

Verification adoption uses B/L/R merging for fields outside the publish, including unrelated remote updates in retained Undo history. Intended unfinished published values remain local. Newly discovered remote rows are retained consistently across every historical order, including after refresh, Undo, save and reopen. Placeholder substitution applies only to identifier input fields; title/body/text values are literal. Issue creation uses persisted start-to-start reservations and a rolling-minute bound; request time overlaps pacing waits, and server backoff is honored on resume. See the [pacing decision](decisions.md#throughput-targets-for-79).
The refresh snapshot reads the built-in Status single-select option's display name independently of optional planning-column mappings; an unavailable or unknown option is a read failure, not an empty Status. Summary-row Estimate, Remaining, Actual, assignee, predecessor, Status, Phase and constraint differences are excluded from unpublished counts as well as writes, including when an earlier effort edit becomes a summary after indenting. Hierarchy publication completes all removals before additions and then reprioritization, stopping dependent phases after a failed batch. Selected publish/live failure reasons include GitHub's error type and a bounded, single-line message with credential-like text redacted; generic transport diagnostics still omit response messages and payloads.

GitHub planning date values use Gregorian `yyyy-MM-dd` with invariant culture; numeric serialization and comparison are also culture independent. The current Windows culture must not change published values or verification.

A parent's children are displayed in the plan's row order, which is the Project item order; the native sub-issue order never selects or sorts displayed rows, so a parent whose two GitHub orders differ displays the Project item order with no unpublished change, no review line and no reorder write. A parent has a child-order difference only when the plan's child order differs from both the baseline child order (the Project item order as read) and the native sub-issue order the plan retains; that one comparison drives the unpublished count, the review line and the relative-order write, so an affected parent counts once and an unchanged order produces no review line. The review shows that difference as the retained native order → the plan's current child order. A parent with fewer than two current children has no relative-order write; relationship additions/removals are reviewed on the affected child, and a remaining child group whose relative order did not change is not rewritten. Children the last read could not deliver keep their displayed position and are excluded from the comparison. When a native-order entry is absent, the comparison uses the baseline child order rather than inventing an empty order; refresh supplies the observed native order. A reorder whose write failed stays pending while the plan still asks for that same order, so an explicit publish retries it. Verification of a publish phase replaces failure records for the identity/field pairs that phase processed and retains unprocessed failures only while they still represent a requested, publishable change. Obsolete failures for converged values or fields excluded from summary publication do not block completion. Successful creation and Project addition preserve still-requested reorder retries for the following phase. Choosing the local side of a child-order conflict retains that order as publish intent even if refresh has advanced the Project baseline to the same order; choosing GitHub cancels that intent. The choice is durable and undoable, and reset discards it. A reorder request writes the parent's complete child order, so a child the PMO did not move takes its plan position on GitHub. On a read, a child-order difference from the baseline child order, a failed reorder still requested by the plan, or an explicitly retained local conflict choice makes a remote native reorder a concurrent divergence to resolve; a remote-only reorder is adopted into those sibling slots when the plan's child order still equals the native order read before it. The evaluation baseline includes native sibling order. Sibling order is tracked and published only for parents that are rows in the current plan; external/archived parents retain their relationship references without a sibling-order conflict. Copying an unavailable task to a new Issue resets Closed to false, CloseDate to empty and Status to empty, while retaining reproducible planning inputs. Only publishable extra values (TEXT, NUMBER, DATE and SINGLE_SELECT) are copied. Read-only, unavailable, unsupported and deleted extra values are omitted. Cached extra observations of standard-owned fields are not copied; the standard roles alone supply their publication values. Verification cannot report publish success while blocking conflicts or unavailable tasks remain, even when the unpublished task count is zero.

### Publish invariants (#79)

- **I1 — Publish outcomes are not Undo state.** History restores local inputs, settings and explicit conflict/unavailable-row dispositions only. It never stores or restores a publish attempt, dispatched/acknowledged writes, verified baseline values or GitHub identities. Title correction and its Undo/Redo may change the input of a definitely unsent/rejected creation, but never a dispatched creation's reconciliation marker or obtained identity. Once creation is observed, its identity is promoted throughout retained local history; an insertion cannot be undone into eligibility for another creation. Later edits remain undoable. Recovery reconciles the retained attempt before planning writes from the latest local inputs, without replaying verified operations. Restoring an unavailable row restores only that row's last-known content, never another row's newer baseline.
- **I2 — Nothing sent, nothing locked.** Identity, complete-read/conflict, field mapping and repository existence/archive/Issue-creation permission checks precede recording a new attempt. If an attempt stops before dispatch, its pending record and wait deadline are released. Local editing, settings correction, Undo/Redo and refresh remain usable, including after restart. Opening a checkpoint containing only Pending writes and no dispatch fact releases that never-dispatched attempt before editing. A dispatch fact survives an absent-result lookup and an incomplete Project read; Pending alone is not evidence that nothing was sent. Once a mutation may have been sent, its outcome remains durable until reconciled; settings and identity-removing operations cannot invalidate that reconciliation.
- **I3 — Relationship phases never pass through a cycle.** For hierarchy and blocked-by relationships, remove all obsolete edges across every row and batch before adding any new edge; hierarchy ordering follows additions. A failed removal stops dependent additions and ordering. The final intended graph is validated locally; remote readback establishes the resulting graph.
- **I4 — Persisted history is always replayable.** Every reachable Undo and Redo state must satisfy the document and publish invariants. Remote adoption (refresh, publish verification and identity promotion) rebases both directions and validates each reachable state before persistence. At the first invalid step, drop that step and all older/further steps in that direction; retain the valid prefix and the other direction. History cannot remove identities needed by a dispatched attempt or change its settings. Validate the serialized checkpoint with the same validation used at load before replacing the last good file. A local edit, Undo or Redo adds or moves one step on a history that already satisfied I4; when stepping it back reproduces the previous document (no publish attempt, and the step restores its baseline and dispositions exactly), every other reachable state is unchanged and is not replayed again, so the edit-to-screen cost does not grow with the history (#256). Any other change replays the whole history.

A Project traversal with changing page totals is classified as concurrent change. Refresh, publish preflight and publish verification retry only classified concurrent change, using a fresh read each time — the complete traversal for refresh and reset, the scoped item read for publish preflight and verification (#201): **at most three attempts, three seconds between attempts**. Other incomplete, permission, malformed-response and cancellation outcomes are not treated as churn. No non-Complete traversal is adopted into local inputs, baseline or history. Exhaustion returns a retryable message with outcome/problem classifications, never source payloads. A complete traversal is required before any subsequent mutation.

When a post-write verification read remains non-Complete, rows with dispatched/acknowledged writes are **unverified**, not verification failures. Their attempt, identities and outcomes survive restart and local Undo/Redo. Refresh can reconcile them without mutations; a later publish first reconciles them and only then derives further writes. A response alone is not complete verification, and an incomplete read cannot authorize blind resend. Creation/membership recovery completes before planning remaining fields and relationships from the latest local inputs.

## Connection and API access

- Startup is local. Manual checking detects or uses the selected gh executable, reads its version and active authentication metadata, and obtains the stable numeric viewer ID from `/user` on the explicit hostname. Authentication JSON content determines validity even when `auth status` exits with zero.
- A connection binds hostname, stable viewer ID, and gh executable. Rechecking does not adopt a different binding. Reads and writes recheck authentication and identity immediately before dispatch; mismatches permanently invalidate that context. An explicit new connection creates a new binding. Checked connection state is in memory; a saved profile does not restore authentication.
- Project URLs in the workspace chooser must be HTTPS on the selected host, with explicit repository/owner and number. Each diagnostic independently reports read access, `viewerCanUpdate`, and the relevant OAuth update scope. Absent metadata stays unknown. After a successful explicit connection, the workspace discovers the viewer's owners and reads an owner's Projects when it is selected in the chooser. Opening a Project retrieves its tasks; connection never creates fields or publishes. Actual permissions and scope presence are separate; neither alone proves a later mutation will succeed.
- Only stored gh authentication is used by child processes. The four token environment variables are excluded without altering global settings. Authentication metadata is projected without the token field. Plaintext storage exposes the `hosts.yml` path and blocks writes; unknown storage blocks writes too. Reads remain available for diagnosis.
- The app never retrieves, stores, or displays credentials. Raw stdout/stderr and payloads are transient parser inputs, not logs or diagnostic output. Safe diagnostics expose outcome, HTTP status, exit code, classified error codes, and timing; remote error messages are omitted.
- REST and GraphQL use explicit host and target, `ArgumentList`, and UTF-8 JSON stdin. No shell interprets the payload. Child prompts, debug output, telemetry, and implicit gh host/repository overrides are disabled.
- The default timeout is 30 seconds per gh process, including stdin transfer. Cancelling or closing the window terminates the owned child process. Multiple commands can make the overall connection check longer than one process timeout.
- Results distinguish success, failure, cancellation, timeout, and unknown outcome, retaining available data and classified GraphQL errors. Partial GraphQL data is not complete success. Interrupted dispatched writes and potentially applied server failures are unknown; preflight failures establish that the target write was not dispatched. No automatic retry is performed.
- A lost or timed-out connection that stops an operation is reported as a connection problem: 「GitHub に接続できません。ネットワークを確認してください。」. The authentication/permission message 「発行に必要な認証またはアクセス権を確認できません。」 is used only when authentication or permission actually fails: not logged in, expired credentials, a missing `project` or `repo` scope, plaintext or unknown credential storage, or a permission denial. Opening a Project, 最新の情報に更新 and publishing apply the same distinction; a refresh stopped this way shows the connection message in its work-card failure bar. A GitHub response that arrived but whose outcome cannot be confirmed is not reported as a lost connection.

Preflight cannot atomically lock gh authentication against changes made by another process between the identity check and API dispatch. Do not switch external gh authentication during an operation. Eliminating that race would require a different credential/session mechanism; token extraction is outside this design.

GHEC + EMU IdP/browser authentication, enterprise host behavior, organization policy, required scopes, proxy/TLS connectivity, credential-store availability, and executable restrictions remain unverified until tested in the company environment under [#92](https://github.com/fukuda-yuki/gh-projects-boards/issues/92).

## Data identity and availability

Keep Issue fields, Project item fields, and application work state distinct. Share the same Issue's body fields across Projects while retaining each Project item's own values. Missing, unreadable, unsupported, and explicitly empty values are different states. See [#6](https://github.com/fukuda-yuki/gh-projects-boards/issues/6).

### Bounded Project read contract

The Core Project reader accepts an explicitly selected Project node ID bound to the existing connection's host and stable viewer ID. It uses the guarded connection service for every page. It performs queries only, with the same identity preflight, credential isolation, per-process timeout and cancellation as other reads. PlanWorkspace owns Project discovery and navigation.

Each returned Project has a stable owner ID, node ID, number and URL. Repository and Issue identities also include the connection scope. Items retain their own node ID, content identity, archived flag and field values. Issues are indexed separately from items: two Project results refer to the same logical Issue key, while their item values remain independent. These are immutable read observations; there is no cross-result cache, automatic synchronization or draft state.

| Data | Read behavior |
| --- | --- |
| Issue title and Open/Closed state | Loaded directly from the Issue, never through a field display name |
| Issue state reason | Read with the state, so `NOT_PLANNED` and `DUPLICATE` are distinguishable from `COMPLETED` (#231) |
| Project NUMBER and DATE | Exact numeric spelling and day dates, with empty/unavailable/unsupported values distinguished |
| Issue assignees, blocked-by, parent and sub-issue order | Complete paged relationships by Issue identity |
| Project single-select, including Status | Field ID, Project ownership, option IDs/names and selected option ID |
| Issue-derived fields exposed by a Project (title, assignees, labels and the like) | Ownership and Project field identity/type retained; their projected values are unsupported |
| Organization Issue Fields exposed by a Project (#258) | A field with `isIssueField` whose organization definition `issueField` is a date, number, text or single-select field is Present: the organization field ID and, for a single select, its option IDs and names come from `issueField`, because the Project side reports `options: []`. The value comes from `ProjectV2ItemIssueFieldValue.issueFieldValue`; the wrapper has no ID, so the inner value's ID is the value ID, and a null inner value is Empty. A multi-select Issue Field, or one whose organization definition is not returned, keeps identity and type as unsupported. The Issue's `viewerCanSetFields` is read with the Issue |
| Other Project fields | Identity, type and known ownership retained as unsupported; unknown ownership stays unknown |
| PR / GitHub Draft | Explicit item kinds with content IDs; no ordinary Issue or local-new-row conversion |
| Redacted/null content | Unavailable content with the Project item identity retained |
| Unknown item/value types | Explicitly unsupported, retaining encountered type and available IDs |

Field names and option names are display metadata, never identity or destination selectors. Native Issue properties use their Issue identity and typed title/state properties; a same-named Project field has its own field ID. The bounded editor additionally reads dated Issue and Project viewerCanUpdate observations. Missing/denied observations do not enable editing; creation and remote updates require the explicit publish contract.

The reader traverses Project field definitions, items and every implemented item-value connection to the terminal page, including more than 100 entries. The items connection walks light pages of at most 100 item IDs with total counts and cursors. Detail requests use nodes(ids:) with at most 25 IDs and at most six concurrent sends, overlapping the walk. Details are accepted in traversal order as soon as preceding batches arrive; all reader state changes remain serial. Missing detail nodes indicate concurrent change; mismatched identities are scope errors. A stopped read starts no further requests and observes all in-flight requests before returning. It checks node/ownership identities, duplicate fields/options/items/Issues/value IDs, duplicate field assignments, repeated cursors, missing paging metadata and inconsistent total counts. On API or structural failure it stops further requests, retains already observed data and reports a classified problem. The reader itself does not retry; planning refresh and publishing apply the bounded concurrent-change snapshot retry policy.

Detail failures containing only GraphQL `NOT_FOUND` errors, each with an exact `nodes` index path pointing to a null node, are concurrent change without an API problem. Other errors retain their API failure classification. Concurrent lease responses retain the latest Retry-After deadline; a shorter deadline cannot shorten an existing wait.

Result outcomes are Complete, Partial, Failed, Cancelled and TimedOut. Cancellation/timeout can retain a partial Project. Per-connection completion flags describe traversal, not universal support or readability. A Complete result means the requested traversal completed without detected problems; it can contain explicitly unsupported fields and known unavailable items. It does not establish a transactionally consistent snapshot: GitHub does not pin successive queries to one revision, and equal-count concurrent replacements can escape count/cursor checks.

A publish does not use this complete traversal. It reads only the items it is about to write, by node ID: each batch of requested Issue identities is resolved to its Project items and those items are read with their Issue fields and field values in one request, so the read never walks the Project item connection (#201). The Project, field and option metadata is read once when that scoped read starts and is reused by the writes and by their verification; a publish repeats neither of those metadata requests. Refresh and reset keep the complete read.

Values distinguish Present, Empty, Unsupported, Unavailable and NotLoaded. An explicit null option, or an absent supported field after a complete, error-free traversal, is Empty. On a partial read, nulls become Unavailable and absent supported fields stay NotLoaded; redacted content never implies an empty Issue or field. Unknown option IDs retain the observed ID as Unavailable. Partial GraphQL data is retained but never treated as complete. Missing or unsupported data cannot authorize clearing or deletion. The reader is query-only; publication belongs to the explicit publisher boundary.

The scheduling contract above defines the supported work/date/relationship model. Unsupported and unavailable observations remain distinct from empty values.

Schema references: [GitHub Project types](https://docs.github.com/en/graphql/reference/projects), [Project API queries and redacted items](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), and [cursor pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api).

## Current planning editor refresh and publishing contract (#79)

A successful PMO refresh sets 基準日 to the read day and merges local work. The read is not an Undo step: rebase both sides of historical settings patches to that date, remove empty settings/operation patches, and retain unrelated edit Undo/Redo. **A refresh moves no task date.** Start and end are plan values, so merging, the new 基準日 and the new forecast change none of them and create no unpublished date difference. The one date a refresh does change is the end of a task the read finds closed since the last read: closing is a fact from GitHub, its 終了日 becomes the close day, and the next publish writes it. Successors follow through the forecast only. Publication reconciliation does not advance 基準日.

A complete read reports its result only at the right end of the [attention strip](#attention-strip-and-filters-260--227--238) (#238): its time, conflicts and the Issues it placed in the plan. No result bar opens and no row moves on screen: the rows, the scroll position and the selection stay where they were, and only values, marks and counts change. Lateness, 未更新 and the other counts are the strip's own toggles.

The **最新の情報に更新** split button keeps refresh as its primary action. Its menu offers **GitHub の状態に戻す…** for the whole Project; there is no per-Issue discard. Reset is available even at zero unpublished tasks. It is disabled during any remote operation or while `Sync.Publish` is non-null or `Sync.Unverified` is nonempty, with the accessible explanation **発行の結果を確認するまで使えません** for unreconciled publication. Verified failures do not block reset.

Reset uses the same complete, consistent read as refresh and sends no mutations. Failure, incomplete reads and cancellation before adoption leave the document, history, sync and 基準日 unchanged. Inside one locked transition, adopt the successful refresh (including today's 基準日 and rebased history), then record one Reset operation. That operation replaces planning inputs and ordering with the fresh GitHub values, removes local-only and unavailable rows, clears conflicts and verified failures, and takes GitHub's dates as the plan dates. Local calendar, rates, allowances, people, column mappings, default repository and project start/end remain unchanged. Unavailable baseline rows are discarded through the existing reversible row-disposition patch. Undo restores the merged local work, new rows and conflicts over the fresh baseline and leaves earlier history undoable; Redo reapplies reset. Undo also restores still-requested failed child reorders as order intent, without restoring historical failure outcomes. No publication outcome is stored in Undo.

The confirmation title is **GitHub の状態に戻しますか？**, with primary **GitHub の状態に戻す**, close **キャンセル**, and Cancel as the default. It names the Project: 「<title> の未発行の変更をすべて破棄します。」 Core supplies the task counts: a new task or a task with any Entered unpublished field counts as entered; all remaining unpublished tasks count as recalculated-date only. Show the total, nonzero entered/recalculated lines and new-task subset; at zero show **未発行の変更はありません。**. Show 「基準日は M/d (曜) になります。」 only when the 基準日 is not already today, then 「「元に戻す」で取り消せます。」. GitHub's dates becoming the plan dates and the retained local settings are documented in the manual, not repeated in the dialog. The existing work-card panel shows **GitHub の状態に戻しています** and refresh read steps. Completion announces **GitHub の状態に戻しました** and uses the existing informational bar with title **GitHub の状態に戻しました（M/d H:mm）**, message **基準日を M/d (曜) にしました。日程は GitHub の値のままです。**, and no filter button.

A first take-in and a reset always show GitHub's dates as the plan dates, so without other local changes 未発行 is zero, no date difference exists and no recalculated marker appears. Lateness is computed from those dates and the forecast as usual, and people load follows the forecast. A stored start that no predecessor or Project start pushes later is shown as stored, even on a non-working day; only a PMO edit that reschedules the task moves it to a working day. The selection start reason is the ordinary winning reason; isolated rows keep **入力エラー**, their warnings and their exclusion from people-load allocation while still displaying GitHub dates. There is no persisted hold and no release step: the next accepted planning command reschedules only what it affects, and no command reports a whole-plan recalculation.

Sub-issue reprioritization and Project item positioning use one mutation per serial request. Each move depends on the preceding order; retrying only failed aliases from a mixed-success batch cannot preserve that order.

Refresh accepts only a complete, Project-scoped read, including all field values, native Issue relationships and item order. Drafts, pull requests and inaccessible items are counted but never scheduled. A REDACTED item with null content is a valid complete observation; its field values are unavailable and are not traversed. It still counts as a delivered Project item. Project item traversal completes at the end of a valid cursor chain even when fewer nodes arrive than totalCount: totalCount minus delivered unique items is added to the inaccessible count, alongside delivered REDACTED items. Short or empty intermediate item pages may continue with a valid next cursor. Duplicate identities, null nodes, repeated or missing next cursors, GraphQL errors, changing totals during traversal and delivered counts above totalCount remain failures. Other field/value/relationship connections retain their strict completeness checks. The live-proof reader uses the same rule. Failed or partial reads leave the entire local checkpoint unchanged. Merge compares each field against the previous baseline: unchanged local values adopt GitHub; unchanged GitHub values preserve local work; equal changes converge; differing changes retain an explicit conflict until the user chooses a side. Resolution is one local Undo operation. Merging moves no plan date; a later PMO edit reschedules only the task it touches, its transitive successors and the roll-ups.

A publish does not use that complete traversal (#201). Before the writes it resolves the rows with an unpublished change to their Project items by node ID and reads those items with their Issue fields, relationships and field values, together with the parent of every row whose child order is written; after the writes it verifies the same items and the Issues it created, resolving each created Issue's membership by node ID instead of re-reading the Project. A scoped snapshot carries every row the read did not cover over from the local baseline, so merging, verification and adoption still see a whole Project in which only the written rows were re-observed. A change to a written item is still a conflict and is not overwritten; a change to an item this publish does not write is not seen by the publish and arrives with 最新の情報に更新 (#201). An incomplete scoped read adopts nothing and asks for a refresh, exactly as an incomplete complete read does. The Project's item order is not observable per item: a position write whose item the read returns is treated as applied, every successful position write advances the baseline order to the reviewed order, and a failed one keeps the previous order so the next publish still sees the move; the true order is re-observed by the next complete read.

When progress changes an automatically scheduled task into in-progress or completed work, previously unused null date inputs are not date-clearing intent. Adopt the known GitHub start when an unstarted task begins or completes, while completion derives the end from the close date. Refresh uses the complete incoming snapshot; a local progress edit uses the current baseline. Preserve locally provided date inputs, date conflicts, and explicit clears made while the corresponding date was already retained. Missing GitHub dates remain missing. This adoption belongs to the same local operation or remote merge and follows its Undo/history rules.

Removed or deleted remote tasks remain visible as unavailable conflicts, retaining their local content and preventing publish. Resolution discards the unavailable task and its local relationships, or copies it to a new local task; it never recreates an Issue implicitly. Refresh replaces the baseline only after the complete merge has been saved. Unresolved conflicts survive refresh and restart. Conflicts remain stored when a task becomes a summary. Core determines publish-blocking conflicts from the current document: conflicts on the eleven non-title summary sheet fields are inapplicable while that row has children, so they are neither presented nor blocking. When the last child is outdented or removed, or hierarchy is undone, the same stored conflicts become visible and block publication again. Explicit conflict resolution still removes only the conflict being resolved; resolving a parent conflict immediately reevaluates applicability. Blocking-conflict review rows, sheet conflict indicators, publish enablement and Core publication guards use this same predicate. A disabled publish confirmation always has a visible reason on the review page. Hierarchy and order conflict contracts remain unchanged. Summary effort roll-ups never count as unpublished changes because only their start and end dates are published.

A new row without a title is not reviewed as a write: its group reads 「タイトルのない新しい行 n 件は発行しません」 with each row's task name (新N) and offers 行へ移動 (selects the row and focuses its title) and 行を削除, it does not count as a writable task, and everything else in the review publishes normally. Writes that would reference a row this publish does not create — its children's placement, 先行 links to it, its sub-issue order and its Project-position anchor — are held and stay unpublished; nothing else is held. ### Editing one Issue body (#216)

The PMO corrects the body of the Issue shown in 詳細 and publishes that one body with its own button. Body publishing is outside the plan document: it is not a local edit, it never enters Undo/Redo, the 未発行 count, autosave or the 発行… review, and it never commits or cancels pending cell input. There is no bulk body publish.

**本文を編集** is enabled only after a successful read of a GitHub Issue whose `viewerCanUpdate` is true. Otherwise it is disabled and explains why in its tooltip and accessible help text: 「GitHub に作成してから編集できます」 for a local task or no selection, 「読み込みが終わると編集できます」 while loading or after a failed read, and 「この Issue の本文を編集する権限がありません」 when the viewer cannot update the Issue.

Edit mode replaces the body document with a native multi-line TextBox (`PlanDetailEditor`, accessible name **Issue の本文**) holding the raw Markdown body. It wraps, scrolls vertically, accepts Enter as a new line and keeps IME composition inside the editor: confirming a conversion never triggers a command. Comments are hidden while editing. The header's third line shows **編集中** (`PlanDetailEditing`). Below the editor, **本文を発行** (`PlanDetailPublishBody`, accent) and **キャンセル** (`PlanDetailCancelEdit`) follow. Ctrl+Enter invokes 本文を発行 when it is enabled; Escape invokes キャンセル unless an IME composition is active, in which case it only ends the composition. Ctrl+Z/Ctrl+Y in the editor act on its text, not on the plan. Entering edit mode focuses the editor; leaving it returns focus to 本文を編集. F6/Shift+F6 and Ctrl+I keep their pane behavior from the editor; leaving the pane keeps the draft.

WinUI TextBox stores line breaks as `\r`. The editor's text, the draft comparison and the sent body use `\n`; text that differs from the starting text only in line endings is unchanged. A hidden plan marker (`<!-- ghpb-plan:… -->`, written when the app created the Issue) is removed from the editor text and appended unchanged after the draft, separated by a blank line (the marker alone when the draft is empty). Other HTML comments stay in the editor.

While editing, the pane stays on the edited Issue: selecting other rows does not switch it. When the sheet's selected row is a different row, a secondary line **編集を終えると、選択中のタスクを表示します** (`PlanDetailPinnedNote`) appears under the header. Leaving edit mode shows the currently selected row's Issue.

**本文を発行** is enabled only when the draft differs from the starting text, no publish of this body is running and no remote work (open, 最新の情報に更新, reset to GitHub, 発行) is running. Publishing never shows a confirmation dialog; the conflict check protects concurrent edits. While it runs, the editor is read-only, both buttons are disabled and **本文を発行しています…** (`PlanDetailPublishing`, polite live region) is shown. Publishing one body:

1. Re-reads the Issue's current body and viewerCanUpdate by node ID. If that body already equals the body to send (ignoring line endings), the publish is complete without a write; this resolves an earlier attempt whose outcome was unknown. If it differs from the body the edit started from, nothing is written: a warning InfoBar (`PlanDetailConflict`, a decision point rather than a failure) titled **編集を始めた後に、GitHub で本文が変更されました** offers **上書きして発行** (`PlanDetailOverwrite`) and **GitHub の本文に戻す** (`PlanDetailRevert`). The draft stays until the PMO chooses. 上書きして発行 adopts the body just read as the new starting body and publishes again (another change arriving meanwhile conflicts again). GitHub の本文に戻す discards the draft without a further prompt, leaves edit mode and reads the Issue again.
2. Checks the bound gh identity as other writes do, then sends exactly one `updateIssue(input: {id, body})`. Nothing else on the Issue changes.
3. Verifies that the returned body equals the sent body (ignoring line endings). On success it leaves edit mode, replaces the Issue's cache entry with a fresh read (new bodyHTML and comments) and shows **本文を発行しました（H:mm）** (`PlanDetailPublished`) in place of 最終更新 in the header's third line until the pane shows another Issue or reloads.
4. On failure (including a failed readback), an error InfoBar (`PlanDetailPublishFailure`) titled **本文を発行できませんでした** shows a bounded failure reason and **再試行** (`PlanDetailPublishRetry`), which runs the same publish again from step 1. The draft stays. Losing update permission fails with **この Issue の本文を編集する権限がありません**.

Body publishing uses the authenticated connection gate. Detail-read cancellation does not apply to it: once started, it runs to its readback so the outcome is known. Remote work started meanwhile waits for the gate. 最新の情報に更新, reset to GitHub and plan publication keep the draft and clear only read results; the edited Issue's cache entry is replaced after its own publish.

Discarding: キャンセル, Escape, closing the pane with either toggle or Ctrl+I, opening アシスト (which closes 詳細), opening or switching a Project (including 接続…) and closing the app check the draft. With changed text a dialog (`PlanDetailDiscard`) titled **本文の変更を破棄しますか？** offers **破棄** and **編集に戻る** (default). 編集に戻る cancels the triggering action, keeps the pane open with the draft and focuses the editor. Unchanged text leaves edit mode silently. A running body publish finishes before the check. Switching to サマリー or settings hides the pane with its draft, which returns on 計画. Drafts are kept only in memory for the app session and never reach assist, plan storage or logs.

## Progress snapshots and report (#262)

A console tool records a Project's progress outside the app and renders a report the team opens on github.com. A scheduled GitHub Actions run calls it for each active Project. It only reads GitHub: it never writes Issues, Project fields or the app's local plan, and it keeps no local history. The data and the report live in a separate private data repository; this public repository holds the tool, the reusable workflow and synthetic test data only.

### Inputs

- **Project**: a Project URL (`https://github.com/users/<login>/projects/<n>` or `/orgs/<org>/projects/<n>`). The tool reads the whole Project with the app's bounded Project read; an incomplete read fails the run and writes nothing.
- **Settings file**: the file the app's 設定を書き出す writes ([settings file](#settings-file)). It supplies the column mappings, calendar (company days off, imported holidays), people rates, Project start and end and the 工程-to-milestone mapping. Its `statusDate` is ignored, as on import. A mapping whose field the read does not contain fails the run, because the values would silently be empty.
- **基準日**: today in the given time zone (default `Asia/Tokyo`), or an explicit `yyyy-MM-dd`. Close dates use the same time zone.
- **Authentication**: gh's stored credentials, exactly as the app uses them; token environment variables are ignored. The workflow stores the token from an Actions secret in a temporary gh configuration for the run only.

### Calculation

The tool builds the plan document from the read and the settings, then uses the app's own scheduler, forecast, `PlanLateness` and `PlanSummary` with that 基準日. The plan is GitHub's published plan: the tool has no unpublished edits, so its numbers equal the app's summary for the same Project, settings and 基準日 when the app has nothing unpublished.

- **見込終了** per task, the version's 完了見込 and each 工程's 完了見込 are the summary's.
- **遅れ** is the union of 期限超過 and 予定より遅れ (owner decision on #260). Each late task keeps which case applies: its 終了日 has passed, its 開始日 has passed with no 実績, or its 見込終了 is later than its 終了日.
- **遅れの原因** and **見積超過** are the summary's sets.
- 工程 totals are the summary's 工程別 rows.

### Snapshot file

One indented UTF-8 JSON file per 基準日, `<data>/<yyyy-MM-dd>.json`. A second run on the same day replaces that day's file; the data repository's Git history keeps every run. Japanese text is written unescaped. Property order and task order are fixed (tasks in plan order), so a Git diff between two snapshots shows what changed.

| Property | Content |
| --- | --- |
| `schema` | `ghpb-progress-snapshot/1`. A reader rejects any other value. |
| `readAt` | UTC time of the read (ISO 8601). |
| `statusDate`, `timeZone` | The 基準日 and the time zone that produced it and the close dates. |
| `project` | `host`, `owner`, `number`, `title`, `url`. |
| `period` | `start`, `end` from settings; either may be `null`. |
| `forecastFinish`, `finishDifference` | The version's 完了見込 and its signed working-day difference from `period.end` (positive = late); `null` when unknown. |
| `totals` | Effort of all tasks (below). |
| `phases` | One entry per 工程 option in field order, then `null` 工程 when tasks have none: `phase`, `milestone` (mapped title or `null`), `target`, `start`, `forecastFinish`, `difference` (working days against `target`, positive = late), `effort`, and `late` and `overEstimate` counts. |
| `lateness` | `late`, `cause`, `overEstimate`: Issue references in plan order. |
| `requirements` | Rows with children: `issue`, `url`, `title`. |
| `tasks` | Rows without children, in plan order (below). |

An effort object (`totals` and each phase's `effort`) has `tasks`, `closed`, `estimate`, `actual`, `remaining`, `forecast` (hours), `variance` (forecast − estimate), `progress` (actual ÷ forecast, 0–1, four decimals) and `unknownEffort` (tasks whose 残 or 見込 is unknown). A sum with no known contributor is `null`.

A task has `issue` (`owner/repo#n`, the reference used everywhere in the file), `url`, `title`, `parent` (the requirement's reference or `null`), `phase`, `milestone`, `assignees` (logins), `estimate`, `actual`, `remaining`, `start`, `end`, `forecastEnd`, `closed`, `closeDate`, `late`, `cause` and `overEstimate`. `late` is `null` or `{ "kind", "date", "days" }`: `finish` with the passed 終了日, `start` with the passed 開始日, or `forecast` with the 見込終了. `days` is the working days the 見込終了 is after the 終了日 for every kind, or `null` when it is not later or unknown. Unknown values are `null`. Node IDs, rates, Issue bodies and comments are not written.

### Report

`REPORT.md` is rebuilt from every snapshot in the data folder on each run, using the latest snapshot for the current state. It is Japanese and renders on github.com without scripts:

1. Title (the Project title), the 基準日, the read time and a link to the Project.
2. The verdict: 完了見込 against the 終了日 in working days.
3. 工程別: 工程, 目標日, 完了見込, 差, 完了/タスク, 進捗, 遅れ, 見積超過.
4. 工程の完了見込の推移 (milestone trend analysis): `report/phase-trend.svg`, one small panel per 工程 (nine 工程 are too many lines for one chart), each plotting its 完了見込 at each 基準日 with its 目標日 as a dashed level and the latest value labelled. A single snapshot shows one point per panel. The image has its own light or dark background.
5. 遅れ as counts only, split by case: 「終了日を過ぎて未完了 N · 開始日を過ぎて未着手 N · 見込終了が遅れ N」. A slipping plan makes most tasks late, so the full set stays in the snapshot.
6. 遅れの原因 and 見積超過 lists in full, each task linked to its Issue with its 担当者 and the reason in the app's tooltip wording: 「終了日 1/12 を過ぎて未完了 · 見込終了は +2日」, 「開始日 1/9 を過ぎて未着手」, 「見込終了 1/14 · +2日」 and 「見積 16h → 見込 24h」. 遅れの原因 is ordered by `days`, most first, then plan order; a cause without `days` comes last. 見積超過 is in plan order.
