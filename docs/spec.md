## Current planning editor scheduling contract (#78)

This section is the current contract for the new UI-independent `PlanEditor` model. The legacy sections below remain **Being replaced**; they do not override this section. Storage, refresh/publish orchestration and UI integration are separate phases.

### Inputs, identity and calendar

- A task has an opaque Issue/local identity, a positive unique plan-row ID, optional parent identity and predecessor identities. Row IDs are supplied by plan order, never recomputed by filtering. External predecessors retain their reference, do not constrain dates and produce `プロジェクト外の先行タスク: {reference}`. References outside the Project have no plan-row ID. Missing parents are external hierarchy boundaries, with `プロジェクト外の親タスク`; they do not create summary rows.
- Inputs retain Estimate, Remaining, Actual, assignees, closed state, 開始日指定, 日程固定, current start/end and GitHub baseline start/end separately. Effort inputs are nullable decimal person-hours; valid effort is nonnegative. Missing effort is not zero. Negative refreshed effort or inverted kept dates isolate that row as described below; nonpositive/duplicate row IDs, duplicate/empty identities and invalid settings still reject the calculation without changing inputs.
- Working time is Monday–Friday 09:00–13:00 and 14:00–18:00, excluding bundled Japanese holidays 2025–2027, additional dates from the existing validated holiday CSV importer, company days off and (only for a single assignee) personal days off. Imported dates supplement the bundle. Beyond the supplied holiday years, weekdays still apply and affected rows warn `祝日データの対象年外`.
- A single person's rate defaults to 100%; allowed rates are greater than 0 and at most 100%. Capacity is 8 hours times rate per day, spread uniformly across both work intervals (50% means 4 person-hours over an eight-hour day). No assignee or multiple assignees use the Project calendar at 100%; multiple assignees warn `担当者が複数`. No resource leveling occurs.
- 状況日 is an optional explicit choice. Every calculation receives the caller's today and uses the explicit date when present, otherwise that supplied today. Clearing the choice restores this daily default; Core never reads the clock. The local document stores the optional choice, not its resolved default. Project start is optional. Day inputs become 09:00 boundaries. Internal working-hour endpoints use exact rational arithmetic derived from decimal effort and rate, only during recalculation, never in returned date cells or persisted inputs. No rounding to minutes or tolerance may move an endpoint across a work-interval/day boundary; successors inherit the exact endpoint, also across differing rates. A 4-hour task at 100% finishes at 13:00; its successor starts at 14:00 that day. At 18:00 a positive-work successor starts on its next working day. Kept start/end dates represent 09:00/18:00 even on nonworking days.

### Scheduling precedence and edits

Before these rules, isolate invalid row data as described below.

1. Summary rows roll up children as below, overriding their valid own scheduling inputs.
2. Closed tasks are complete. Open tasks with Remaining = 0 are complete only when Estimate > 0 or Actual > 0. They retain current GitHub/locally typed dates, reason `完了`; a missing end warns `完了タスクの終了日なし` and imposes no successor constraint. An open task with Estimate and Remaining each absent or zero (at least one zero), and Actual absent or zero, is a milestone. Thus typing Estimate = 0 on a new row (which also fills Remaining = 0) creates a milestone, while finishing planned or performed work creates a completed task. 日程固定 still keeps explicitly fixed milestone dates.
3. 日程固定 retains current typed dates, reason `日程固定`. Missing either date warns `日程固定の日付不足`. A start earlier than any effective predecessor finish warns `先行タスクより前に開始`; dates do not move.
4. Both Estimate and Remaining absent retain dates, reason `工数なし`.
5. Otherwise work is Remaining, falling back to Estimate. Earliest start is the maximum of 状況日, optional Project start, 開始日指定 and effective predecessor finishes. Normalize positive-work starts to the assignee's next working interval. An unfixed zero-work milestone has identical start/end at the earliest boundary's day without calendar normalization (including an 18:00 predecessor endpoint); its reason names that winning constraint just as for positive-work tasks. An unfixed open task with Actual > 0, Estimate = 0 and Remaining absent is neither a milestone nor explicitly complete: isolate it with `残が未入力` until Remaining is supplied.
6. Actual > 0 and positive work retains the existing start cell; remaining work begins at max(状況日, retained start), normalized to working time. Its end uses Remaining (Estimate fallback if Remaining is absent). Dependencies, Project start and 開始日指定 do not move an existing actual start; predecessor violation warns as above. Missing start uses the ordinary earliest start, calculates both dates and warns `進行中タスクの開始日なし`. This preserves recorded history while never placing remaining work before 状況日.
7. Other positive-work tasks calculate both dates from earliest start and work/rate. Calendar adjustment does not replace the start reason.

Entering a nonempty Estimate fills Remaining only when Remaining is absent; subsequent Estimate edits leave Remaining unchanged. Clearing Estimate does not clear Remaining. Typing/clearing a start updates both the current start input and 開始日指定; typing a nonempty end updates the end and enables 日程固定, while clearing an end does not silently disable the flag. These pure input transformations are composed by the local document commands below. Estimate, Remaining and Actual edits reject a negative new value; start/end edits reject an inverted resulting pair when dates are kept. An automatic start edit may move past an old GitHub end because its end is recalculated; typing an end enables 日程固定 and validates the resulting pair. Rejection throws a validation error and returns no replacement task, leaving the original input intact. A valid correction to one field is allowed while another refreshed field still needs correction.

Each date cell exposes its day value, `Calculated` or `Kept` origin and a boolean difference from the corresponding GitHub baseline (including null transitions). In-progress start is Kept, end is Calculated. Valid summary cells are Calculated; isolated summaries keep their GitHub dates. Unchanged calculated values are not unpublished changes. Inputs are never overwritten by a calculation.

### Hierarchy, dependencies and reasons

- A row with in-Project children is a summary. Each effort column sums direct children recursively; if any child's value is absent the total remains absent (never turn missing into zero). Check all children for absence before addition, so an unknown total never overflows merely because of child order. Start is the minimum available child start, end the maximum available child end; all absent yields absent. Its own valid effort/date/constraint/closed inputs remain intact but are ignored for summary scheduling; invalid data follows the isolation rule below. Removing its last child restores ordinary task semantics. Publishing writes rolled-up start/end but **not** rolled-up effort; no publish implementation is implied here.
- A predecessor link to a summary waits for its rolled-up internal end. A summary's predecessors constrain every descendant, including nested summaries. Completed/fixed/no-effort descendants still retain dates; fixed and in-progress violations warn. Parent 開始日指定 is not inherited. Duplicate predecessor references have no extra effect.
- Reject parent hierarchy cycles, dependency cycles (also those induced by summary roll-up/inheritance), self-links and any predecessor link between ancestor and descendant. Errors identify the involved plan-row IDs as `循環参照: #1, #2`. Reject the whole calculation, with no partial result or input mutation. Unrelated descendants of a cycle are not named as cycle members.
- Exact start reasons: `状況日`, `プロジェクト開始日`, `開始日指定 M/d`, `#{row ID} の終了後`, `開始日を維持`, `完了`, `日程固定`, `工数なし`, `子タスクの集計`, `入力エラー`. Dates use invariant M/d. For equal constraints, predecessor wins, then 開始日指定, Project start, 状況日; tied predecessors use the smallest plan-row ID. In-progress with a retained start uses `開始日を維持`; a missing start uses the winning earliest-start reason. A valid summary uses `子タスクの集計`; isolated rows use `入力エラー`.
- Warnings are per row, unique strings. Refreshed negative effort warns `工数が負の値`; an inverted kept start/end pair warns `開始日が終了日より後`. An unrepresentable calculated schedule warns `日程が日付の範囲外`; effort-total overflow warns `工数の集計が範囲外`. The affected row retains its GitHub baseline dates with Kept origin and reason `入力エラー`; inputs (including invalid values) remain available for correction, and no date change is proposed. Neither date is used as a dependency or summary endpoint. Invalid leaf effort is displayed as received, never included in summary totals.
- A summary containing an isolated child is also isolated, with `子タスクに入力エラー`, retained GitHub dates and unknown rolled-up effort. This propagates through ancestors instead of publishing incomplete summary totals/dates or constraining successors from them. Other children and unrelated tasks still calculate normally; hierarchy and dependency cycle validation still applies to every row. A summary's own invalid refreshed values likewise isolate that summary but do not stop its children.
- Scheduling is bounded by DateOnly's supported range, with no arbitrary short horizon. Dates/settings identities are not silently repaired. Structural errors and cycles remain whole-calculation errors; ordinary refreshed row data problems do not.

## Current local plan document, operations and storage (#78 / #79 / #81)

This section defines UI-independent local commands. Refresh, verified Issue creation, conflict resolution and publishing extend it under the current #79 contract below; ordinary local commands never contact GitHub. The legacy sections below remain **Being replaced**.

### Document and atomic operations

A document belongs to one normalized host, stable numeric GitHub viewer ID and Project node ID. Its immutable baseline holds the last retrieved Issue rows in Project order and the known mapped column identities/names. Each row retains identity, title, repository, Status option identity, closed state, assignees, predecessors, parent, Estimate/Remaining/Actual, start/end, 開始日指定 and 日程固定. Current rows and settings are separate from that baseline; no edit changes it. New rows use `local:<GUID>` identities until Phase 4 verifies an Issue identity. Order is the row sequence; displayed IDs are its one-based positions, never affected by filtering.

Each command builds and validates a complete candidate before replacing current state. Cell edit, rectangular paste, fill/Ctrl+D, Delete-clear, inserting one/many rows, indent/outdent, moving rows and settings replacement each create exactly one Undo step. A rejected command changes neither state, history nor the pending save. A no-op creates no history and does not discard Redo. A new effective command clears Redo. Recalculation uses the Phase 2 scheduler and caller-supplied today; calculated dates and reasons are never document inputs.

- Edits use typed Core values (text, decimal hours, DateOnly, boolean, identity lists or null), not locale-dependent string parsing. Estimate/Remaining/Actual/start/end pass through the Phase 2 transformations. Paste validates all cells and applies them in supplied order to a candidate (validate kept date pairs only after all cells, so a valid two-date paste can move both endpoints); an explicit Remaining cell therefore follows an Estimate cell when both are pasted. Fill/Ctrl+D snapshots the source inputs once and expands to the same atomic cell operation. Paste/fill never creates rows. Duplicate target cells in one operation are rejected. Clear uses null, empty identity lists or false according to the field; title becomes empty. Summary effort, date and constraint cells are derived and cannot be edited directly; edit their children instead.
- Insert accepts already prepared local rows, defaulting an empty repository from settings; an explicit or default `owner/repository` is required. CSV parsing is not implemented here: a future importer submits its fully validated rows as the same one-step bulk insert. Undo removes inserted rows; Redo restores their exact identities and relationships. Closed state is a retained GitHub input, not an Issue-administration command.
- Indent applies to selected consecutive siblings and reparents them under the preceding sibling. Outdent reparents selected siblings to their parent's parent; a missing/external parent cannot be outdented. Both preserve the explicit row order. Move places exactly the selected rows, preserving their current relative order, before a specified unselected row or at the end; it does not implicitly move descendants or change parents. Invalid identities, hierarchy or dependency cycles reject the complete command.
- Undo/Redo restores exact row inputs, relationships, order and settings using before/after patches. Local edits leave the baseline unchanged. Keep at most **200 effective operations** in the combined Undo/Redo chain, dropping the oldest reachable Undo step when necessary. Persist changed rows, changed order and changed settings per step rather than 200 copies of the whole Project. Verified publication promotes created identities; published creation is a history barrier while subsequent edits remain undoable.

Unpublished fields compare current inputs with the baseline: title, repository, Status, assignees/predecessors as sets, parent, Estimate, Remaining, Actual, 開始日指定 and 日程固定. Start/end compare the scheduler's displayed dates with baseline dates, so calculated differences count and internal typed starts superseded by automatic calculation do not create false date markers. A new row has a NewTask marker regardless of its values. Order compares positions among baseline rows, ignoring inserted local rows (inserting one task does not mark every existing task). Reordering existing rows marks every existing row whose relative position changed. The unpublished task count is the number of distinct rows with any marker, including affected summaries. Local settings alone are not GitHub fields; their changed calculated dates can create markers. Negative refreshed inputs remain intact under Phase 2 row-isolation rules; commands cannot introduce new negative effort. Unrelated edits do not revalidate an unchanged invalid refreshed date pair; editing start/end or the fixed flag, or changing an automatic task to kept-date semantics, must leave a valid kept pair.

### Settings file

Store column mappings for the seven planning roles (Estimate, Remaining, Actual, Start, End, StartNoEarlierThan, Fixed), each with a GitHub field ID, name and expected NUMBER/DATE/SINGLE_SELECT type. Mappings may be absent until configured; duplicate roles or reused field IDs are invalid. Known baseline column definitions remain separate from settings. Settings also hold company days off, imported holiday dates and coverage/source metadata, people (stable identity, readable name, rate, personal days off and nullable nonnegative whole-Project allowance), optional Project start, optional default repository and optional explicit 状況日. Bundled holidays remain a product resource, not repeated in the settings file. No UI layout or column visibility is stored in this phase.

Export writes a versioned, indented UTF-8 JSON settings file, containing no document rows, account binding or history. Import validates the entire schema and all values before replacing settings as one Undo step. Duplicate people/dates, invalid rates/allowances/repositories/mappings, malformed holiday data, unknown JSON properties and unsupported versions are rejected without any document/history change. Explicit null/default settings remain distinct. An imported person absent from baseline assignees, or a field ID absent from baseline column definitions, is retained and reported as `プロジェクトに未確認の担当者: {name}` / `プロジェクトに未確認の列: {name}`; no network lookup, silent dropping or remapping occurs. Settings have no embedded account scope and can be imported into another data root. Existing-file export replacement is atomic and explicit through the export call.

### Autosave, isolation and recovery

Use `<resolved data root>/PlanningEditor/v1/`; resolve `GHPB_DATA_ROOT` and the default root exactly as RegistrationStore does. Use a SHA-256 filename of host/viewer/Project and repeat that scope inside each versioned checkpoint. Never enumerate, read or migrate legacy files outside this new subfolder. Persist baseline, current inputs/settings and Undo/Redo patches together in one atomic checkpoint. No tokens, credentials, scheduler output or UI state are part of the schema. Immutable collections prevent later caller mutation of queued saves or history.

A committed command updates memory synchronously, then schedules autosave on a **single background writer**. Consecutive pending revisions can coalesce into the latest checkpoint, which still includes every retained Undo step. Serialization, file I/O and durable flush never run on the caller's edit path. The returned save task reports durability or failure; `FlushAsync` awaits the latest state before a normal close. An abrupt process exit before successful flush can lose the unsaved tail; never report that tail as durable. This is separate from the 0.2-second edit-to-screen target.

Reuse the existing temp-file / durable-flush / readback / File.Replace (or first File.Move) mechanism, with a last-good `.bak`. A per-Project exclusive writer lock and expected SHA-256 of the loaded/saved file prevent competing or externally changed files from being overwritten, even if a revision number was reused. Check scope, schema, current document and every reachable history state both before replacing the checkpoint and when loading; malformed or unreadable data returns a blocked result without creating a new session or modifying the file. Unknown `.tmp` candidates or a backup with no primary file are reported as interrupted storage, never silently adopted or discarded. A live writer may remove only its own failed temporary candidate so a retry remains possible.

Any failed save leaves the latest in-memory document and history intact. Transient I/O/access errors return a retryable result; explicit retry writes the latest state, not an older snapshot. Changed/corrupt source files return a non-overwrite result requiring preservation and reconciliation before retry/reopen; they cannot be bypassed by a normal save. New-session creation is permitted only after a missing-file result, and races are checked again under the writer lock. Successful writes update the expected fingerprint; older writes cannot supersede newer in-memory operations. This phase introduces no recovery dialog or background publish.

Verification adoption uses B/L/R merging for fields outside the publish, including unrelated remote updates in retained Undo history. Intended unfinished published values remain local. Newly discovered remote rows are retained consistently across every historical order, including after refresh, Undo, save and reopen. Placeholder substitution applies only to identifier input fields; title/body/text values are literal. Issue creation uses persisted start-to-start reservations and a rolling-minute bound; request time overlaps pacing waits, and server backoff is honored on resume. See the [pacing decision](decisions.md#throughput-targets-for-79).
The refresh snapshot reads the built-in Status single-select option's display name independently of optional planning-column mappings; an unavailable or unknown option is a read failure, not an empty Status. Summary-row Estimate, Remaining and Actual differences are excluded from unpublished counts as well as writes, including when an earlier effort edit becomes a summary after indenting. Hierarchy publication completes all removals before additions and then reprioritization, stopping dependent phases after a failed batch. Selected publish/live failure reasons include GitHub's error type and a bounded, single-line message with credential-like text redacted; generic transport diagnostics still omit response messages and payloads.

GitHub planning date values use Gregorian `yyyy-MM-dd` with invariant culture; numeric serialization and comparison are also culture independent. The current Windows culture must not change published values or verification.

開始日指定 and 日程固定 mappings are optional. Without a mapping, these are local scheduling constraints: refresh preserves them, they do not create unpublished field differences, and publishing still writes resulting dates through the configured Start/End fields. Adding the corresponding GitHub fields remains an explicit settings action. Sibling order is tracked and published only for parents that are rows in the current plan; external/archived parents retain their relationship references without a sibling-order conflict. Copying an unavailable task to a new Issue resets Closed to false and Status to empty, while retaining reproducible planning inputs. Verification cannot report publish success while conflicts or unavailable tasks remain, even when the unpublished task count is zero.

### Publish invariants (#79)

- **I1 — Publish outcomes are not Undo state.** History restores local inputs, settings and explicit conflict/unavailable-row dispositions only. It never stores or restores a publish attempt, dispatched/acknowledged writes, verified baseline values or GitHub identities. Title correction and its Undo/Redo may change the input of a definitely unsent/rejected creation, but never a dispatched creation's reconciliation marker or obtained identity. Once creation is observed, its identity is promoted throughout retained local history; an insertion cannot be undone into eligibility for another creation. Later edits remain undoable. Recovery reconciles the retained attempt before planning writes from the latest local inputs, without replaying verified operations. Restoring an unavailable row restores only that row's last-known content, never another row's newer baseline.
- **I2 — Nothing sent, nothing locked.** Identity, complete-read/conflict, field mapping and repository existence/archive/Issue-creation permission checks precede recording a new attempt. If an attempt stops before dispatch, its pending record and wait deadline are released. Local editing, settings correction, Undo/Redo and refresh remain usable, including after restart. Opening a checkpoint containing only Pending writes and no dispatch fact releases that never-dispatched attempt before editing. A dispatch fact survives an absent-result lookup and an incomplete Project read; Pending alone is not evidence that nothing was sent. Once a mutation may have been sent, its outcome remains durable until reconciled; settings and identity-removing operations cannot invalidate that reconciliation.
- **I3 — Relationship phases never pass through a cycle.** For hierarchy and blocked-by relationships, remove all obsolete edges across every row and batch before adding any new edge; hierarchy ordering follows additions. A failed removal stops dependent additions and ordering. The final intended graph is validated locally; remote readback establishes the resulting graph.
- **I4 — Persisted history is always replayable.** Every reachable Undo and Redo state must satisfy the document and publish invariants. Remote adoption (refresh, publish verification and identity promotion) rebases both directions and validates each reachable state before persistence. At the first invalid step, drop that step and all older/further steps in that direction; retain the valid prefix and the other direction. History cannot remove identities needed by a dispatched attempt or change its settings. Validate the serialized checkpoint with the same validation used at load before replacing the last good file.

A Project traversal with changing page totals is classified as concurrent change. Refresh, publish preflight and publish verification retry only classified concurrent change, using a fresh traversal each time: **at most three attempts, three seconds between attempts**. Other incomplete, permission, malformed-response and cancellation outcomes are not treated as churn. No non-Complete traversal is adopted into local inputs, baseline or history. Exhaustion returns a retryable message with outcome/problem classifications, never source payloads. A complete traversal is required before any subsequent mutation.

When a post-write verification read remains non-Complete, rows with dispatched/acknowledged writes are **unverified**, not verification failures. Their attempt, identities and outcomes survive restart and local Undo/Redo. Refresh can reconcile them without mutations; a later publish first reconciles them and only then derives further writes. A response alone is not complete verification, and an incomplete read cannot authorize blind resend. Creation/membership recovery completes before planning remaining fields and relationships from the latest local inputs.

## Project row views

Source: #5/#7, with #8 durability. Each host/account/Project owns one local row definition: source order, ordinal case-insensitive Title order, or one supported Project single-select ordered by its current option definitions. Both directions put present values first, followed by Empty, local Unspecified, and Unknown; equal values use stable row identity. Title filtering is a literal ordinal case-insensitive substring. Validate the whole batch before applying it. Read-only, permission, conflict, unknown-option or pending-input failures identify the target and leave values/history unchanged. Clipboard waits and fill retain their starting mapping generation and workspace revision; stale work is cancelled rather than retargeted.

Each successful paste, fill, copy-down or clear is one transaction and Undo unit. An earlier source edit is a separate unit: the first Undo restores destinations, and the next restores the source. Undo of a confirmed single-cell or contextual Actual/Date edit restores the prior confirmed values and calculation without reopening the text consumed by that confirmation. Independent pending text remains recoverable; a batch overwrite or explicit draft cancellation is not confirmation of that text. Finishing otherwise unchanged input persists its removal without an empty Undo entry; returning to the baseline removes the difference.

A rectangle that writes Actual cannot also write unrelated columns or dates. Values, reports and derived schedules share one durable Undo without changing progress or publishing to GitHub. A single-cell Actual paste retains the existing unfinished-input path.

Undo addresses original IDs even if now hidden and preserves current unrelated pending work. It validates the complete affected state before changing anything: later shared-Issue edits, new input on an affected field, or remote acknowledgement cannot be bypassed. Consecutive local-field edits and planning projections retain coherent Undo after restart. Persisted history without an explicit input footprint keeps its recorded behavior; loading does not guess which old text belonged to a confirmation. Project histories cannot undo another Project's independent work. Selection, local edits, copy/fill/paste, saving and Undo perform no network permission check, GitHub write or automatic Apply dispatch.

Ordinary cells have a neutral value-first background. Selection uses a subtle fill and outer range border, with a stronger active-cell frame. Committed unreflected changes use a subtle distinct fill plus a fixed upper-right diamond; the lower-right fill handle has separate geometry. These overlays never move values, arrows, column widths or row heights. Pending native input uses the editing frame/caret, separately from committed differences. ### Local durability and lifecycle

Fetched observations, editor buffers and committed local differences remain separate. Committing/saving never modifies the baseline; returning to baseline removes the effective difference. Titles share a host/viewer/Issue identity across Projects; selects remain scoped to Project/item/field IDs. Opening another cached observation never replaces an active draft's pinned baseline. The UI distinguishes per-Project and profile-wide changed-field counts and local saving/saved/failed states from GitHub synchronization.

One versioned JSON draft record per host/stable viewer under `Drafts/` holds baseline value/source Project/retrieval time, clear/value intent, recoverable text, field stamps and transaction history. Version 2 adds observations, conflicts and the authoritative registration checkpoint described below; version 1 is still readable. It contains neither credentials, raw API payloads nor private IME state. Startup/profile selection restore it locally. A restored buffer is pending text, not a committed cell.

Draft saves are serialized. Under a filesystem writer lock, the expected durable revision is checked, a temporary record is flushed and validated, and the complete profile record is atomically replaced with a last-good backup. A cross-field operation is recovered wholly or not at all. The session advances its acknowledged revision only after success and drains later changes before reporting a successful flush. Competing-process/stale saves fail instead of overwriting. Corruption, incompatible schema, mismatched scope and interrupted files are diagnosed without resetting source data. Intermediate edits after the last successful save may be lost on forced termination; normal transitions/close wait for a successful flush. Save failure keeps in-memory text and cancels navigation/close.

Preparing an unmounted replacement table does not start a draft save or change the current table's save presentation. Once the replacement is mounted, it saves fields initialized by opening that Project and presents saving, failure and retry in the current table. Replaced tables stop presenting subsequent session changes. These presentation boundaries do not discard pending work or bypass the durable save required before navigation and normal close.

Refresh reconciles existing titles and Project-owned single-select fields using the contract below. The final checkpoint replacement rechecks local revision, operation generation, connection identity and active composition synchronously immediately before replacement. Unregistration settles owned work and defaults to cancellation, offering explicit retention or discard. Discard never removes Issue work shared by another registration; its pinned source provenance remains in the surviving draft record. Discard plus registration removal is one durable checkpoint decision; legacy files remain recovery material after migration.

## Data identity and availability

Keep Issue fields, Project item fields, and application work state distinct. Share the same Issue's body fields across Projects while retaining each Project item's own values. Missing, unreadable, unsupported, and explicitly empty values are different states. See [#6](https://github.com/fukuda-yuki/gh-projects-boards/issues/6).

### Bounded Project read contract

The Core Project reader accepts an explicitly selected Project node ID bound to the existing connection's host and stable viewer ID. It uses the guarded connection service for every page. It performs queries only, with the same identity preflight, credential isolation, per-process timeout and cancellation as other reads. Project registration/navigation UI is separate work.

Each returned Project has a stable owner ID, node ID, number and URL. Repository and Issue identities also include the connection scope. Items retain their own node ID, content identity, archived flag and field values. Issues are indexed separately from items: two Project results refer to the same logical Issue key, while their item values remain independent. These are immutable read observations; there is no cross-result cache, automatic synchronization or draft state.

| Data | Read behavior |
| --- | --- |
| Issue title and Open/Closed state | Loaded directly from the Issue, never through a field display name |
| Project single-select, including Status | Field ID, Project ownership, option IDs/names and selected option ID |
| Issue-derived or organization Issue fields exposed by a Project | Ownership and Project field identity/type retained; their projected values are unsupported in this slice |
| Other Project fields | Identity, type and known ownership retained as unsupported; unknown ownership stays unknown |
| PR / GitHub Draft | Explicit item kinds with content IDs; no ordinary Issue or local-new-row conversion |
| Redacted/null content | Unavailable content with the Project item identity retained |
| Unknown item/value types | Explicitly unsupported, retaining encountered type and available IDs |

Field names and option names are display metadata, never identity or destination selectors. Native Issue properties use their Issue identity and typed title/state properties; a same-named Project field has its own field ID. The bounded editor additionally reads dated Issue and Project viewerCanUpdate observations. Missing/denied observations do not enable editing; creation and remote application require the separate explicit Apply contracts.

The reader traverses Project field definitions, items and every implemented item-value connection to the terminal page, including more than 100 entries. It checks node/ownership identities, duplicate fields/options/items/Issues/value IDs, duplicate field assignments, repeated cursors, missing paging metadata and inconsistent total counts. On API or structural failure it stops further requests, retains already observed data and reports a classified problem. No automatic retry occurs.

Result outcomes are Complete, Partial, Failed, Cancelled and TimedOut. Cancellation/timeout can retain a partial Project. Per-connection completion flags describe traversal, not universal support or readability. A Complete result means the requested traversal completed without detected problems; it can contain explicitly unsupported fields and known unavailable items. It does not establish a transactionally consistent snapshot: GitHub does not pin successive queries to one revision, and equal-count concurrent replacements can escape count/cursor checks.

Values distinguish Present, Empty, Unsupported, Unavailable and NotLoaded. An explicit null option, or an absent supported field after a complete, error-free traversal, is Empty. On a partial read, nulls become Unavailable and absent supported fields stay NotLoaded; redacted content never implies an empty Issue or field. Unknown option IDs retain the observed ID as Unavailable. Partial GraphQL data is retained but never treated as complete. Missing or unsupported data cannot authorize clearing or deletion. The reader is query-only; publication belongs to the explicit Apply boundary.

The [selected matrix](planning.md#selected-ownership-and-operation-matrix) defines P1 work/date/relationship extensions and every broader candidate's disposition. Existing unsupported/unavailable classifications survive these extensions.

The bounded #9 workflow refreshes registered Projects with existing local work. It covers Issue titles and Project-owned single-select option IDs only. Structural changes report added/no-longer-observed items, archive state, missing/type-changed fields and renamed/deleted option IDs. Absence from a complete Project traversal is not proof of Issue deletion. Unknown capabilities and detached values stay blocked and retain identifiers, drafts and buffers.

## Current planning editor refresh and publishing contract (#79)

Refresh accepts only a complete, Project-scoped read, including all field values, native Issue relationships and item order. Drafts and pull requests are counted but never scheduled. Failed or partial reads leave the entire local checkpoint unchanged. Merge compares each field against the previous baseline: unchanged local values adopt GitHub; unchanged GitHub values preserve local work; equal changes converge; differing changes retain an explicit conflict until the user chooses a side. Resolution is one local Undo operation. Dates are recalculated after merging.

Removed or deleted remote tasks remain visible as unavailable conflicts, retaining their local content and preventing publish. Resolution discards the unavailable task and its local relationships, or copies it to a new local task; it never recreates an Issue implicitly. Refresh replaces the baseline only after the complete merge has been saved. Unresolved conflicts survive refresh and restart. Summary effort roll-ups never count as unpublished changes because only their start and end dates are published.

Publish reviews before/after values, calculated dates, assignees, hierarchy, dependencies, order and new tasks. It requires resolved conflicts and durable storage. Its serial write phases are creation and Project addition, fields and assignees, sub-issue relationships/order, blocked-by relationships, then Project item order. Field writes use at most 50 aliases; Issue creation and Project addition use at most 10 each. Identity preflight and a complete conflict read precede writes. Creation/membership is verified and adopted before planning remaining fields/relationships, followed by their complete verification read; each traversal follows the bounded concurrent-change retry policy. Successful aliases are retained even when siblings fail. An exact already-present Project addition is reconciled by Issue identity; resource-limit failures remain distinct.
