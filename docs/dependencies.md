## Exact payload boundary

`MicrosoftWindowsAppSDKPackageDir` resolves to `Microsoft.WindowsAppSDK.Runtime/2.5.1`, whose main x64 framework MSIX is `tools/MSIX/win10-x64/Microsoft.WindowsAppRuntime.2.msix`. The audit discovers exactly one main framework MSIX in that architecture directory and excludes DDLM/Main/Singleton packages; zero or multiple matches fail. Its license retains the explicit binplaced-file grant.

The self-contained build uses Base 2.0.4's `build/Microsoft.WindowsAppSDK.SelfContained.targets`, target `AddMicrosoftWindowsAppSDKPayloadFilesFromComponents`. It collects files from each `WindowsAppSdkComponentPackages` entry's `runtimes-framework/win-x64/native` and `metadata` directories; it does not extract the Runtime MSIX. Therefore, an identical MSIX entry establishes byte identity, not the physical copy source. InteractiveExperiences 2.1.9 supplies `Microsoft.Graphics.winmd`, `Microsoft.Foundation.winmd`, `Microsoft.UI.winmd` from `metadata/10.0.18362.0` and `Microsoft.Internal.FrameworkUdk.dll` from `runtimes-framework/win-x64/native`; those originals differ from the same-named Runtime MSIX entries.

The distribution audit accepts a Windows App SDK component binary only when its SHA-256 exactly matches a file in a resolved, reviewed package whose own `license.txt` contains "Any files that are binplaced with your application" at audit time. That license must be retained as `<id>-<version>-license.txt` in `docs/notices`, listed in `hashes.json`, and byte-identical to the resolved package's license. Record the matched origin as `package/version/relative-path`. Files identical to Runtime MSIX entries may retain `package/version/MSIX-path!entry-path` origins after the same Runtime license validation. A same-named MSIX entry with different bytes is not an origin match; the file must instead pass the resolved-package comparison. Unknown or unlicensed origins fail the audit.

Application binaries retain their application-build origins. The established non-binplaced license boundaries for WebView2, System.Numerics.Tensors, the .NET runtime pack and Windows SDK .NET projection pack remain as listed above; these files still require exact resolved-package SHA-256 matches and the existing notice/inventory checks. SDK build tools are not accepted merely because they were restored.

`DWriteCore.dll` must be present with a verified origin. Native Widgets DLL/WinMD files are not required. The app does not use Widgets APIs; its exact-version direct reference uses the supported [NuGet ExcludeAssets mechanism](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#controlling-dependency-assets) to exclude component assets before compile and publication. The audit rejects `Microsoft.Windows.Widgets.Projection.dll` in the payload or dependency runtime assets. Any native Widgets file that is present must pass the same licensed-origin checks as other component binaries. Files are not manually inserted or removed after publication.
The retained [Windows SDK REDIST source](notices/Windows-SDK-redist-20261008.html), referenced by the SDK license, includes `Microsoft.Windows.SDK.NET.Ref` files under `lib/net8.0`, including `Microsoft.Windows.SDK.NET.dll` and `WinRT.Runtime.dll`. This is the applicable list for those runtime-pack files, not an inference from an unrelated SDK tool's terms.

The packaging script starts with a new isolated build/output directory, transfers compiled XAML and the application PRI from that same build when the WinUI publish target omits them, copies the retained notices plus original notices from the resolved .NET runtime pack, and records SHA-256 identities, package content hashes and runtime-file origins. It requires the build and published application assembly to match before transferring resources, and audits each required resource. It bundles only application output, notices and the Japanese distribution guide, not developer settings, credentials, evaluation data or build logs. Build logs and source evidence remain beside the ZIP. GitHub CLI is installed separately by the user and is not bundled. Bundled holidays retain Cabinet Office attribution and their original source hash in the notice manifest.

[Issue #92](https://github.com/fukuda-yuki/gh-projects-boards/issues/92) owns internal distribution and user acceptance. Packaging does not establish clean-PC operation, a colleague's acceptance, physical IME acceptance or one working day without lost input. No certificate trust, Developer Mode, machine-wide setup, automatic updater or public release is part of this portable ZIP. Dependency upgrades require a renewed exact-payload audit.
