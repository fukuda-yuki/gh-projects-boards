# Dependency terms

The app pins Windows App SDK `1.8.260804001`. Its resolved package versions, NuGet content hashes and versioned package URLs are in [notices/packages.json](notices/packages.json). The adjacent original terms/notices cover those packages, with SHA256 values in [notices/hashes.json](notices/hashes.json). The app has no TableView dependency. Existing test dependencies remain in their test project files.

The package licenses govern packaged artifacts; a source repository's license is not a substitute for their terms. Internal distribution uses the exact self-contained x64 payload produced by [Publish-Internal.ps1](../scripts/Publish-Internal.ps1). Its package, source and payload manifests identify the actual files and preserve original notices. This record is an engineering interpretation of the retained terms, not company or legal approval.

## Exact payload boundary

`MicrosoftWindowsAppSDKPackageDir` resolves to `Microsoft.WindowsAppSDK.Runtime/1.8.260804001`. The SDK's `AddMicrosoftWindowsAppSDKPayloadFilesFromMsix` target copies the runtime from that package's `tools/MSIX/win10-x64/Microsoft.WindowsAppRuntime.1.8.msix`. That package carries the explicit binplaced-file grant. Distribution must verify this provenance rather than infer a license from the filenames or from unused features.

`Microsoft.Windows.Widgets.Projection.dll` instead comes from the Widgets component package and is not present in the Runtime MSIX. The app does not use Widgets APIs. Its exact-version direct reference uses the supported [NuGet ExcludeAssets mechanism](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#controlling-dependency-assets) to exclude all component assets before compile and publication. The packaging audit rejects that projection in either the payload or the dependency runtime assets. Native Widgets files from the Runtime MSIX remain unmodified; files are not manually removed after publication.

The retained [Windows SDK REDIST source](notices/Windows-SDK-redist-20261008.html), referenced by the SDK license, includes `Microsoft.Windows.SDK.NET.Ref` files under `lib/net8.0`, including `Microsoft.Windows.SDK.NET.dll` and `WinRT.Runtime.dll`. This is the applicable list for those runtime-pack files, not an inference from an unrelated SDK tool's terms.

The packaging script starts with a new isolated build/output directory, transfers compiled XAML and the application PRI from that same build when the WinUI publish target omits them, copies the retained notices plus original notices from the resolved .NET runtime pack, and records SHA-256 identities, package content hashes and runtime-file origins. It requires the build and published application assembly to match before transferring resources, and audits each required resource. It bundles only application output, notices and the Japanese distribution guide, not developer settings, credentials, evaluation data or build logs. Build logs and source evidence remain beside the ZIP. GitHub CLI is installed separately by the user and is not bundled. Bundled holidays retain Cabinet Office attribution and their original source hash in the notice manifest.

[Issue #92](https://github.com/fukuda-yuki/gh-projects-boards/issues/92) owns internal distribution and user acceptance. Packaging does not establish clean-PC operation, a colleague's acceptance, physical IME acceptance or one working day without lost input. No certificate trust, Developer Mode, machine-wide setup, automatic updater or public release is part of this portable ZIP. Dependency upgrades require a renewed exact-payload audit.
