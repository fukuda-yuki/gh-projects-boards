## Identity and storage

Host/stable viewer is the isolation boundary. Project, Issue, item, field and person node IDs are distinct; names never select a mutation target. A task key is its Issue node ID within the Project or its existing `local-<guid>` until verified creation. Promotion uses the retained creation journal, never title equality. Cross-Project observation grants no write permission. Unavailable content is not inferred deleted.

`DraftRecord` v14 retains typed scalar operations, coherent planning history in `ProjectPlanning[]`, and explicit input-write keys for new edit transactions. The keys distinguish an operation's input from independent text carried through its derived projections or local row. History without those keys retains its recorded comparison and restoration rules; migration does not infer ownership from text. Planning metadata v3 explicitly distinguishes adopted native assignment from retained legacy owner semantics; v4 additionally retains Summary allowances, labor classification and the protected baseline. Checkpoint versions 1–13 remain readable, including Summary v10/planning v2 and assignment v11/planning v3. Their owners, exact dates, reports, baseline and Undo history are preserved without reinterpretation; the next save writes v14 and retains the previous file as a backup. Version 14 adds historical-field observations, explicit handling decisions and exact follow-up links as related records within the same atomic checkpoint; original Apply attempts remain unchanged. Legacy records without these decisions retain unresolved history. Older readers reject the combined checkpoint instead of dropping unfamiliar metadata. Unknown versions are rejected with their bytes preserved. Reuse `DraftStore`/`DraftSession`, complete registrations, B/L/R field drafts/buffers, operation history and Apply/creation journal. No second database, queue, credential owner or hidden Issue prose. Metadata contains explicit Project start/cutoff, field mappings, exact adopted calendar, weights and task metadata. Exact intraday mode/time/attribution/calendar has **local checkpoint authority**. GitHub NUMBER scalars remain in the existing field-draft lifecycle; do not introduce another editable metadata copy of them. New tasks retain equivalent typed local values until verified promotion. Date/actual-total publication is a labelled projection. Typed Boards input routes through contextual date/report operations; generic scalar writes cannot bypass exact endpoints or attribution.

UI-free plan consumers use committed work and the same scoped metadata. No writes arise from input, calculations, saves, filters or switching. Publication retains explicit selection, fresh permissions, immutable approved payload, durable dispatch state, pacing, independent readback and uncertain-result recovery. No concurrent multi-device synchronization is claimed.

New-row TSV accepts committed estimate/remaining values in the visible column order; blank cells leave them unspecified, while an explicit clear is a retained creation intent. Date/actual projections use their coherent planning editor. Row duplication copies committed title, select and raw estimate/remaining values, starts Unplanned and does not fabricate actual history, dependency membership or date adoption for the new task. Add/duplicate/delete and their retained typed values share one operation-level Undo.

Do not split a local row's typed work or adopted plan from its Undo. After intervening remote input or creation lineage makes that compound operation unsafe, retain its current state and invalidate the whole operation with a reason. Ordinary independent title/select row operations keep their existing recoverable portions. Acknowledgement of selected NUMBER/DATE values invalidates older planning history that could diverge from the adopted projections. Shared native dependency acknowledgement does the same in every registered Project containing that Issue, even when the date-only projection happens to stay on the same day.

Undo of an earlier row addition/removal also checks later typed values, pending buffers and plan references outside the row object. If that older operation cannot restore them coherently, it is refused while the row and work remain available.

## Numeric, time and field rules

One person-day = eight raw hours. Accept finite nonnegative decimal hours <=1,000,000,000 with at most eight fractional digits; inspect the lexical fractional length before decimal parsing, including trailing zeros, and reject excessive precision rather than round raw labor. GitHub Float publication is limited to 15 significant decimal digits. Higher-precision accepted local work remains exact and explicitly unpublishable; do not round it to make it fit. Independent readback must equal the canonical decimal; a mismatch never acknowledges publication. The bounded proof covers representative values, not every service/version/magnitude. Formatting is not stored rounding.

Explicitly map distinct existing Project NUMBER fields to Estimate/Remaining/Actual and DATE fields to Start/Finish by ID/type. No automatic field creation or name remapping. A missing/type-changed field blocks dependent input/publication, preserves local work and leaves unrelated work available. Same-named native Issue fields are not substitutes. Arbitrary number/date editing is not selected implicitly.

An unavailable selected field retains its committed and pending draft in comparison. PMO may explicitly cancel that unavailable draft, with one Undo, before remapping the role; viewing or refreshing never cancels it. Incomplete Auto results cannot publish retained stale date projections. Adopted Manual/Auto tasks cannot return to Unplanned; explicitly selecting Auto is the only release of Manual dates. Reopened Auto requires newly entered or explicitly reconfirmed remaining work, including deliberate zero.

Use `DateTimeKind.Unspecified` for Asia/Tokyo wall-clock minutes, independent of machine timezone. Common week: Mon–Fri 09:00–13:00 / 14:00–18:00. Intervals are start inclusive/end exclusive. Valid finish at 13:00/18:00 stays there; positive new work advances to the next eligible interval. Required minutes = E / weight * 60, rounded upward once at the final schedule boundary. Expose that rounding without changing E. No resource leveling, staggering, productivity factor or headcount division.

Forward FS includes filtered-out prerequisites, Project start, earliest start, fixed start/finish and explicit cutoff for remaining work. Deadlines warn without shortening effort. Cycles, missing inputs, ambiguous owners, inaccessible prerequisites, unknown holiday years, zero capacity and impossible fixed constraints explain unresolved Auto results. Valid Manual pairs survive advisory conflicts; suggestion and warnings remain separate. Previous results, if retained, carry stale/source-revision labels. Hierarchy is never an FS edge.

A fixed finish places the unchanged duration back from that exact working boundary, then verifies the forward Project/cutoff/earliest/dependency bounds. A simultaneous fixed start must match that placement; an impossible pair is unresolved, with Manual available as an explicit exception. This does not enable automatic backward Project planning. Bound placement to ten years and report exhausted capacity explicitly. Completed Auto uses explicitly entered actual endpoints and deliberate zero remaining, never an update timestamp. Native state disagreements remain visible beside the PMO-selected progress; native state is not mutated by this feature.

## Remote edits, first use and restore

Complete explicit refresh reconciles NUMBER inputs through existing B/L/R. Preserve offscreen/pending native work; failed/partial refresh cannot replace the complete checkpoint. Changed GitHub DATE carries no time. Keep exact Manual endpoints/mode while showing baseline/local/remote days. Adopting the remote day requires PMO to confirm the exact endpoint; retaining local prepares its day projection. Remote clear also requires a decision and never flips mode. Unchanged day means projection compatibility, not remote proof of exact time. External actual-total changes preserve reports and require explicit attribution/correction and reporting date.

Compare R with B before treating a differing local day as an external edit: R=B preserves local intent; R equals the adopted local projection is compatible; R differs from both requires an exact-endpoint decision. Explicit remote-day adoption changes only the chosen endpoint, retains the other and establishes Manual. In the current assignment contract, one completely observed native assignee supplies the person identity; the Project supplies the explicitly configured weight. Estimate and remaining person contributions have independent nullable operands; unknown is never synthesized as zero.

Pending text is never a scheduling operand. A refresh whose remote value still matches the baseline or committed local value keeps calculating from the committed value while preserving the buffer. An actual B/L/R conflict remains unresolved. Both choices for an externally changed actual total require explicit cumulative reports and reported-through dates; a publishable total must still equal those reports after Undo. An empty report list explicitly clears the total; missing reports do not synthesize a zero or a reporting date.

Tasks without an adopted plan remain **Unplanned**, with unknown missing work. Explicit setup selects Project start, cutoff, mappings, calendar and person weights without inventing per-task owner metadata. In metadata v3/v4, the first valid Estimate commit initializes an Unplanned task to Auto using its observed assignment, in the same Undo operation. Missing capacity leaves an explained unresolved result. Viewing alone initializes neither method nor assignment. Existing legacy planning retains its owner, mode, exact dates and reports; adopting current assignment requires the contextual Auto comparison. Undo restores the earlier contract and data together. Unknown checkpoint/metadata versions or missing required assignment metadata reject with original bytes preserved; no default reset.
