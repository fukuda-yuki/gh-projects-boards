# Architecture

At rest, plan cells render text through lightweight TextBlock displays. The native TextBox remains the focus, selection, accessibility and input target; its text host participates in layout only while editing or composing. Recycled rows refresh the display from their current identity, including formatting, theme and read-only state. This trades one small display element per realized cell for avoiding idle native text-editor layout; it does not virtualize away columns or remove native input.

## Production boundaries

One UI-independent GhProjectsBoards.Core library and one GhProjectsBoards.App WinUI 3 application implement the [specification](spec.md). The GhProjectsBoards.Report console reuses Core for scheduled progress snapshots ([progress report tool](#progress-report-tool-262)). Core owns authentication orchestration, scoped identity, retrieval, validation, scheduling, local storage and publication. The app owns controls, presentation, window lifetime, file pickers, clipboard, shell document launching and UI Automation. No UI framework enters Core.

PlanManualHtml in Core converts the shipped Markdown text to escaped, self-contained HTML markup and resolves relative resources against the supplied manual directory. The UI reads the source, writes a per-user temporary HTML file and shows it in a single PlanHelpWindow (WebView2) that F1 reactivates; when WebView2 cannot start it falls back to the process-launch boundary. OpenDocument is the test seam that replaces both. Conversion/write failures retain the Markdown launch path. The capture script is development tooling over Start-Evaluation and Invoke-EvaluationUi, not a product execution mode.

## Workspace and settings (#81)

MainWindow hosts PlanWorkspaceView, sizes the ordinary window and cancels UI-owned remote operations, waits for their owned processes and local saves on close. Failed saves keep the window open. PlanWorkspaceView contains connection, Project discovery, the registered-Project list, the editable plan sheet and row-aligned Gantt and one settings page. Native control events invoke Core operations. Save recovery bypasses pending-input application until the retained save has been retried. The company day-off editor uses native calendar selection and explicit date-list changes. Pending text is committed before navigation or normal close; obsolete settings controls cannot apply late events after replacement.

PlanWorkspace reuses GhConnectionService, ProjectDiscovery, ProjectReader, PlanSession, PlanStore and PlanPublisher. It retains one session per scoped Project and writes an atomic workspace catalog beneath PlanningEditor/v1 before adopting a changed Project selection. Opening a new Project reads its complete snapshot and supplies the Project's people from the Issues' assignees; it never reads an assignable-user list. It matches typed columns and initializes empty period and phase milestone settings from that baseline before creating the session, without a settings command or Undo step. Opening an existing Project restores its local document; refreshing is explicit. Authentication is always rechecked; a saved Project does not imply a connected identity. The catalog does not read old registrations or checkpoints.

Column mappings, ordered sheet-column choices and their widths, display names of GitHub Project fields, calendar, people rates and allowances, company days off, Project start/end and repository are ProjectPlanSettings; the app's own columns keep their standard names, so a stored name for one is ignored (#319). Each accepted setting operation goes through ReplacePlanSettings, the same scheduler and bounded Undo history. Settings export/import use the existing Core JSON contract. Refreshed assignee display names and Issue links are remote metadata in PlanSync, separate from locally chosen rates; so is each row's Issue history, which yields the read-only 着手日 and 完了日 columns and is never a plan value or a publish write (#308). One assigned-people derivation serves settings, the summary and the month matrix: a stored person is listed only while a row holds them, and a row assignee without a stored entry appears at 100% with the readable login the read returned. File pickers remain in the view; the test substitution replaces only picking a path.

PlanSummary consumes the sheet's scheduled result, Project settings and status date without scheduling again. It groups leaf tasks into phase/person cells, known-effort totals with exclusions, attention identity sets and Project-end capacity measures over the same assigned people. PlanPeople accepts that same result for monthly daily-allocation/overload aggregation. Summary presentation is read-only; phase edits use the existing sheet operations and settings own rates and allowances through ReplacePlanSettings. Neither calculator writes remotely or levels resources.

## Planning editor Core

PlanRow and PlanBaseline retain typed day-level input and GitHub values, including the Issue's organization Issue type and the Project's type catalog (#319). Stable string field keys identify built-in fields and Project fields (Project: plus the GitHub field ID) across cell operations, history, conflicts and verified publication. Extra scalar observations retain availability separately from their invariant JSON value; repository catalogs resolve label and milestone names to remote identities. All supported Project values and Issue labels are included in every bounded Project read, independent of visibility, with batched continuation pages and repository-level catalog pagination. A mapped field has one editable owner; extra observations are cached but cannot produce edits or writes while a standard role owns that field. PlanScheduler produces derived dates, roll-ups, reasons and warnings from Remaining, rates, calendars, predecessors and hierarchy. Its exact internal work endpoints never become persisted minute dates.

PlanSession applies immutable operation patches, guards atomic rejection and owns the 200-step Undo history. PlanStore checks identity and data, serializes durable saves with optimistic fingerprint checks, writes and verifies temporary files, and atomically replaces the prior checkpoint. Failed saves retain the in-memory document for retry.

PlanCsvTemplate derives the header-only import template from the current column settings, and PlanCsvImport accepts exactly those shown editable columns (plus the previous header names) in any order, decodes and validates whole files through the sheet's own cell rules, resolves file keys and loaded Issue references, and prepares one InsertPlanRows command (#324). Repository and assignable-user catalog reads use the active Core connection lease; the view owns only native file selection, error presentation and repeat-import confirmation. A row's original-file SHA-256 is local provenance, follows normal row history/identity promotion and is never a GitHub field. New resource identities are added in the same command, preserving existing rates. Publication resolves repository placeholders by their destination rather than by one global default.

PlanSnapshot translates complete Project reads (including each Issue's state reason, #231, its organization Issue type and each Project item's and Issue's `updatedAt`) (#319) and the Issue-history read into the document's read observations (#308). A publish instead reads only the items it will write, by node ID, and assembles that scoped observation over the rows the read did not cover, so the same snapshot shape carries a whole Project in which only the written rows were re-observed (#201). PlanMerge reconciles baseline/local/remote values; the Issue's closed state, its reason and the close day are GitHub-owned unless the plan holds a pending state change, which the next read confirms instead of discarding. PlanValues canonicalizes numeric JSON for extra-field comparisons. Deleted-field edits are retained as nonblocking PlanConflict records with DeletedFieldName, while their values are removed from publishable rows; the review offers explicit discard. PlanPublishPlan and PlanPublisher provide ordered, batched writes (field/assignee requests up to four in flight, other phases serial), duplicate-guarded Issue creation, verification and durable recovery. PlanWorkspacePublish presents field differences and conflict choices and starts writes only on explicit confirmation. It reports publisher stages without a second outcome store. Closing the review leaves the workspace-owned operation running; window close cancels and awaits it. Failed and unverified rows come directly from PlanSync. See the [publish contract](spec.md#current-planning-editor-refresh-and-publishing-contract-79).

PlanCsvExport generates Excel-safe UTF-8 CSV bytes from an immutable document using the same effective rows, schedule and unpublished differences as the sheet. PlanSheetText and PlanSheetColumns share the indicator text and publish-review field names with the app. The view resolves pending input, picks a destination and runs generation/writing in background work; this path has no GitHub dependency. See [CSV export](spec.md#csv-export-173) for the column and file contract.

## GitHub boundary

GhConnectionService binds host, stable viewer and executable, serializes operations, rechecks identity and guards writes by authentication storage/scopes. GhApiTransport uses shell-free arguments and UTF-8 JSON stdin. GhProcessRunner owns process cancellation/timeouts and token-environment isolation. No token is retrieved, stored or displayed.

ProjectDiscovery pages the viewer's owners and one owner's Projects with closed state, last update and linked repositories, and resolves explicit same-host URLs. PlanWorkspace caches each owner's Project listing for the connection; ProjectChooserFilter derives repository entries and the filtered, ordered Project list without UI types. ProjectReader / ProjectQueries read fields, all items, assignees, blocked-by edges, parents and Issue types with complete pagination and scoped identities; each repository owner organization's Issue types are read once per read (#319). ProjectHistoryReader reads the Issue timeline events (Status changes, closes, reopens) with the same bounded batching, only for the Issues a read needs history for: a first open reads every Issue, and a refresh reuses each stored row's history while its Project item and Issue `updatedAt` are unchanged (#308). ProjectQueries also carries the on-demand assignee read that verifies one typed login against the row's repository on the read-only lease, with an exact login match, so assigning never needs the full assignable-user list. Within planning operation leases, the item traversal pipelines light 100-ID connection pages with nodes(ids:) detail requests of at most 25 IDs and six concurrent sends. Detail acceptance and reader state mutation remain in traversal order on one logical flow; all in-flight sends are observed before returning. The non-leased service path retains its per-request identity preflight and serialization. Incomplete observations are never accepted as complete snapshots.

## Native plan surface (#78)

PlanSheetView owns the selected cell/range, pending native TextBox input, clipboard, the attention strip's filter state, zoom and independent horizontal offsets. Core's `PlanFilter` is the one filter model (toggles, assignees, phases, title text and a named task set); Core decides the matching and context rows and the per-assignee copy text, and the sheet only presents them. Cell focus notifications update selection only while the cell still has focus. Copy, paste and clear capture row identities and column keys before entering the command queue; paste retains the visible ordering for matrix expansion across clipboard waits. PlanSheetRow presents a bounded set of virtualized rows with an offscreen buffer of one eighth of a viewport on either side (ItemsStackPanel.CacheLength 0.25); native cell editors are retained while their row container is reused. Each cell editor is a native TextBox with a reduced template that keeps only its border and text host and the default pointer and focus appearance, because a realized row carries a dozen editors and the default template's unused header, description, placeholder, delete-button and scroll-bar parts dominated the row's element count. Title, forecast, estimate and assignee cells also paint with an overlay, so their text host stays collapsed until the cell is editing or an IME composition needs the caret. The TextBox value, focus and input path stay. Cells, bars and dependency segments share DPI-aware compact row geometry. One ListView owns vertical scrolling and keeps one observable row source for its lifetime. Filtering and folding remove or insert membership by task identity without resetting unchanged native row editors while focus is within the rows or the change is small; a larger membership change with focus outside the rows replaces the source in one reset notification, because per-row notifications cost hundreds of milliseconds at version scale. Document reordering moves the corresponding identities. Containers can remain loaded during recycling, so focus requests verify a task's identity and owning sheet through the list's current container for that task. Native composition events guard IME confirmation separately from cell commit. Native key overrides return synchronously; asynchronous commits use captured managed values without retaining routed event arguments. The list's ContainerContentChanging notification establishes the row's current item identity, ownership and realized membership together; entering its recycle queue clears the binding and its automation identities. The notification's typed item distinguishes the empty append row from an unbound container. Template DataContext inheritance does not define this binding because native string content can project an empty value as a null context. The row template has no data bindings; its phase-zero notification is marked handled to avoid redundant DataContext propagation, following [WinUI’s manual item-update guidance](https://learn.microsoft.com/en-us/windows/apps/develop/performance/optimize-gridview-and-listview#update-listview-and-gridview-items-progressively). Child Loaded/Unloaded events do not define ownership because native reuse can keep a row loaded while its content changes. Recycling rebinds presentation and automation identities without retaining plan state in the row. Final window close is queued after the cancellable native closing callback returns.

The sheet derives schedule, unpublished fields and row metadata from one immutable document and calculation date. A filter-only refresh reuses those values; a changed document, including baseline/sync changes and Undo, invalidates them. Selection-only changes refresh the prepared rows in the old and new selection ranges, so selection highlights, range-end handles and the active row update without repainting unrelated rows. Document and layout changes still refresh all affected presentation. Toolbar overflow uses an app-owned animation-free flyout while CommandBar still determines width-driven primary-command overflow. Horizontal and Shift-wheel input is routed from the Gantt to its horizontal ScrollViewer before the row scroller handles it.

Dependency geometry is limited to each prepared row's vertical bounds, with a stroke guard outside its clip. Source and destination rows retain their individual native polylines and arrowheads with endpoint automation identities. Interior rows draw the straight crossing segments in one retained native Path per row; coincident segments with the same brush share one stroke. Its geometry includes only crossings within the horizontal viewport and a stroke guard, using a local origin so distant dates cannot enlarge its rasterization surface. The accepted horizontal offset updates this crossing geometry without refreshing cell editors. This bounds layout elements independently of the number of links crossing a row, while the path data remains proportional to its distinct visible crossings. Rebinding updates the current geometry and removes obsolete segments; neither paths nor endpoint shapes accumulate across previously visited rows. This is passive Gantt geometry: native cell editors, their automation values and input behavior are unchanged. Task bars update independently of unchanged dependencies. Row clips are retained; horizontal chart movement uses a translation while the sticky header follows the same accepted offset.

PlanSheetEditing translates visible rows/columns and text/clipboard into typed local operations using stable PlanRow identities. PlanSession remains the single state/history/save owner. Rendering and frame instrumentation use the same native controls as ordinary editing.

The planning editor uses PlanPublisher, PlanSession and the current scheduling model exclusively. Only the new scoped checkpoint format is loaded. Calendar resources and Project retrieval remain independent of editing and publication.

## Progress report tool (#262)

GhProjectsBoards.Report is a net10.0 console with no Windows dependency, for scheduled GitHub Actions runs. It only parses arguments and writes files. ProgressSnapshotReader in Core connects through GhConnectionService on a read-only lease, resolves the Project URL with ProjectDiscovery, reads it with PlanSnapshot.ReadConsistentAsync and builds a PlanDocument from that read and an imported settings file. ProgressSnapshot takes that document's PlanOperations.Schedule, PlanLateness and PlanSummary result, so the snapshot and the app's summary are one calculation. ProgressReport renders the Markdown report and its SVG trend chart from snapshot files alone, without GitHub. The reusable workflow `.github/workflows/progress-report.yml` builds the tool from this repository and commits the snapshot and report into the calling data repository; see [progress snapshots and report](spec.md#progress-snapshots-and-report-262).

## Validation boundaries

The [test policy](../tests/README.md) prioritizes logic, then UI integration, then representative E2E. Workspace adapter tests use real fake-gh subprocesses and isolated storage. Hosted UI tests exercise actual views, events and rendered values with the same Core. E2E drives the ordinary executable through public UI Automation, including restart. Fake endpoints do not establish live GitHub, physical IME, performance or human acceptance.

## Evaluation boundary

The test executable generates the offline evaluation data by replaying the team's daily progress with PlanOperations.Schedule, persists an ordinary PlanStore document and serves the matching remote rows through FakePlanEditor. Start-Evaluation.ps1 launches the ordinary app with an isolated data root and child-only PATH pointing to that fake executable. There is no product evaluation branch, network fallback or additional dependency. Resume retains both local edits and the fake remote state.

Milestone membership is read inside the Project item traversal; repository catalogs use the same bounded completeness checks. Baseline milestone groups and local task membership feed Core summary calculations, never scheduler inputs. Configurable task milestone membership uses the existing merge and verified publish pipeline. Phase-to-milestone mappings are local Project settings.

## AI assist (#208)

App adapts the SDK conversation through an `IAssistRuntime`/`IAssistTurn` transport boundary and Credential Manager through `IAssistSecretStore`. Hosted tests replace only those external edges and keep the real settings store, plan tools, command queue and session. A bounded channel delivers at most 32 events per dispatcher batch; virtualized conversation and change lists retain scrolling while the plan remains editable. Proposal application commits pending workspace input before checking the captured revision. No credential is held in a serializable settings or presentation model.

Core owns the non-secret app-wide `AssistSettingsStore`, strict schema and atomic writes under the same data root as `PlanStore`. The tool layer reads one `PlanSession` snapshot, calls `PlanOperations.Schedule`, `PlanSummary`, `PlanLateness` and unpublished-change calculations, and returns serializable records with stable row identities. Manual retrieval reads the Markdown source used by `PlanManualHtml`. Proposals validate a single existing `EditPlanCells` command on a candidate document; application checks the captured session revision atomically with executing that command. No separate edit, history, scheduling or publish path is introduced.

A Core conversation owns the SDK client and session as an external edge: isolated stdio Empty runtime, curated environment, verified gh-cli host/viewer identity or caller-supplied BYOK credentials, five custom tools, deny-all permissions and UI-independent streaming/tool-progress/turn/error/cancellation events. Session state is deleted at conversation end; `AssistConversation.CleanupLeftovers` removes leftovers at app startup and runtime startup repeats that cleanup. Per-conversation directories have exclusive leases so another window cannot remove a running conversation. The App owns the pane, settings section, task navigation, proposal cards and user confirmation, the user-scoped Windows Credential Manager secret store, and ending the conversation on Project/account/settings changes or window close. Close grants a short runtime stop timeout followed by force stop. App-wide assist settings never enter Project history or settings import/export.

## Issue detail pane (#211)

Core owns the single-Issue reader, the single-body publisher (conflict re-read, identity check, one `updateIssue`, readback) with its line-ending and plan-marker rules, and UI-independent model/parsing through the authenticated gh boundary. App owns the pane, the selection-line toggle wiring, the in-memory body draft and its discard checks, selection debounce, session cache and its invalidation wiring, WebView2 environment/rendering with native Markdown fallback, and the injectable external-link edge. The shared detail/assist dock has one visible pane; detail content never enters plan storage or assist tools. Detail cancellation precedes remote operations using the connection gate.
