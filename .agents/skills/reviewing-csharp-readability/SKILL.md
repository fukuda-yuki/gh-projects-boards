# C# 可読性レビュー

読者がそこで止まるかを見る。指摘はチェックリストの項目だけで構成し、各指摘は決められた欄を埋める。

## 手順

1. 対象を決める。パスならそのファイルを読む。差分なら追加・変更された `.cs` だけを対象にし、名前と型を判断するのに必要な周囲も読む。貼り付けならその C# を対象にする。対象が無ければ、どのファイルかを聞く。リポジトリ全体はレビューしない。
2. `<TargetFramework>` が読めるときはそれを使う。読めないときは .NET 10 / C# 14 と出力の先頭に書く。
3. 見送りに当てはまるファイルは指摘しない。出力の見送り節に、ファイル名と理由を一行で書く。
4. 差分レビューでは、追加・変更された行を指摘する。変更が依存して新しいコードが読めなくなる既存コードだけ、あわせて指摘する。
5. コードは、ユーザーが適用を頼んだときだけ変える。
6. 指摘が無いときは「指摘はない」と書く。

## 出力

ユーザーの言語で、この形だけを出す。

~~~markdown
# 可読性レビュー: {対象}

対象: .NET {version}。根拠: {csproj の TargetFramework、または指定が無いため .NET 10 / C# 14}。可読性のみ。

## 見送り

- {ファイルまたは観点}: {理由}

## 指摘

### 1. {path:line} {メンバー} — {名前|コメント|条件|式|構造|言語機能|Web}

読者が止まる理由: {その場で追えないもの}
書き換え:

```csharp
{その指摘の範囲だけ。ドメイン語は残す}
```

質問: {その語がドメイン語かもしれないときだけ。何を指すかを聞く}

## 読めているところ

- {具体的な名前、構造、またはコメント}
~~~

見送りが無いときは、見送り節に「なし」と書く。質問欄は、ドメイン語の可能性がある指摘だけに付ける。

## 見送り

次のファイルは見送り節に名前を書いて終える。`.html`、`.css`、`.scss`、`.js`、`.ts`、`.tsx`、`.jsx`、`.razor`、`.cshtml`。

チェックリストに無い事項は指摘にしない。セキュリティ、秘密情報、認可、割り当て、LINQ の性能、N+1、二重列挙、テストの有無、インデント、波括弧、`using` の並び、`var` と明示型の選択、ログレベルの妥当性はここに入る。`Span<T>` の暗黙変換、ユーザー定義の複合代入、`partial` コンストラクタも、可読性の提案にしない。

## 採用する規則

- 失敗はガード節と早い `return` で抜ける。出口を一つにまとめない。
- ネストが 3 段以上なら指摘する。行数や文数だけでは指摘しない。長さは、上位の目的と下位の目的が混ざっているかを見るきっかけにする。
- 非同期メソッドの `Async` 接尾辞は残す。
- 公開する HTTP 契約と、ライブラリとして公開するメンバーには、名前の繰り返しではない一行の XML ドキュメントを求める。private メンバーには求めない。全シンボルへの日本語コメントは求めない。
- ドメイン語かもしれない名前は断定しない。書き換えにはその語を残し、質問欄で何を指すかを聞く。
- 新しい構文は、読者が追う名前か分岐が減るときだけ提案する。

## チェックリスト

### 名前

Microsoft の C# 命名に合わせる。型とメンバーは PascalCase、private フィールドは `_camelCase`、ローカルと引数は camelCase、インタフェースは `I`、型引数は `T` で始める。record の位置パラメータは PascalCase、class のプライマリコンストラクタ引数は camelCase。

- 名前から動作が一つに読める。`Get`、`Process`、`Handle`、`Data`、`Info`、`Manager` は、型と呼び出し箇所を見ても動作が決まらないときに指摘する。
- 型がすでに示している語は削る。`ConvertToString` は `ToString` で足る。
- `bool` は `Is`、`Has`、`Can` で、保持している事実が読める。
- 単位と境界が名前にある。`TimeoutMilliseconds`、`MinInclusive`、`First` と `Last`、`Begin` と `End` のように、「以下」と「未満」が区別できる。
- `i` や `v` は、数行で閉じるスコープに限る。
- 略語は、そのコードベースで広く通っているものだけを使う。
- ファイル内で、同じ種類の操作に同じ語を使う。

### コメント

- 一読で分かるコメントは消す。
- 残すのは、なぜそうしたか、制約、定数の根拠、未完了の `TODO`。
- 古いコメント、代名詞が多いコメント、二通りに読めるコメントを先に直す。
- 説明が長い公開メソッドには、入出力の短い例を XML ドキュメントに添える。

### 条件

- 調べる値を左、比較対象を右に置く。`if (count == 0)`。
- 否定より肯定を使う。
- 失敗はガード節で先に `return` する。ループ内の除外は `continue` にする。
- ネストは 2 段までを通常とし、3 段以上を指摘する。
- 二つの値から一方を選ぶだけの分岐は、条件演算子、`??`、`?.` にする。副作用が隠れる場合は文のままにする。
- `do`/`while` は、本体を一度は実行する理由がコメントにあるときだけ許す。
- 後続の `if` を操るためだけの `bool` 変数は、ガード節か別メソッドに分ける。

### 式

- 複雑な式と長い論理式は、意図の名前を持つメソッドに出す。
- 固定値は名前付き定数にする。`0`、`1`、`-1`、空文字のように、意味が名前と一致するものはそのままにする。定数には、なぜその値かを書く。
- 一度しか使わない単純な一時変数は置かない。複雑な論理式を説明するための変数は残す。
- ローカル変数への代入は一度を基本にする。ループの集計は、その名前が集計と分かるなら許す。
- オブジェクトの状態でない値は、フィールドではなく引数かローカルに置く。
- インスタンス状態を使わないメソッドは `static` にする。
- 読まれない private メンバーとローカルは指摘する。

### 構造

- 一つのメソッドは一つの目的にする。取得、変換、除外、検証、結果への写像は下位目的なので、本体の物語が混ざったときに分ける。
- 各行を、平易な一句で言える。
- エンドポイントのハンドラーとコントローラのアクションは、検証、呼び出し、結果への写像が短い名前の並びとして読めるなら、この分割を求めない。下位の処理が本体内に展開されていたら指摘する。
- 型の中は、状態、構築、公開操作、非公開の補助の順でグループにし、グループの間は空行で分ける。
- ファイルスコープ名前空間を使う。

### 言語機能

- 不変の要求、応答、DTO は `record` にする。同一性や変更が本体の型は `class` のままにする。
- 「必ず入る」は `required` や `init` で示し、コメントで補わない。
- DI するサービスはプライマリコンストラクタでよい。依存が多く、型の仕事も複数なら指摘する。
- リストや配列の中身が主役ならコレクション式を使う。
- `if` の階段が値の分岐なら、`switch` 式やパターンにする。
- バッキングフィールドが null 拒否や整形のためだけなら、`field` キーワードに寄せる。アクセサ内のローカル名 `field` は指摘する。
- `?.` の代入は、「null なら何もしない」が読み取れるときだけ使う。
- `extension` ブロックは、その型のメンバーとして読める操作に限る。サービス依存を隠す拡張にはしない。

### Web

- ハンドラーとアプリケーションサービスは、ユースケースが名前になる。
- 要求と応答のプロパティ名は、クライアントが読む契約として、名前の規則を同じ厳しさで見る。
- 検証ルールは、失敗の理由が文として読める。
- ドメインの結果から `IResult` や ProblemDetails への写像は、一箇所で追える。ステータスコードの数値を処理の途中へ散らさない。
- ミドルウェアとフィルタは、通す条件か拒む条件が名前になる。実行順に意味があるときは、その理由をコメントする。
- Options のプロパティには単位と境界を入れる。セクション名とクラス名は対応させる。
- クエリメソッドは、どの条件の何を返すかが名前になる。長いクエリは、仕様か名前付きメソッドに出す。
- ログのメッセージテンプレートは、業務上の出来事が読める。
- 例外の型とメッセージは、失敗した条件が読める。理由のコメントがないまま握りつぶす `catch` は指摘する。

## 例

指摘の粒度は、この一段である。

対象コード:

```csharp
public async Task<IResult> Process(int id)
{
    var data = await _db.Orders
        .Where(o => o.CustomerId == id && o.Status == 2)
        .ToListAsync();
    var result = new List<OrderResponse>();
    foreach (var d in data)
        result.Add(new OrderResponse { Name = d.Name, Total = d.Total });
    return Results.Ok(result);
}
```

### 1. OrdersEndpoint.cs:1 Process — 名前

読者が止まる理由: `Process` では、注文を確定するのか、出荷済みの注文を返すのかが決まらない。
書き換え:

```csharp
public async Task<IResult> ShippedOrdersForCustomerAsync(int customerId)
```

質問: `Status == 2` は出荷済みでよいか。

### 2. OrdersEndpoint.cs:4 Process — Web

読者が止まる理由: `2` がどの注文状態かを、クエリの途中で思い出せない。
書き換え:

```csharp
.Where(order => order.CustomerId == customerId
    && order.Status == OrderStatus.Shipped)
```
